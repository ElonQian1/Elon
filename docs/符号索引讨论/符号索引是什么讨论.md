**符号索引，就是给代码里的“名字”建索引。**

在 repo map 里，文件结构告诉 AI：

> 这个项目有哪些文件、目录、模块。

而**符号索引**告诉 AI：

> 每个重要的函数、类、struct、trait、enum、method、常量、类型、模块在哪里定义，长什么样，被谁使用，和谁有关。

可以把它理解成代码仓库的：

> **通讯录 + 目录 + 跳转表 + 关系图**

---

# 1. 什么是“符号”？

“符号”就是代码里有名字、可以被引用的东西。

比如 Rust 里：

```rust
pub struct User {
    pub id: UserId,
    pub email: String,
}

pub trait UserRepository {
    async fn find_by_email(&self, email: &str) -> Result<Option<User>, AppError>;
}

impl AuthService {
    pub async fn login(&self, email: &str, password: &str) -> Result<Token, AppError> {
        // ...
    }
}

pub const MAX_RETRY: usize = 3;
```

这里的符号包括：

```text
User
User.id
User.email
UserRepository
UserRepository::find_by_email
AuthService
AuthService::login
MAX_RETRY
UserId
AppError
Token
```

对于不同语言，符号种类不一样：

```text
函数 function
方法 method
类 class
结构体 struct
枚举 enum
trait / interface
type alias
常量 constant
变量 variable
模块 module
namespace
宏 macro
字段 field
构造器 constructor
测试函数 test
```

在 Rust 项目里，尤其要关注：

```text
crate
mod
use
pub / pub(crate)
struct
enum
trait
impl
fn
async fn
const
static
type
macro
derive
associated type
generic parameter
```

# 2. 什么是“符号索引”？

符号索引就是一张表，记录每个符号的信息。

比如：

```text
符号名: AuthService::login
类型: method
文件: src/service/auth_service.rs
位置: line 42 - line 87
签名: pub async fn login(&self, email: &str, password: &str) -> Result<Token, AppError>
所属对象: AuthService
可见性: pub
依赖: UserRepository, TokenService, PasswordHasher, AppError
被使用于:
  - src/api/auth_handler.rs
  - tests/auth_login_test.rs
```

也可以用 JSON 表示：

```json
{
  "id": "src/service/auth_service.rs::AuthService::login",
  "name": "login",
  "qualified_name": "crate::service::auth_service::AuthService::login",
  "kind": "method",
  "language": "rust",
  "file": "src/service/auth_service.rs",
  "start_line": 42,
  "end_line": 87,
  "signature": "pub async fn login(&self, email: &str, password: &str) -> Result<Token, AppError>",
  "visibility": "pub",
  "parent": "AuthService",
  "references": [
    "src/api/auth_handler.rs",
    "tests/auth_login_test.rs"
  ],
  "depends_on": [
    "UserRepository",
    "PasswordHasher",
    "TokenService",
    "AppError"
  ]
}
```

但是注意：**JSON 适合存储，不一定适合直接给 AI 看。**

最终喂给 AI 的时候，可以渲染成更省 token、更像代码笔记的格式：

````md
## src/service/auth_service.rs

Defines:

```rust
pub struct AuthService<R: UserRepository> {
    repo: R,
}

impl<R: UserRepository> AuthService<R> {
    pub async fn login(&self, email: &str, password: &str) -> Result<Token, AppError>;
}
````

Depends on:

* UserRepository
* PasswordHasher
* TokenService
* AppError

Used by:

* src/api/auth_handler.rs
* tests/auth_login_test.rs

````

# 3. 符号索引有什么用？

## 用处一：让 AI 快速知道“该看哪里”

没有符号索引时，用户问：

> 登录逻辑在哪里？

AI 只能靠文件名猜：

```text
auth.rs
login.rs
user.rs
handler.rs
service.rs
````

有符号索引后，系统可以直接搜：

```text
login
AuthService::login
LoginRequest
UserRepository::find_by_email
PasswordHasher::verify
TokenService::issue
```

然后把最相关的文件和函数放进上下文。

这会显著减少 AI 瞎猜路径、瞎改文件的概率。

---

## 用处二：让 repo map 不只是“文件地图”，而是“代码语义地图”

普通 repo map 可能只是：

```text
src/
  main.rs
  config.rs
  service/
    auth_service.rs
  repository/
    user_repository.rs
```

这只能告诉 AI 项目结构。

符号索引可以告诉 AI：

```text
AuthService::login 定义在 src/service/auth_service.rs
AuthService::login 调用了 UserRepository::find_by_email
UserRepository trait 定义在 src/repository/user_repository.rs
PostgresUserRepository 实现了 UserRepository
auth_handler::login_handler 调用了 AuthService::login
tests/auth_login_test.rs 测试了 AuthService::login
```

这就从“目录树”升级成了“代码关系图”。

---

## 用处三：做精准上下文检索

比如用户说：

> 帮我修改注册逻辑，要求邮箱重复时返回 409。

系统可以通过符号索引查：

```text
register
signup
create_user
UserService
UserRepository
DuplicateEmail
Conflict
```

然后找到：

```text
UserService::register
UserRepository::find_by_email
UserRepository::create
AppError::Conflict
register_handler
tests/register_test.rs
```

最后给 AI 的上下文可能只需要这些：

```text
src/service/user_service.rs
src/repository/user_repository.rs
src/api/user_handler.rs
src/error.rs
tests/register_test.rs
```

而不是把整个 repo 都塞进去。

这就是 repo map 最重要的作用之一：**压缩上下文，但不丢关键语义。**

---

## 用处四：做“影响范围分析”

假设你要改：

```rust
pub trait UserRepository {
    async fn find_by_email(&self, email: &str) -> Result<Option<User>, AppError>;
}
```

如果没有符号索引，你不知道这个 trait 被哪里实现、哪里调用。

有符号索引后，可以查到：

```text
Implementations:
- PostgresUserRepository
- MockUserRepository
- InMemoryUserRepository

Callers:
- AuthService::login
- UserService::register
- AdminUserService::find_user

Tests:
- tests/auth_login_test.rs
- tests/register_test.rs
```

这样 AI 就知道：

> 改这个 trait，不只要改定义，还要改实现、调用方和测试。

这对于大型项目非常重要。

---

## 用处五：辅助重构

符号索引可以支持很多高级操作：

```text
rename symbol
move function
extract module
find unused function
find all references
find implementations
find callers
find callees
detect circular dependency
detect duplicate abstractions
```

比如你要把：

```rust
AuthService::login
```

改名成：

```rust
AuthService::authenticate
```

符号索引可以告诉你所有引用位置：

```text
src/api/auth_handler.rs:31
src/cli/login_command.rs:18
tests/auth_login_test.rs:44
tests/auth_error_test.rs:71
```

这比纯文本搜索安全得多，因为纯文本搜索可能误伤注释、字符串、同名局部变量。

---

## 用处六：让 AI 更少幻觉

AI 最容易犯的错之一是：

```text
调用不存在的函数
引入不存在的类型
误判模块路径
忘记 trait 约束
搞错函数签名
搞错错误类型
```

符号索引能给 AI 提供真实存在的 API：

```rust
pub async fn find_by_email(&self, email: &str) -> Result<Option<User>, AppError>
```

AI 看到这个签名后，就不容易编出：

```rust
repo.get_user_by_email(email).await?
```

而是更可能写对：

```rust
repo.find_by_email(email).await?
```

# 4. 符号索引和全文搜索有什么区别？

全文搜索是搜字符串。

例如搜索：

```text
login
```

可能搜到：

```text
函数名 login
注释里的 login
README 里的 login
测试描述里的 login
字符串 "login failed"
变量名 login_attempts
```

符号索引搜的是代码语义。

它知道：

```text
login 是 AuthService 的方法
login_handler 是 HTTP handler
LoginRequest 是请求 DTO
LoginError 是错误类型
```

区别大概是：

| 能力             | 全文搜索 | 符号索引 |
| -------------- | ---: | ---: |
| 搜文件内容          |   可以 |   可以 |
| 知道函数定义在哪里      |  不稳定 |   可以 |
| 知道函数签名         |  不稳定 |   可以 |
| 知道谁调用了它        |   很难 |   可以 |
| 知道 trait 的实现   |   很难 |   可以 |
| 支持安全重构         |   很弱 |    强 |
| 适合 AI repo map |   一般 |  很重要 |

全文搜索是基础能力，符号索引是语义能力。

# 5. 符号索引和 AST 有什么区别？

AST 是代码的语法树。

比如这段代码：

```rust
pub async fn login(&self, email: &str) -> Result<Token, AppError> {
    // ...
}
```

AST 会记录得非常细：

```text
visibility: pub
async: true
function name: login
parameters:
  - self
  - email: &str
return type:
  - Result<Token, AppError>
body:
  - ...
```

符号索引不是完整 AST。

符号索引是从 AST 里提取出来的“重要导航信息”。

可以理解为：

```text
源码 code
  ↓ parse
AST 语法树
  ↓ extract important named things
符号索引 symbol index
  ↓ rank / render
repo map
  ↓ send to AI
LLM context
```

AST 很细，适合程序分析。
符号索引更轻，适合检索、跳转、repo map、AI 上下文。

# 6. 一个符号索引通常应该包含什么？

我建议你的 MVP 至少包含这些字段：

```text
id
name
qualified_name
kind
language
file_path
start_line
end_line
signature
visibility
parent_symbol
module_path
doc_summary
```

例如：

```json
{
  "id": "sym_001",
  "name": "login",
  "qualified_name": "crate::service::auth_service::AuthService::login",
  "kind": "method",
  "language": "rust",
  "file_path": "src/service/auth_service.rs",
  "start_line": 42,
  "end_line": 87,
  "signature": "pub async fn login(&self, email: &str, password: &str) -> Result<Token, AppError>",
  "visibility": "pub",
  "parent_symbol": "crate::service::auth_service::AuthService",
  "module_path": "crate::service::auth_service",
  "doc_summary": "Authenticates user credentials and returns an access token."
}
```

第二阶段再加关系：

```text
references
calls
called_by
imports
exports
implements
implemented_by
overrides
type_uses
test_targets
```

例如：

```json
{
  "from": "crate::api::auth_handler::login_handler",
  "to": "crate::service::auth_service::AuthService::login",
  "relation": "calls"
}
```

第三阶段再加 AI/RAG 相关字段：

```text
embedding
importance_score
last_modified
git_commit
chunk_hash
token_estimate
summary
```

# 7. 对 repo map 来说，最关键的不是“所有符号”，而是“重要符号”

不要把每个局部变量都索引进去，否则 repo map 会爆炸。

优先级应该是：

## 高优先级

```text
public function
public struct
public enum
public trait
trait method
impl method
constructor/new
main entry
handler/controller
service method
repository method
error type
config type
test function
macro
```

## 中优先级

```text
private function
private helper
field
associated type
type alias
module-level const
```

## 低优先级

```text
局部变量
临时变量
循环变量
match 分支内部变量
短生命周期闭包参数
```

对 AI repo map 来说，通常不需要这些：

```rust
let x = ...
let result = ...
for item in items
|x| x.id
```

除非你要做非常细的代码分析或静态检查。

# 8. Rust 项目的符号索引要特别注意什么？

Rust 里有几个难点，容易让 repo map 做错。

## 1. `impl` 和类型定义是分开的

```rust
pub struct AuthService<R> {
    repo: R,
}

impl<R: UserRepository> AuthService<R> {
    pub async fn login(&self, email: &str, password: &str) -> Result<Token, AppError> {
        // ...
    }
}
```

符号索引里不能只记录 `login`，最好记录成：

```text
AuthService::login
```

并且知道它属于：

```text
AuthService<R>
```

---

## 2. trait method 和 impl method 要区分

```rust
pub trait UserRepository {
    async fn find_by_email(&self, email: &str) -> Result<Option<User>, AppError>;
}

impl UserRepository for PostgresUserRepository {
    async fn find_by_email(&self, email: &str) -> Result<Option<User>, AppError> {
        // ...
    }
}
```

这里至少有两个符号：

```text
UserRepository::find_by_email
PostgresUserRepository::find_by_email
```

并且它们之间有关系：

```text
PostgresUserRepository::find_by_email implements UserRepository::find_by_email
```

这个关系对 AI 很有用。

---

## 3. `use` 和 re-export 很重要

```rust
pub use crate::domain::user::User;
```

AI 可能看到某个文件里用了：

```rust
User
```

但真实定义在：

```text
crate::domain::user::User
```

如果符号索引能处理 `use` 和 `pub use`，AI 会更容易搞清楚路径。

---

## 4. 宏和 derive 可能生成隐藏符号

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct User {
    // ...
}
```

这些不会显式出现为函数，但会影响可用能力。

MVP 阶段可以先记录 attribute：

```text
derive: Debug, Clone, Serialize, Deserialize
```

不一定要展开宏。

# 9. 推荐你的符号索引数据结构

你可以用两个核心表：`symbols` 和 `relations`。

## symbols 表

```sql
CREATE TABLE symbols (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    qualified_name TEXT NOT NULL,
    kind TEXT NOT NULL,
    language TEXT NOT NULL,
    file_path TEXT NOT NULL,
    start_line INTEGER NOT NULL,
    end_line INTEGER NOT NULL,
    signature TEXT,
    visibility TEXT,
    parent_id TEXT,
    module_path TEXT,
    doc TEXT,
    hash TEXT
);
```

## relations 表

```sql
CREATE TABLE symbol_relations (
    id TEXT PRIMARY KEY,
    from_symbol_id TEXT NOT NULL,
    to_symbol_id TEXT NOT NULL,
    relation_kind TEXT NOT NULL,
    confidence REAL DEFAULT 1.0
);
```

`relation_kind` 可以是：

```text
defines
contains
calls
called_by
references
imports
exports
implements
implemented_by
extends
uses_type
tested_by
```

再加一个 `files` 表也很实用：

```sql
CREATE TABLE files (
    id TEXT PRIMARY KEY,
    path TEXT NOT NULL,
    language TEXT NOT NULL,
    module_path TEXT,
    hash TEXT NOT NULL,
    last_modified INTEGER
);
```

# 10. 最小可用版怎么做？

你可以先别追求完美语义解析。

MVP 只做这些就已经很有用了：

```text
1. 遍历项目文件
2. 用 tree-sitter 或语言 parser 抽取符号
3. 记录文件路径、符号名、符号类型、行号、签名
4. 建立 parent-child 关系
5. 建立 import/use 关系
6. 根据用户问题检索相关符号
7. 渲染成 Markdown repo map 给 AI
```

MVP 的输出可以像这样：

```md
<symbol_index>

## crate::service::auth_service

File: src/service/auth_service.rs

Symbols:
- struct AuthService<R>
- impl<R: UserRepository> AuthService<R>
- method AuthService::login(email: &str, password: &str) -> Result<Token, AppError>

Relations:
- AuthService::login uses UserRepository
- AuthService::login returns Token
- AuthService::login returns AppError
- AuthService::login is called by login_handler

</symbol_index>
```

这已经足够让 AI 对项目有明显更好的理解。

# 11. 你可以这样理解它在 repo map 里的位置

完整流程是：

```text
文件树
  ↓
源码解析
  ↓
AST
  ↓
符号索引
  ↓
符号关系图
  ↓
根据任务排序
  ↓
渲染 repo map
  ↓
给 AI
```

所以 repo map 不是单一东西，而是一个生成结果。

符号索引是 repo map 背后的核心基础设施。

没有符号索引，repo map 大多只是：

```text
这个项目有哪些文件
```

有了符号索引，repo map 才能变成：

```text
这个项目有哪些重要概念
这些概念在哪里
谁调用谁
改一个地方会影响哪里
AI 应该优先读哪里
```

---

# 12. 最终建议

你的 repo map 系统可以这样设计：

```text
SQLite / JSONL 存 symbol index
        ↓
relations 表存调用、引用、实现、依赖关系
        ↓
根据用户任务召回相关 symbol
        ↓
按重要性排序
        ↓
渲染成 Markdown + 代码签名
        ↓
喂给 AI
```

一句话总结：

> **符号索引就是代码仓库的语义目录。它让 AI 不只是看到文件，而是看到函数、类型、trait、模块和它们之间的关系。**

对于你要做自己的 repo map 来说，符号索引是非常关键的一层。它决定了你的 repo map 能不能从“文件列表”升级成“代码理解系统”。
