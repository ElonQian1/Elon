# 跨平台媒体卡片实施记录

## 本轮范围

- 原因：上一轮只有方案。已有大封面布局只对视频号启用，B站、抖音、小红书仍走 56px 缩略图普通链接卡。
- `social_links.js/css` 负责 Win/PWA 的统一媒体外观；APK 复用 `SocialLinkCardView`，不新增独立播放器或网页抓取引擎。
- 卡片显示真实封面、两行标题、作者/平台与入口。横竖比例取实际图片，范围限制为 2:3 至 16:9，不裁掉封面内容。无图/图片失败时仅占 100px 媒体区，不出现破图和大片空白。
- 小红书仍是笔记，不假定都是视频；其入口使用查看标记。普通首页、仿冒域名不升级为媒体卡。
- 视频号继续使用原有 3:4 海报、作者头像与直接微信打开；保留“查看原网页”。没有修改其协议和后台播放器。
- 保留原消息、带参链接、B站时间位置、长按/右键/多选和 AI 回复。
- 预览层过滤小红书登录/首页元数据；抖音 iframe 元数据检查业务错误码。已有标题不能阻止同身份校验通过的成员封面回填。
- 真机补缺：B站嵌套 `【标题【副标题】】` 使用有界括号解析，完整分享文案可折叠，额外评论仍保留。B站原网页读回扩展到同一 BV 号，必须可见标题与 Open Graph 标题一致，只允许 `hdslb.com/bfs/archive/` 视频封面，拒绝其他视频、头像及仿冒域名。
- APK 1826 验收发现，B站打开的是官方嵌入播放器而非原网页，原网页读回不会执行。补充独立公开元数据请求：服务器无封面时按 BV 号获取标题、作者、封面，4 秒超时、256 KiB 限额、禁止重定向，复用现有预览缓存和后台队列。不复制凭证，不改变播放器路由。1827 已发布并通过下述真机卡片验收。

## 抖音与小红书封面补齐（后续批次）

- 读取完整外链：Win 群业务 MCP 新增只读 `links`，要求已绑定账号、指定群和一条消息，最多返回两条完整支持平台 URL。不能用 `messages.preview` 的 240 字摘要代替原链接；访问参数不写入日志或报告。
- 服务端增加同内容 ID 的公开 hydration JSON 解析：抖音 `RENDER_DATA`、小红书 `__INITIAL_STATE__`；不执行下载的 JavaScript。维持公网逐跳校验、长度限制、CDN 校验及现有封面副本。只有标题但缺图的两平台结果缓存 5 分钟，失败仍为 30 秒。
- APK / Win 共用原网页适配器。抖音在文档开始时被动观察官网本来就会发出的详情响应，只保留同视频 ID 的标题、作者、封面，不重发带签名请求，不保存请求头或凭证。小红书读取同 note ID 的页面状态，并核对可见正文/标题。
- 抖音原网页路由取服务端已解析出的稳定视频 ID，缓存仍用原分享 URL；APK 此类页面使用桌面浏览模式，保留官方播放器合同。小红书始终保留完整查询参数。
- 这两类用户页面的读回仅进入本机账号隔离缓存，不默认上报共享服务器。没有为聊天中每张卡片启动隐藏 WebView；未取得公开封面的链接可能需要用户首次打开原网页，不能宣称所有首屏卡片都会自动有图。
- 实际抖音样本：正常匿名桌面 Chromium 页面成功返回同 ID 详情，生产共享适配器读回成功，真实封面请求 HTTP 200。独立 HTTP/事后重放详情请求失败，因此已删除重放方案，使用上述被动观察。
- 自动验证：共享适配器的 XHS 同 ID/隐藏正文/仿冒 CDN，以及抖音 fetch/XHR 被动读回/零额外请求/切换内容检查通过；PC 生产组件读回缓存、短链别名、账号隔离、过期与容量检查通过；PC 类型检查和服务端预览 harness 通过。
- 首批发布：Server / PC 前端 `0.3.1788`（`6308a9358`），Win 实际桌面与节点 MCP 回读均为 `0.3.69+01924062f730f805382712fa25b9412a1351a486`，升级恢复回执 `8327bf59-d9bd-4c0b-b383-14a3d68b24ea` 成功。APK `1.1.1828` 已通过 `-r` 安装小米并回读版本；荣耀离线。
- 使用群业务 MCP 读取小红书完整原链接后，真实桌面 Chromium 生产适配器已返回同 note ID 的标题、作者、封面，图片 HTTP 200；没有复制登录凭证或公开链接参数。
- 1828 真机验收仍发现缺图，未据浏览器成功宣称手机成功。两个具体断点：小红书手机页使用 `noteData.data.noteData`、`.author-desc` 和 `user.nickName`，不是桌面结构；APK 阅读器 Intent 已传 `player` / `x_id`，但 Activity 未恢复，抖音已解析视频 ID 被丢弃。
- 后续修复补齐移动笔记的同 ID 解析和可见正文校验；恢复阅读器参数时限定平台、嵌入域名和内容 ID，拒绝跨内容覆盖及任意播放器地址。小红书真实 Android UA 页面读回与封面 HTTP 200 已通过；新增移动页/隐藏正文/错 ID 与 Intent 恢复回归测试。新 APK 真机结果在安装验收后追加。

## 未完成边界

- 抖音公开 iframe 仍不提供封面；后续批次已确认正常桌面网页的被动响应读取可行（见上），不代表独立 HTTP 调用、所有账号/内容或各端真实播放均可用。
- 小红书群样本仍保留完整访问参数。真实桌面和移动浏览器已确认封面可获取，APK 卡片显示结果以最后真机记录为准；不能据此保证所有链接、已删除内容或访问受限内容均有封面。
- 本轮不宣称 B站/抖音的实际声音/首帧播放、Win 视频号精确直达、新平台原生 handoff、YouTube/TikTok/Vimeo 已完成；相关策略继续按方案推进。
- B站 APK 独立公开元数据补丁未移植到 Win HTTP 层。Win 可用服务器或同 BV 原网页读回缓存，浏览器生产组件已用真实封面验证布局，但不把 APK 实测当作 Win 群样本自动取图的证据。
- PC 不增加 `pc_page` 遗留入口。卡片样式通过 PC 前端资源发布更新；B站原网页读回适配器也被桌面壳 `include_str!` 嵌入，因此该新增读回能力必须更新桌面二进制，不能用网页刷新回执代替。未更新桌面仍可显示服务器/已有缓存返回的真实封面。
- 已更新桌面的无人值守回执：`69ab66f5-8ae2-4915-88db-c541989dbdda`，`workflow_complete=true`；本轮 Win 运行版本核对与浏览器生产组件布局验证均完成，但没有将其表述为 Win 所有平台封面和视频播放均已真机验收。
