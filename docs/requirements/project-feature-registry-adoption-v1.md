# 一龙项目功能注册表启用要求 V1

## 目标

在一龙项目自身启用 Git 共享的功能注册表，使 Codex、Copilot、Claude、Gemini 和平台内 AI 能通过同一低 token 工作流判断功能状态、需求范围、依赖和证据，减少重复实现及误用旧议案。

## 范围

- 使用现有 `project_feature_workflow` 创建和维护 `.elon/project-features.json`，禁止代理手工编辑注册表。
- 首批只登记当前明确、可维护的功能，不批量迁移全部历史讨论或把长期愿景伪装成待开发任务。
- 每项功能必须绑定当前需求 Markdown、短摘要、验收标准、任务路径和实现证据；源码、测试和运行证据始终高于注册表元数据。
- 已否决、归档、历史或需求漂移的路线不能进入可认领列表。

## 非目标

- 不以注册表替代 `AI_CURRENT.md`、正式需求、ADR、源码或测试。
- 不把注册表扩展为聊天归档、产品全文、跨团队分布式锁或自动开发调度器。
- 不在本功能中迁移开放商业、ERP、算力、Sui 等全部业务模块。

## 验收标准

1. `.elon/project-features.json` 由正式 MCP 创建，首条功能绑定本需求的当前内容哈希。
2. `project_feature_workflow list/plan/check_drift` 能返回有界结果，且不返回需求或源码正文。
3. 功能可按状态机认领、记录文档与测试证据，并在需求漂移时失败关闭。
4. `AI_CURRENT.md` 明确说明一龙项目自身已启用注册表，以及首批仅登记少量当前功能的边界。
5. 文档模块化、项目入口和功能工作流回归通过；注册表与需求文档进入同一 Git 提交。

## 后续扩展原则

后续每次只登记经过当前事实核对的一小组功能。优先登记正在开发或明确待验收的 P0/P1 项；已发布能力可在证据齐全时补录，长期愿景保留在路线图或讨论图中，不进入可认领队列。
