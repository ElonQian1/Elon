# 商户 SQLite 一致性备份与离线恢复 V1 需求

## 背景

通用 ERP SQLite 适配器和开放商业商户运行时幂等存储已经具备事务、WAL、重启恢复、锁竞争与损坏拒绝能力，但仍缺少可复用的一致性备份与恢复工具。直接复制主数据库文件会遗漏 WAL 中已提交的数据，也无法证明备份完整、目标未被并发覆盖或恢复内容属于审核过的工件。

## 目标

提供独立的 Node SQLite 运维 SDK，使商户项目可以在数据库继续提供服务时创建一致性快照，验证快照，并在运行时停止后把审核过的快照恢复到一个全新的数据库文件。ERP 主库和开放商业幂等库共用同一底层工具，但继续由各自 schema 和运行时负责业务语义。

## 范围

1. 从现存的磁盘 SQLite 数据库创建在线一致性备份，使用 SQLite backup API 而不是复制主文件。
2. 对备份执行 `PRAGMA quick_check`，读取 `user_version` 与表目录，并支持调用方要求特定版本和表集合。
3. 为已发布备份返回 SHA-256、字节数、版本、表集合和创建时间回执，不在回执中保存源路径或业务正文。
4. 恢复时必须提供预期 SHA-256；只有备份验证通过后才恢复到不存在的新目标文件。
5. 备份与恢复先写入目标目录内的随机临时文件，验证和刷盘完成后再原子发布；并发争抢同一目标时最多一个成功。
6. 拒绝内存数据库、同一路径、符号链接、已有目标、损坏数据库、摘要不符、未来或不符的 schema 版本及缺失必需表。
7. 对通用 ERP 数据库和商户运行时幂等数据库分别完成真实写入、备份、恢复与重开验证。

## 非目标

- 不覆盖或替换正在使用的数据库文件，不自动修改运行时配置。
- 不提供定时调度、远程上传、加密、密钥托管、保留策略或生产灾备编排。
- 不宣称多机高可用、多主复制、跨设备同步或生产恢复演练已经完成。
- 不迁移 `cofficethinking` 生产数据库，也不处理真实支付或外部平台数据。

## 验收标准

1. WAL 模式数据库保持打开并完成写入后，在线备份包含已提交记录且 `quick_check` 为 `ok`。
2. ERP 采购、库存、订单、幂等与审计数据可从备份恢复到新文件，并由 `SqliteErpStore` 正常重开读取。
3. 商户运行时成功幂等结果可从备份恢复到新文件，并在重开后返回 `replayed`，不再次执行动作。
4. 已存在目标、同一路径、符号链接、摘要不符、损坏文件、缺表和版本不符全部失败关闭。
5. 两个并发操作争抢同一目标时恰好一个发布成功，失败方不覆盖结果。
6. 失败路径不留下最终目标或未清理的工具临时文件。
7. API 声明、README、ADR、验收文档和当前能力基线与实现保持一致。
