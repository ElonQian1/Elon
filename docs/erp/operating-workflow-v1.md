# 通用 ERP 端到端运营工作流

本文只描述已经落地的 V1.3 工作流。商业网络、真实平台适配器、生产支付和链上资产仍以各自文档为准。

## 角色与所有权

| 角色 | 可以做什么 | 不能代替谁 |
|---|---|---|
| 蓝图维护者 | 追加蓝图定义、发布不可变版本、评审通用提案、为实例准备升级检查 | 不能替商户采用或回滚版本 |
| 商户项目成员 | 配置本店实例、登记私有扩展、授权脱敏信号、创建初始化 Matter、采用或回滚版本 | 不能直接修改公共蓝图 |
| AI 代理 | 检索固定版本能力、解析需求、编排已有能力、在授权后提交脱敏信号、准备兼容检查 | 不能接受提案、演进蓝图、创建治理 Matter、发布版本或采用升级 |
| Matter Bot | 在项目批准并启动 Matter 后获得 Assignment，在隔离工作区实现和验证 | 不能自动合并或发布 |

## 新商户初始化

1. 维护者从已发布版本新建独立商户项目，或显式选择一个自己有编辑权的现有项目纳入治理，并登记行业、主题、公共模块、插件和私有扩展边界。
2. 商户进入自己的项目，只能修改本实例配置；所有更新携带 `configuration_revision`，并发旧写入会失败。
3. 商户创建初始化 Matter。系统把固定版本的源提交、模块、插件、主题和边界编译为计划，并原子写入 `bootstrap_matter_id`。
4. 重复点击返回同一 Matter，不生成孤立计划。项目有授权在线 Bot 时，计划包含可在人工启动后生成 Assignment 的角色信息。
5. 真实源码实现、测试、合并和发布继续走项目现有流程；蓝图服务不暗中复制仓库或执行部署。

## 现有项目纳入

1. 用户可在 PC ERP 工作台输入已知本机路径或通过系统窗口选择仓库；本机节点先校验目录并登记或复用一龙平台项目，工作台再把该项目作为候选项选中。登记本身不创建 ERP 实例，输入路径不会绕过节点校验。
2. 平台纳入时只接受用户再次明确确认的 `target_project_id`，并核对操作者对蓝图项目和目标项目均有编辑权。
3. 纳入成功后，PC 工作台进入目标商户项目的“开放商业 / ERP 蓝图”视图；刷新或分享地址时通过 `commerce=erp` 保持该视图。维护者也可从实例清单重新进入，不必手工寻找项目。
4. 进入目标项目不等于启动开发。商户仍须单独确认实例配置，再显式创建初始化 Matter；工作台不会把目录登记、实例纳入和 Matter 启动合并成一次静默操作。
5. 系统归档项目、蓝图维护项目自身及已绑定 ERP 实例的项目不能重复纳入。
6. 纳入只增加 ERP 治理关系和 `existing_project` 来源标识，不修改目标项目名称、成员、工作区、代码或部署配置。
7. 初始化 Matter 首先要求输出已有能力与蓝图能力的差异清单，再以最小改动补齐缺口；不得用空白模板覆盖现有项目。
8. 若实例登记失败，平台只清理本次新建的空项目，绝不清理被选择的现有项目。

PC 工作台的就绪度面板只提供可恢复导航：ERP 未验收时定位到商户确认和初始化 Matter 操作区，调用或目录未就绪时进入商户节点工作区，目录就绪后可进入消费者沙盒。导航不会自动创建商户、发布目录、创建 Matter 或执行消费者订单。

## 物化合同、证据与恢复

1. 初始化 Matter 的 `plan.execution_contract` 固定记录源项目与 Git 提交、可选公共运行时包、目标商户项目、实例配置修订、模块、插件和私有扩展边界。
2. Assignment 执行提示会携带合同。完成初始化时应生成 `.yilong/erp-instance.json`，并登记 `erp_instance_materialization` Artifact。
3. Artifact 元数据使用 `yilong.erp.materialization_evidence.v1`，至少包含实例、配置修订、源提交、清单路径、清单 SHA-256 和真实验证结果。
4. 工作台状态从 Matter、Assignment 和 Artifact 真源实时计算；没有额外状态表，因此重放与刷新不会制造第二套事实。
5. Assignment 失败时列出失败任务并沿原任务重试。Matter 已完成但证据缺失时显示“已验收，证据不完整”，不得解释为已发布。
6. 实例配置变更后，旧合同显示漂移。商户可再次确认生成当前修订的新 Matter，旧 Matter 和证据继续保留；旧流程正在执行或等待验收时必须先完成或取消。
7. 清单绑定 `yilong.erp.kernel.v1` 时，代理优先复用该包，只实现目标数据库适配、主题和私有插件；现有项目仍先盘点，不得直接覆盖原领域逻辑。

## 需求处理与公共提案

1. AI 只检索商户固定版本已经发布的能力。维护分支新增但未发布的能力不会被误判为可复用。
2. 强匹配返回 `existing` 或 `composition`；无强匹配时按商户意图进入 `private_extension` 或 `candidate_common`。
3. 私有需求在本项目扩展命名空间实现。通用候选只有在商户授权脱敏摘要后才写入信号。
4. 同一实例对同一 `need_key` 只计一次。达到独立商户阈值后仍由维护者评审。
5. 接受提案与创建 Matter 在同一事务关联。公共内核实现完成后，维护者显式追加蓝图定义并发布新版本。

## 发布、采用与回滚

1. 蓝图定义使用 `definition_revision` 乐观更新，只允许追加，不修改已发布清单。
2. 发布清单必须使用严格 `x.y.z` 版本、当前最新 `previous_version`、已声明模块/能力/扩展点以及可逆回滚约束。
3. 升级准备保存实例修订、升级前配置、目标配置、私有扩展快照和兼容问题。新增必需模块进入目标配置，删除已启用模块或扩展点会阻止升级。
4. 商户完成真实开发、迁移、测试和发布后，在 PC 工作台填写验证摘要与可选 Git 提交并确认采用。
5. 采用和回滚都核对实例修订与配置快照。采用后仍可填写原因回滚，恢复原固定版本、主题、模块和插件；私有扩展始终保持不变。

## 当前非目标

- 不自动从远端 Git 克隆或把本机仓库直接纳入 ERP；PC 工作台只能通过本机节点把已选择目录登记为用户可编辑的平台项目，之后仍须用户显式确认纳入。
- 不实现美团、抖音、京东、淘宝闪购等真实生产适配器或绕过官方授权。
- 公共内核只提供基础采购双分录；不把它解释为完整财务核算、税务、支付结算、自动营销发布或效果回流。
- 不发行代币，不提交 Sui 网络，不把升级活动解释为收入权益或公司股权。
- 不把“商户确认”字段当作密码；身份和项目权限由现有认证体系负责，AI 工具调用还应遵守 Harness 审批。
