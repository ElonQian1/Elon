# 一龙开放商业融合架构

本文定义现有 AI 开发平台、群体 AI、开放商业网络、共享节点和候选 Sui 经济层如何组合为一套系统。详细字段和接口仍由各专题文档负责。

## 架构目标

用户可以在手机或 PC 描述一个经营目标；系统把目标拆成可审计的开发或经营任务，选择合适的 AI、API 和计算节点执行，生成应用、营销内容或经营结果。商户可以把经过授权的能力暴露给消费者 AI 和第三方应用，而不必把全部数据迁移给新的中心化平台。

## 分层结构

```text
消费者 App / 商户 App / 一龙 APK / PC 工作台 / 第三方 AI
                           |
                    意图与应用交互层
         对话、Demo、应用生成、ERP、海报、视频、小游戏
                           |
                      任务协作层
       Matter、Assignment、Agent、审核、Git 工作区、产物
                           |
                    开放商业协议层
     Merchant、Capability、Grant、Invocation、Meter、Audit
                           |
                     资源执行层
     云模型、用户 API Token、PC 节点、闲置算力、外部服务
                           |
                  回执、计量与结算层
       当前链外账本和审计回执 -> 候选 Sui 结算适配器
                           |
                      数据所有权层
      用户数据、商户数据、项目 Git、凭据保险箱、授权记录
```

## 两条核心闭环

### 应用开发闭环

```text
用户需求
  -> 一龙 AI 澄清和预演
  -> 创建 Matter
  -> 分配 Assignment
  -> AI 或节点在 Git 工作区执行
  -> 审核与验证
  -> 构建和发布应用
  -> 成功经验进入项目文档和上下文
```

这条闭环承接“一个 APK 让用户直接开发应用”和“群体成员一起开发应用”。微信群式沟通是交互入口之一，真正可复用的协作事实必须落入项目成员、Matter、Assignment、产物和审核记录。

### 开放商业闭环

```text
商户发布结构化商业能力
  -> 消费者 AI 或第三方 App 发现能力
  -> 用户授权或商户策略校验
  -> 调用库存、预约、营销或交易能力
  -> 记录计量与审计回执
  -> 商户系统返回结果
  -> 可选进入链外或 Sui 结算
```

平台连接的是能力和授权，不拥有消费者与商户之间的全部关系。基础公开信息可以被发现，客户、订单、财务等私有数据只能在明确授权和最小权限下调用。

## 统一领域对象

| 领域对象 | 作用 | 当前落点 |
|---|---|---|
| Identity | 标识用户、商户、Agent、节点和服务账户 | 现有用户、项目成员与节点身份 |
| Project | 承载应用源码、文档、配置和发布历史 | 项目空间与 Git 工作区 |
| Matter | 表达一个需要协作完成的业务或开发目标 | `server/src/group_ai/` |
| Assignment | 把可执行步骤分配给 Agent、节点或外部能力 | `server/src/group_ai/` |
| Capability | 描述商户或服务提供者可被调用的能力 | `server/src/open_commerce_model.rs` |
| Grant | 描述谁可在何种范围和时限内调用能力 | 开放商业 V1 |
| Invocation | 记录一次真实商业能力调用 | 开放商业 V1 |
| Integration | 描述商户授权的数据来源、接入方式、范围和健康状态 | 开放商业接入控制面 |
| Sync Receipt | 记录适配器同步数量、摘要、结果和时间，不保存原始经营值 | 开放商业接入控制面 |
| Usage Receipt | 记录模型、节点、商业能力或任务的可计量事实 | 节点账本、调用审计、链外影子账本 |
| Settlement Intent | 把 Assignment 与真实用量来源绑定，等待人工验收或取消 | `server/src/task_settlement/` |
| Settlement Receipt | 记录验收后不可重复的影子经济判断及双分录 | `server/src/task_settlement/` |
| Settlement Adapter | 把已经确认的回执映射到具体结算网络 | 当前仅实现无网络副作用的 Sui 信封，网络适配器仍是提案 |

## 可融合与不可混合的边界

可以融合：

- AI 应用生成与商户 ERP、营销活动、小游戏和内容生产共用工程执行链路。
- 群体 AI 的 Matter/Assignment 与节点算力调度共用任务事实。
- API Token、云模型和闲置节点共用资源选择、预算和用量回执。
- 开放商业调用与未来结算共用 Invocation 和 Usage Receipt。

不能直接混合：

- API Token 所有权、节点算力贡献、商户数据权利、公司股权和合同收入权不是同一种资产。
- “AI 能生成内容”不代表已具备各平台的发布权限和订单数据接口。
- “多个普通 GPU 的总计算量”不等于“企业级 GPU 集群的同步训练性能”。
- Sui 对象和代币不能成为核心业务数据库的唯一真源；链上层故障时，授权、经营和开发主干仍应可运行。
- 开放协议不等于公开全部数据，也不等于取消身份、隐私、质量审核和争议处理。

## Sui 的候选位置

Sui 适合放在已经产生确定业务事实之后：

1. 将 Project、Task、Capability 或 RevenuePosition 表达为拥有明确所有者的对象。
2. 对同一项目内的大量对象使用动态字段组织状态，避免单个全局账户成为争用点。
3. 对可并行的任务回执和微支付使用对象级并行执行。
4. 使用可编程交易块把验证回执、分配费用和更新状态组合成原子操作。
5. 对共享规则使用共享对象，对用户凭据、商户私有数据和敏感权限仍保留链下控制。

第一步不是发币，而是实现链外 `Usage Receipt -> Settlement Intent -> Settlement Receipt`，证明计量、对账和争议流程成立。随后再接入 Sui 测试网适配器；网络资产、服务 Credit、收入权益和公司融资必须继续分层。

## 多平台接入路径

```text
商户授权或导出
  -> 经审核的平台 / POS 适配器
  -> Integration 接入记录
  -> 有界 Sync Receipt
  -> 商户自有数据存储与 Capability
  -> AI 开发上下文 / Matter / Assignment
```

控制面已实现，但具体平台适配器必须逐项验收。登记一个平台标识只表达准备接入，不代表已获得该平台的官方权限。开发代理读取的上下文只包含能力契约、数据域、授权范围和同步健康度，密钥与原始经营数据不进入代码提示或协作文档。

## 模块依赖方向

```text
产品与行业模板
      -> 群体任务与工程执行
      -> 开放商业领域服务
      -> 资源计量与审计
      -> 可选结算适配器
```

上层可以组合下层能力，下层不得依赖某个具体行业页面、某一种代币或某一家外部平台。这样既能支持当前 APK 开发体验，也能逐步演进到开放商业网络，而不需要重写现有系统。
