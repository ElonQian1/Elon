# 工作室分层构建缓存方案

本文是待实施和验收的目标设计，不代表已经部署。本轮只确定分层、接入顺序和验收标准。
当前可用命令和删除权限仍以 [Rust 缓存平台](../rust-cache-platform.md)、
[网络存储手册](../rust-cache-network-storage.md) 和安装版工具为准。
其他项目的 AI 从 [工作室缓存接入入口](../studio-cache-ai-entry.md) 开始，不复制实现。

## 现状与目标

现有平台支持每台电脑独占的本地根或 UNC 根、项目清单、薄启动器、命名分区锁和受管 GC。
现有 UNC 方案用于转移本机容量压力；不同电脑不能把同一个可写 Cargo/sccache 目录当成共同根。
安装器目前把平台、状态、build 分区和 sccache 目录放在一个 CacheRoot 下；
自动容量选址、本地与远端两级配置、共享对象服务、跨节点容量预约均未实现。
目标实现先把常驻平台、策略、注册表与凭据留在本机，将任务 BuildRoot、
本地对象缓存和远端 ObjectCacheBackend 分开。当前原生 wrapper 会根据自身位置推导根，
不能只改一个环境变量就宣称完成解耦；同一常驻 sccache 也不能随并发任务来回切根/重启。
现有跳过 GC 的入口也会跳过部分空间预检，因此当前还没有不可绕过的统一容量门禁。
后续应将硬性空间接纳与可选 GC 分开，不能把“没运行清理”理解成“无需空间检查”。

目标是：小而有上限的本地热缓存 + 工作室共享对象缓存 + 独立冷归档。
查找顺序与空间选址是两个决策：本地没有对象就查询共享层，即使本地空间充足也可复用；
新构建的临时空间和可写目录则在构建开始前决定，不能等磁盘写满才迁移。

## 数据分层

| 数据 | 默认位置 | 多电脑共享方式 |
|---|---|---|
| 源码、未提交内容、凭据、节点身份、运行数据库 | 本机 | 由 Git/身份/数据库所属流程处理，不当缓存 |
| 活动 Cargo build-dir、增量状态、最终链接和临时文件 | 本机受管分区 | 同机同项目兼容分区可复用；跨机不共写 |
| 编译对象，如 sccache 对象 | 小容量本地 L1 + 共享 L2 | 通过缓存服务的对象键复用 |
| Gradle task outputs | 本地 build cache + 远端 HTTP cache | 使用 Gradle 原生协议，和 Rust 独立命名空间 |
| Cargo/npm/Maven 等下载包 | 本地限额 + 按工具适配的制品代理 | 按包与校验摘要复用，不共享整个用户目录 |
| node_modules、Gradle 可写元数据、工具链安装 | 本机或指定构建节点 | 不做多客户端可写 UNC 公共树 |
| 旧发布包、确认退役的恢复材料 | 冷归档 | 校验清单、保留期和恢复规则独立于缓存 GC |

L2 命中仍要把输出落到构建目录，不能消除链接、解压和临时文件的空间需求。
sccache 也不缓存全部 Rust 工作：所选版本对增量编译和需要系统链接器的 crate 有限制；
开发增量与 sccache 模式应按任务实测选取，不全局关闭增量来追求表面命中率。

## 缓存宿主怎样使用自己的盘

宿主同时有两个角色，必须使用不同目录和权限：

1. **作为开发电脑**：在共享盘所在的实际本地卷建立自己的新受管根；
   通过本地绝对路径使用自己的热缓存和 build 分区，不绕 UNC 访问本机文件。
2. **作为缓存服务器**：缓存服务账户独占 L2 对象存储目录；开发进程通过同一受支持的
   缓存协议访问服务。可用经验证的回环端点或同一 HTTPS 服务名，不能直接写服务的数据文件。
3. 其他电脑的 UNC 溢出目录归对应电脑所有。宿主不因拥有物理磁盘就接管这些目录。

本工作室已允许缓存宿主在空闲时承接其他电脑的编译。实施时按独立构建账户、
精确源码快照和每任务工作区执行，初期最多一个重构建；限制 CPU、内存、磁盘与网络并发，
给本机交互和缓存读取留余量。仅在任务边界停止接单或调整并发，不随意杀掉正在写入的构建。
已知规模是 4–5 台开发电脑，缓存盘为机械硬盘，通过网线连接标称千兆路由器；
宿主网口、所有中间端口、线材实际协商及端到端吞吐尚未验证。
因此首期不默认开放多台电脑在该机械盘上通过 UNC 并发构建。宿主自己的构建目录
也应优先本地 SSD；若只能使用机械盘，最多先试一个构建并测量对缓存读取的影响。

示意布局（占位符，不是已经存在的目录或可直接运行的配置）：

```text
<cache-volume>/studio-cache/
  service-data/objects/            # 只有缓存服务操作
  clients/<host-node-id>/          # 宿主自己的受管可写根
  clients/<other-node-id>/         # 对应电脑的可选 UNC 溢出根
  archives/                       # 冷归档，独立策略
```

当前归属校验主要针对网络路径，不能把另一个客户端的 UNC 根改成本地路径来绕过它。
上线宿主接入前，需验证本地路径和 UNC 别名对应同一物理目录时的归属、锁和拒绝接管行为。
近期做法是只初始化宿主自己的新空目录，不复用任何已有客户端根。

## 两条执行链

**缓存对象查找**：本机 L1 命中 → 返回；未命中 → 查询工作室 L2；仍未命中 → 实际编译。
L2 命中可在 L1 配额内回填，不全量同步共享池。成功输出按权限写回；缓存上传失败不改变
已经完成的构建产物，但必须记录失败，不能伪造远端命中或上传成功。

**构建空间选择**：

1. 识别项目、工具链、domain、用户和节点；核对当前受管根与活动构建。
2. 先复用兼容的已有本地分区，再评估可用空间、缓存配额和其他任务的空间预约。
3. 空间不足时，只通过所属工具清理已批准策略覆盖的闲置缓存；不碰游戏、源码和未知目录。
4. 仍不足时，优先把整个构建任务交给获准的构建节点。源代码状态必须精确绑定，
   未提交修改需显式、完整传输；不能用远端旧 checkout 冒充当前构建。
5. 没有构建节点时，才考虑经过验证的本机独占 UNC 构建分区；保留必要的本地临时余量。
6. 所有位置都不足，明确报告无法接纳本次构建。不能偷偷改回 C 盘或新建无人治理的 target。

远程缓存只提供已有对象，不会把 CPU 编译自动搬到宿主。远程执行是独立能力和授权，
本设计不恢复已经暂停的 PC 自动派发或监督流程。
一次构建固定执行计划与根目录；路径切换仅在无活动写入的任务边界进行。

## 配额与并发

建议试点先给磁盘紧张的客户端 2–5 GiB 本地对象缓存，空间充足后再按热集调大。
这不包含 build-dir、target、下载包和临时目录；必须同时治理它们的总量。
初始系统盘保底可设为 `max(20 GiB, 卷容量的 10%)`，它是待测策略值，不是现有硬编码。

任务接纳条件：

```text
卷可用字节 - 系统保底 - 已预约空间 >= 本任务预计新增峰值 + 安全余量
```

预计峰值由历史同类构建测量；没有数据时先受限试跑，不能填 0。
一个机器级协调器汇总所有项目和 AI 的预约，防止每个代理看到相同余量后都启动大构建。
共享卷也需要统一预约与用户/项目配额，不能让每台 PC 都把共享盘剩余容量算成自己的。
工具预约是协作约束，不能阻止外部应用写盘，仍须监测实际余量并配置存储侧配额。
低水位减小热缓存、停止新大构建；高水位恢复，保留滞回区间避免来回搬迁。

## 共享层的服务与冲突模型

首期复用成熟工具：Rust 评估 sccache 的 disk + S3 兼容后端；
Android/Gradle 使用原生本地 + HTTP build cache。端点可在同一宿主，协议和目录各自独立。
不先开发一个接管所有语言缓存布局的通用文件系统，也不要求把大缓存全部装进 Redis 内存。

对象服务需要：受验证的完整对象发布、原子可见、并发同键写入约定、完整性检查、
容量配额和服务端 GC。客户端不能用共享盘任意覆盖/删除对象来替代这些能力。
键由原生工具根据编译输入生成；再按工作室/信任域/平台/兼容策略做命名空间隔离。
工具链、目标架构、feature、编译参数、依赖和相关环境必须保持正确缓存区分，
不能手工简化键来强行提高命中率。路径归一化只走已验证的工具能力。

多人共用不会保证相同未命中任务只编译一次；首期接受少量重复计算。
只有测出明显浪费后才增加按构建键的有界去重，不用一把全局锁把所有开发串行化。
本地可写分区锁由所属机器持有；公共对象由服务并发处理；GC 由各层所有者执行。

默认共享池只允许可信构建写入，普通开发者读取；需要互相贡献的可信开发节点可进入
单独可写池。测试代码、外部项目和发布缓存按信任域隔离。内容哈希不能替代发布者身份验证。
共享目录标记只是误操作保护，必须有真实 ACL/服务身份；客户端不能读写别人的私有分区。
签名材料、token 和用户配置留本机凭据存储，禁止进入 Git、共享策略文件或缓存对象。

## 网络与降级

大对象受吞吐限制，小文件和目录扫描常受往返延迟、元数据操作、磁盘随机 I/O 与杀毒开销限制。
千兆链路理论上限为 125 MB/s，2.5G 为 312.5 MB/s，10G 为 1250 MB/s；实际有效速率更低。
传 10 GB 的理想纯数据时间分别为 80、32、8 秒，不是构建时间承诺。
若宿主只有一个千兆口，多客户端共同分摊这一个上行；提高客户端网卡不能突破它。
机械盘适合冷归档；频繁访问的对象与服务索引优先放 SSD。先测再决定是否升级链路。
已有机械盘可先承接较冷的 L2 对象，小规模试点后再决定是否增加 SSD 热层；
不能因为带宽没有跑满就断言网络足够，也不能仅升级到 10G 而忽略机械盘随机 I/O。
4–5 台机器的构建拉取与归档上传共享资源：交互/构建读取优先，归档避开高峰并限速，
宿主编译并发初始为 1。客户端 L1 命中可减少热点重复拉取；不启动所有客户端全量同步。

| 现场状态 | 目标行为 |
|---|---|
| L2 不可达，但本地可接纳构建 | 有界超时后本地构建；记录共享不可用，不无限等待 |
| 本地不足，L2 有对象 | 仍计算输出/链接空间；不能因命中就跳过空间检查 |
| 本地不足，构建节点可用且获准 | 精确绑定源码状态后远程构建并验证结果 |
| 本地不足且无可用执行位置 | 拒绝启动大构建，报告缺口与已有数据位置 |
| 正在写入的 UNC 分区断线 | 停止该次构建并保留证据；不能中途换根继续写 |
| L2 满或上传失败 | 限额内本地继续，远端缓存写入降级；不删除别人缓存 |
| 配置/身份/协议不兼容 | 保留现场并报错，不自动接管目录或放宽认证 |

网络超时、读失败和只读远端下 L1 回填必须现场验证，不能仅按环境变量名称推断工作正常。
sccache 0.16.0 已提供多级配置文档，但有公开的“只读 S3 导致本地未写入”问题报告；
部署版本需要锁定，并通过读写组合测试后再扩展。现有安装器会重写生成配置，
应扩展安装器后统一安装，不能手改生成文件后宣称长期生效。

## 文档、配置与 AI 接入

三层信息各有一个真源：

1. **工作室策略与适配器版本**：受版本控制的权威文档和平台发布包；
   本文描述目标，运行手册描述已实现边界。节点保存校验后的本地只读副本，断网仍可诊断。
2. **机器事实与凭据**：本地配置记录真实卷、服务端点、角色、限额、受信节点和凭据引用。
   不提交机器路径、账号、密码或机器身份。不能用主机名等于某字符串推断目录归属。
3. **项目能力**：Git 提交 project_id、domain、薄 wrapper 与 AI 入口链接；
   不把工作室共享路径写进每个仓库，也不复制路由、锁或清理实现。

第一阶段继续用现有用户环境、安装 launcher 和根下 policy 配置作为生效来源。
额外机器清单只记录索引与检查结果，不能虚构一个现有工具并不读取的 localconfig 真源；
需要新配置 schema 时由安装器、解析器和迁移一起实现，再统一生效。

每个项目的 AGENTS/对应代理入口只需引用统一接入文档，并要求大构建前运行已安装平台的 doctor。
全局 Skill 是辅助分发；不假设所有 AI 产品会自动加载 Codex Skill。
新项目接入由现有 adopt-project 生成受审查的 manifest 和薄 wrapper；非 Rust 项目使用各自
原生缓存适配器，未实现时明确报告，不伪装成 Rust 受管项目。

运行时应输出策略版本、节点角色、实际根、选择原因、配额/预约、锁等待、
本地/远端命中率、网络字节和降级原因。中央汇总使用脱敏指标，事实来自探测结果，
不能靠 AI 从上次聊天推测磁盘状态。共享文档的存在不会自动配置任何电脑。

## 上线顺序与验收

1. 完成本方案与统一 AI 入口；明确 implemented/proposed，建立主机角色和本地配置清单。
2. 在宿主本机确认共享目录对应的物理卷、SSD/HDD、配额和空闲容量；
   仅安装宿主自己的新受管根，用 doctor 和小型真实编译验证。此步尚未在宿主执行。
3. 接入一台客户端，先运行各自独占根，验证不会跨机共写、不会误清理对方。
4. 部署一套共享对象服务，完成本地命中、第二台远端命中、再次本地命中的链路。
5. 再实现容量预算、跨项目预约和明确的降级；最后按需要增加远程执行适配器。
6. 按项目逐步扩展 Gradle/包代理，再推广全部电脑；每一步均可回到原已知配置。

性能对照使用同一源码与工具链，至少记录冷构建、热构建、源码微改、第二台首建、
单机和预期峰值并发、共享服务断线及配额耗尽。比较总耗时、P95 延迟、缓存命中、
传输字节、CPU/磁盘负载和本地峰值空间。基准写入独立临时命名空间，不清空正式缓存。
必须证明输出正确、隔离有效、网络失败可解释、没有泄漏凭据，才算接入完成。
针对当前工作室先确认每一跳实际为 1 Gbps 全双工，再分别测端到端网络吞吐、
独立临时命名空间的大文件读写、小文件访问，以及 1 台/4–5 台并发构建。
单个网卡的 LinkSpeed 不是端到端证明；若发现百兆端口或协商，先修复链路再评估升级。
注意当前 `install` 即使不传 `-Apply` 也会安装文件和 launcher，不能作为只读预演；
`adopt-project` 的默认预演语义不能类推到安装命令。
