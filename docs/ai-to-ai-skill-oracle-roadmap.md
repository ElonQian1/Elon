# 内部 AI-to-AI Skill 与预言家 AI 路线

最后更新：2026-07-19

## 1. 产品判断

一龙的核心不是让用户一次性提交完整需求，而是让用户和一龙 AI 持续讨论，把模糊想法逐步变成清晰、可验收、可交付的产品。

在这个定位下：

- 用户不需要理解或手动组合 Skill。
- 一龙会话主 AI 是长期对话 owner，负责理解目标、维护上下文和向用户解释决策。
- 预言家 AI（Demo Oracle）负责在正式开发前低成本生成可讨论 demo。
- 总调度 AI 根据确认后的目标生成 Matter，并调用 Skill Router 选择能力组合。
- Skill Agent / Worker Bot 在隔离工作区完成正式开发。
- Reviewer / Verifier 独立验收，人类在关键节点决定继续、打回、发布或放弃。
- Skill 是平台内部的官方工程能力，不面向用户售卖，不接受第三方上架，不建设 Skill 市场。

## 2. 目标链路

```text
用户讨论
  -> 一龙会话主 AI 总结需求与不确定点
  -> 需求成熟度判断
       -> 明确小改动：直接进入 Matter
       -> 方向不清：继续讨论
       -> 适合预演：调用预言家 AI
  -> 生成低成本 demo
  -> 用户确认、调整或放弃
  -> Skill Router 选择官方 Skill 组合
  -> 生成 Matter、预算、风险和验收标准
  -> Skill Agent / Worker Bot 执行
  -> Reviewer / Verifier 验收
  -> 构建、发布、分发
  -> Context / Taste / Skill 质量数据沉淀
```

## 3. 现有能力与缺口

当前已经具备：

- 一龙 AI 多轮会话和项目上下文。
- `intent_router` 的多路线辅助分流。
- Codex 轻量意图确认作为可选保护层，用于未显式选定路线时避免非执行类项目问答误进入构建、发布或代码修改。
- Group AI Coordinator、Matter 计划、Bot 选择、节点授权和执行记录。
- Context compiler、repo map、符号索引、task pack、验证和修复线索。
- 项目频道、任务、artifact、审批、计费和发布链路。

当前还不具备完整预言家 AI：

- 没有独立的 `DemoPreview` 状态和需求成熟度协议。
- 没有专用低成本模型、token 预算和超时策略。
- 没有 demo artifact 类型、临时存储和生命周期。
- 没有“demo 确认后才生成正式 Matter”的状态转换。
- 没有专门用于静态原型的受限工具集合。

当前也不具备完整的内部 Skill 基础设施：

- 没有统一 Skill manifest、版本、依赖和权限模型。
- 没有平台级 Skill Registry 和语义检索。
- 没有按需求、兼容性、成本、风险和历史质量综合评分的 Skill Router。
- 没有统一的 Skill 安装、运行、审计、质量评价和升级机制。

因此，现有一龙 AI 只有预言家能力的基础组成部分，不能视为预言家 AI 已经完成。

## 4. 预言家 AI MVP

### 4.1 触发条件

满足任一条件时建议生成 demo：

- 用户描述的是新产品，而不是明确的小修改。
- 存在两个以上合理产品方向。
- 需要新增多个页面或核心业务流程。
- 正式开发预计成本明显高于 demo 成本。
- 用户明确说“先看看效果”“先出原型”。

以下情况默认跳过：

- 文案、颜色、按钮、字段等明确小改动。
- 明确 bug 修复。
- 已有确认过的产品规格和验收标准。
- 紧急恢复、部署或安全修复。

### 4.2 MVP 产物

第一版只支持：

- 产品定位和目标用户摘要。
- 关键用户流程。
- 3 至 5 个页面/状态。
- 使用假数据的静态 HTML 或现有 React 组件 demo。
- 截图或可点击预览。
- 未实现能力、风险和待确认问题。
- 后续建议 Skill 列表。

不支持：

- 真实支付。
- 生产数据库写入。
- 生产账号、密钥和隐私数据。
- 正式 Git 合并和发布。
- 把 demo 当成正式功能交付。

### 4.3 成功标准

- demo 成本显著低于正式开发。
- 用户能在一次或少量讨论内确认或否定方向。
- demo 的页面、流程和假数据都有明确状态标记。
- 用户确认后可稳定转换为 Matter 和验收标准。
- 用户打回原因可进入项目 Taste，减少后续重复偏差。

## 5. Skill MVP

长期只建设和维护内部官方 Skill，不开放市场，也不引入第三方创作者、Skill 交易或 Skill 订阅。

每个 Skill 至少包含：

```text
skill.json
SKILL.md
inputs.schema.json
permissions.json
tests/
examples/
```

`skill.json` 至少描述：

- ID、版本、平台维护者和适用项目类型。
- intents、capabilities、输入、输出。
- 前置条件、权限、风险和成本等级。
- 可组合 Skill、冲突领域和兼容版本。
- 验收方式和历史质量指标。

第一批官方 Skill 建议覆盖：

1. 产品 demo/页面原型。
2. Android 或 Web 项目初始化。
3. 设计规范和 UI 实现。
4. 后端/API/数据模型实现。
5. 测试、审查和发布检查。

Skill Router 的结果必须写入 Matter，并包含选择理由、未选择候选、成本和风险。Skill 不具备购买或售卖能力，也不允许未经审批扩大权限。

## 6. 分阶段计划

### P0：文档和契约

- 固定会话主 AI、预言家 AI、总调度 AI、Skill Router、Skill Agent 的职责边界。
- 定义需求成熟度、demo artifact、Skill manifest 和 Matter 关联字段。
- 规定预算、权限、临时文件和用户确认门禁。

### P1：预言家 AI 试运行

- 在项目讨论中增加“继续讨论 / 生成 demo / 直接开发”决策。
- 使用低成本模型生成静态 demo。
- demo 保存为临时 artifact，并能在 PC/APK 中预览。
- 用户确认后生成正式 Matter；打回后保留反馈，不自动进入开发。

### P2：官方 Skill Router

- 建立官方 Skill Registry。
- 从需求摘要和项目 Context Pack 检索候选 Skill。
- 生成 Skill 组合、顺序、预算、权限和冲突说明。
- 先由人确认，再派发给现有 Group AI Bot。

### P3：执行和质量学习

- 记录每次 Skill 调用的成功率、构建通过率、修复次数、token、耗时和用户采纳。
- 将 demo 打回、Matter 验收和失败原因用于排序，但不能自动绕过安全规则。
- 支持版本升级、兼容性检查和回滚。

### P4：内部 Skill 治理

- 官方 Skill 由平台团队维护，进入 Registry 前必须经过沙箱测试、安全扫描、权限审计和人工审核。
- 支持内部版本升级、依赖和兼容性检查、质量评分与回滚。
- Skill 的模型和节点消耗只作为平台运行成本记录，不形成 Skill 商品、售价或作者收益。
- 项目中沉淀的私有经验默认留在项目内；只有平台团队明确接管并完成脱敏和审核后，才能转成内部官方 Skill。

### P5：应用和模板分发

- Skill 生成的 APK、项目模板和插件可以进入分发仓库。
- 支持版本、更新、评价和二次创作。
- 分发不改变项目所有权、隐私和 Git 可追溯原则。
- 分发对象是应用、模板和插件，不包含 Skill 上架、Skill 交易或 Skill 订阅。

## 7. 当前建议

现在适合植入预言家 AI MVP 和内部官方 Skill Router；Skill 商店不属于当前或长期产品目标。

原因：

- 项目已经具备会话、Matter、Bot、项目上下文、artifact、任务状态和 PC 节点执行基础。
- 正式开发链路成本较高，demo 预演能够直接降低做偏和返工风险。
- 当前缺口可以通过受限旁路逐步补齐，不需要重写现有一龙会话主线。
- Skill 保持为内部工程能力，可以减少商业化、供应链审核和第三方权限带来的额外复杂度，让团队集中验证用户真正需要的应用生产闭环。

第一项实施任务应是“需求成熟度 + demo artifact 契约”，不包含任何 Skill 市场、交易或创作者入驻工作。
