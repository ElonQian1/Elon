# Windows 节点升级兼容与事故处置

最后更新：2026-07-15

本文是 Windows EXE 节点升级时按需读取的兼容性门禁。数据根的目录合同见 `docs/pc-node-data-root.md`，发布命令和收尾步骤只引用 Git/发布手册，不在这里复制。

## 用户能听懂的一句话

“AI 临时工作区”不是用户的项目，也不会搬走或删除项目。它只存放 AI 执行任务时产生的临时副本、编译缓存和中间文件，目的是避免这些大文件悄悄挤满 C 盘。客户端应自动管理，普通用户不需要选目录或手动迁移。

## 升级不变量

每次节点升级必须同时满足：

1. 保留 `install_id`、节点凭证、登录状态、本地授权、任务 journal 和项目绑定。
2. 新增必填配置时，同一个版本必须提供幂等自动迁移或兼容宽限路径，不能先加硬门禁再要求用户补配置。
3. 已验证可运行的外部项目继续使用原路径；托管数据目录不得认领、移动或清理项目目录。
4. 明确只读任务不创建 worktree、不申请构建缓存、不被构建容量线阻断。
5. 配置迁移必须“先校验、再持久化、最后发布内存状态”；失败保留旧值和旧目录。
6. 节点对服务器报告的“可运行”必须按任务模式拆分，至少区分只读、项目写入和构建。

## 自动迁移合同

当旧版 `node.json` 没有新字段时：

1. 首次项目写任务以已绑定项目路径为位置提示，优先选择其同盘、同级的 `ElonNodeData`。
2. 若名称被非本节点数据占用，使用带安装实例短标识的稳定备用名称，不覆盖任何文件。
3. 拒绝磁盘根、相互嵌套、符号链接、junction、重解析点和其他节点 marker。
4. 创建 marker 和托管子目录成功后，原子写入 `node.json`；重复启动得到同一结果。
5. 外部项目原地使用；cache/temp 从空目录重建；旧 Git 工作区和 storage 在完成 Git 校验前保持只读回滚源。
6. 自动迁移无法安全完成时，错误必须说明“原项目未移动或删除”、失败原因和唯一下一步，不能只显示“项目空间不足”。

## 发布门禁

节点更新进入全量发布前至少验证：

- 最近三个已发布版本的 `node.json` fixture，包括缺字段、空字段、旧 workspace/storage、自定义路径和损坏显式配置。
- 空盘、低空间、只有 C 盘、项目在 D/E 盘、目录被占用、junction、脏 worktree、未 push 提交和多项目绑定。
- 更新中断、原子写失败、EXE 重启和重复迁移；任何一次失败都不能丢失身份或覆盖项目。
- 只读诊断、普通写任务、实际构建三种任务分别验证就绪状态和容量门禁。
- 节点握手包含可定位构建的版本标识以及数据根就绪状态；服务器能在派单前识别不兼容节点。

发布采用小批量灰度并保留服务端停止派单/停止升级开关。出现身份丢失、项目绑定丢失、自动迁移失败或升级后首任务失败率异常时立即停止扩量；按 Git/发布手册执行前向修复或回滚。

## 事故处置

1. 冻结继续扩量，保留线上证据和受影响版本标识。
2. 分开统计“明确报错次数”和“满足故障条件但尚未发起任务的潜在节点”，不能用前者否定用户反馈。
3. 优先发布零手工前向修复；无法在可接受时间内完成时才回滚客户端。
4. PC 页面和任务错误使用上面的通俗解释，明确项目安全，并给出自动恢复进度。
5. 修复后先验证自有节点，再按小批量扩大；观察升级后第一次只读、写入和构建任务。
6. 复盘结论必须落到代码迁移器、fixture、协议能力、监控和发布门禁；文档只承担路由和长期记忆。
