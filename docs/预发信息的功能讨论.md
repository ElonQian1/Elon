对，**Codex CLI 也支持这两类能力**，只是表现形式不像桌面版那么“图形化”。

你说的可以理解成两件事：

## 1. “下一条信息预发”——CLI 支持

在 Codex CLI 里，**当 Codex 当前还在运行时，你可以提前输入下一条信息，然后按 `Tab` 排队到下一轮执行**。官方文档明确写了：Codex 正在运行时，按 `Tab` 可以把 follow-up text、slash command 或 `!` shell command 排到下一轮。排队内容可以是普通 prompt、`/review` 这类 slash command，或者 `!ls` 这种本地 shell 命令。([OpenAI开发者][1])

区别是：

```text
Codex 正在运行中：

按 Enter  = 把这条新指令插入当前正在运行的 turn
按 Tab    = 把这条新指令排队到下一轮 turn
```

官方也说明了：**按 `Enter` 是往当前 turn 注入新指令；按 `Tab` 是排队到下一 turn**。([OpenAI开发者][1])

所以你可以这样用：

```text
下一轮先不要继续改代码，先总结目前 diff、风险点、还没验证的地方。
```

然后按：

```text
Tab
```

这条就会变成“下一条预发消息”。

也可以排队 slash command：

```text
/review Focus on edge cases and security issues
```

然后按 `Tab`，等当前任务结束后再执行 review。

---

## 2. “引导信息”——CLI 也支持，而且方式更多

Codex CLI 的“引导信息”主要有几种层级。

### A. 临时引导：直接排队下一条 prompt

比如当前它正在改代码，你提前输入：

```text
下一轮请先停止实现，改成：
1. 汇总已修改文件
2. 说明为什么这样改
3. 列出还需要跑的测试
4. 等我确认后再继续
```

按 `Tab`，这就是最简单的“下一步引导”。

---

### B. 计划模式：`/plan`

CLI 支持 `/plan`。官方说明里 `/plan` 的作用是切换到 plan mode，并且可以带 inline prompt，比如：

```text
/plan Propose a migration plan for this service
```

它会让 Codex 先做执行计划，而不是直接开始实现。([OpenAI开发者][2])

你可以这样用：

```text
/plan 先分析这个 Rust 项目的模块结构，给我一个三阶段重构计划。不要改代码。
```

这非常适合你想“先引导它思考，再让它开发”的场景。

---

### C. 持久目标：`/goal`

桌面版里有 goal / progress 这种感觉，CLI 也有 `/goal`。官方文档说 `/goal <objective>` 可以给当前 thread 设置一个持续目标，`/goal` 查看当前目标，`/goal pause`、`/goal resume`、`/goal clear` 可以暂停、恢复或清除。([OpenAI开发者][2])

例如：

```text
/goal 完成本项目的 tokio 异步任务重构，要求每个阶段都先跑 cargo test，失败时先修测试，不要引入新的外部依赖。
```

如果你的 CLI 里没有 `/goal`，官方说可以在配置里开启：

```toml
# ~/.codex/config.toml

[features]
goals = true
```

也可以运行：

```bash
codex features enable goals
```

官方的 goal 用例文档也说，`/goal` 适合长期任务、迁移、大重构、实验等，需要 Codex 持续朝一个可验证的目标推进。([OpenAI开发者][3])

---

### D. 项目级引导：`AGENTS.md`

这个很重要。CLI 会在开始工作前读取 `AGENTS.md` / `AGENTS.override.md`，作为全局或项目级的指导信息。官方文档说，Codex 会在工作前读取这些文件，通过全局 guidance 和项目特定 override，让每个任务都有一致的预期。([OpenAI开发者][4])

你可以放一个全局规则：

```markdown
# ~/.codex/AGENTS.md

## 我的默认开发习惯

- 和我沟通时使用中文。
- 写 Rust 代码时必须带中文注释。
- 每个 Rust 文件开头必须写文件名注释。
- 修改代码前先说明计划。
- 修改后必须给出验证命令。
- 不要自动引入新依赖，除非先说明理由。
```

也可以在项目根目录放：

```markdown
# AGENTS.md

## 本项目规则

- 本项目使用 Rust stable。
- 所有修改必须通过 cargo fmt。
- 修改核心逻辑后必须运行 cargo test。
- 不要改动 public API，除非用户明确要求。
- 新增文件必须遵守现有模块命名风格。
```

如果你想快速创建，CLI 里也有 `/init`，官方说明 `/init` 可以在当前目录生成 `AGENTS.md` scaffold，用来捕获当前仓库或子目录的持久指令。([OpenAI开发者][2])

---

### E. 可复用引导：Skills

如果你有固定工作流，比如“Rust 底层项目审查”“异步代码重构”“FFI 安全检查”“性能优化 checklist”，可以做成 Codex Skill。官方文档说 Skills 可用于给 Codex 增加任务特定能力，CLI、IDE extension、Codex app 都支持；CLI/IDE 中可以用 `/skills` 或输入 `$` 显式调用 skill，也可以让 Codex 根据 skill 描述隐式触发。([OpenAI开发者][5])

例如你以后可以做一个：

```text
$rust-review
```

里面固定要求：

```markdown
- 检查 unsafe 使用
- 检查 Send / Sync 边界
- 检查 Tokio runtime 使用
- 检查错误处理
- 检查是否有阻塞 IO
- 检查是否缺少 cargo test / clippy
```

这比每次手打 prompt 稳定很多。

---

## 我建议你的实际用法

你可以把 Codex CLI 当成三层控制：

```text
临时控制：当前输入 / Tab 预发下一条
中期控制：/plan、/goal、/review、/side、/fork
长期控制：~/.codex/AGENTS.md、项目 AGENTS.md、Skills
```

一个比较好用的组合是：

```text
第一步：
/plan 先分析这个 Rust 项目的异步任务结构，给我重构计划，不要改代码。

第二步：
/goal 按计划完成重构。每完成一个阶段都运行 cargo fmt 和 cargo test，失败时先修复，不要引入新依赖。

第三步：
Codex 运行中提前输入并按 Tab：
下一轮先总结当前 diff、测试结果、还有哪些风险点，然后等我确认。
```

结论：**是的，Codex CLI 支持类似桌面版的“下一条信息预发”和“引导信息”。**
对应关系大概是：

| 桌面版感觉       | CLI 里的对应能力                         |
| ----------- | ---------------------------------- |
| 下一条消息预发     | Codex 运行时输入内容，按 `Tab` 排队到下一 turn   |
| 当前任务中追加提醒   | Codex 运行时输入内容，按 `Enter` 注入当前 turn  |
| 先规划再开发      | `/plan`                            |
| 长期目标 / 持续推进 | `/goal`                            |
| 项目级引导       | `AGENTS.md`                        |
| 个人固定偏好      | `~/.codex/AGENTS.md`               |
| 可复用工作流      | Skills / `$skill-name` / `/skills` |
| 审查当前改动      | `/review`                          |
| 临时旁路问问题     | `/side`                            |
| 分叉探索另一种方案   | `/fork`                            |
