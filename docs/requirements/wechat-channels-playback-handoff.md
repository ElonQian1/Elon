# 视频号播放与微信跳转

## 产品目标

Win 与 APK 保留两个独立入口：**在一龙播放**、**在微信打开**。扫码与复制链接是
恢复方式，不替代这两个目标的验收。当前能力和真实研究证据见
[研究记录](../reports/wechat-channels-handoff-20260928.md)。

第一阶段聊天卡片显示封面和作者，默认从群聊直接请求微信跳转，不先打开 WebView。
APK 使用已确认可用的协议；Win 提供明确不夸大结果的兼容入口。
“查看原网页”单独保留，未来有效播放数据接入该阅读/播放路径，不影响直接跳转。
直接播放和 Windows 精确定位视频仍在研究中，不能标记完成。

## 前端已确认的合同

1. 短链接解析到官方预览页；固定同源 `get_feed_info` 返回内容与临时 `sceneInfo`。
2. 官方播放器读取 `h264VideoInfo.videoUrl`、`h265VideoInfo.videoUrl`，兼容旧 `videoUrl`。
   官方实现有 HEVC 失败后切 H.264 的逻辑。**存在播放器代码不代表本条视频已授权返回流。**
3. `no_redirect` 控制微信环境下的前端自动跳转；`no_autoplay` 控制自动播放。
   它们不会生成媒体地址、身份或原生桥，也不是服务端播放许可。
4. `openFinderFeed` 外部 scheme 与 `WeixinJSBridge.openFinderView` 是两种调用合同。
   前者由操作系统分发，后者必须由真正的微信容器执行；不能互相冒充。

## 模块分工

| 模块 | 职责 | 不承担 |
|---|---|---|
| Channels Resolver | 精确来源校验、固定公共接口请求、短链接身份、封面缓存、临时场景参数 | 任意请求重放、导出 Cookie |
| Playback Adapter | 判断当前响应是否有有效媒体；控制官方播放器；投影播放状态 | 用封面假装视频、隐藏拒绝提示 |
| Handoff Adapter | Android 固定包 Intent；Windows 已验证的协议；生成新鲜参数 | 把进程启动当作视频已打开 |
| Chat Card / Reader UI | 卡片直接跳转；原网页独立入口；保留群聊返回位置 | 用一个成功布尔值混合两条能力 |

聊天卡片通过服务端固定公共接口取得新鲜场景，两个原生平台独立复核后调度系统。
已有 `wechat_channels_handoff.js` 用于阅读器页面同源跳转，不是聊天卡片的前置条件。
播放适配器以后独立扩展，不改变普通站点 UA 或放开全部自定义 scheme。
静态抓包材料留本机；源码哈希、字段合同和验证结果入文档，避免每次从头研究。

## 应用内播放路线

**优先复用官网 HTML video 播放器。** 如果当前合法页面会话能拿到视频字段，让其在
现有 WebView 中播放，先不另造播放器、不搬运身份。需要原生控制时只增加播放、暂停、
进度、音量和全屏桥接；离开阅读页暂停并释放，禁止双播放器同时出声。

只有拿到真实可播放媒体后，再比较原生播放器的必要性。若媒体依赖 Cookie、Referer、
短期签名或平台限定的授权，就在原会话中处理；不把临时地址公开分享或长期缓存。
H.264 优先兼容，HEVC 支持按实际解码能力选择；403/过期最多刷新一次当前授权数据，
失败保留封面和“在微信打开”，不能无限刷新。

当前样本 `get_feed_info` 在四种 UA 下都未返回媒体字段。下一步需取得一个**在普通
授权 WebView 内真实可播放的样本或对方可用的测试身份流程**，比较返回字段与请求来源，
而不是猜测签名或伪造原生桥。如果服务端明确只给微信容器播放数据，要对方开放授权合同；
没有 SDK 不妨碍研究，但前端代码本身不能替代服务端许可。

## 微信跳转路线

- Android：每次点击获取新鲜 `sceneInfo`，使用官方观察到的 `openFinderFeed` scheme，
  仅发给 `com.tencent.mm`；页面自发调用须主框架、可信来源和用户确认。有效期失效则
  刷新一次，不保存临时 export ID。返回一龙时保留当前阅读页和群聊滚动位置。
- Windows：当前协议实测只唤起微信主窗口，未精确进入视频，状态保持未验证。
  后续只实现官方前端/实际客户端中观察到、能验证对应视频的外部入口；微信内部
  `openUrlWithExtraWebview` 不等于 Windows 已注册的外部协议。现阶段提示“已请求打开”，
  提供稳定短链接复制和官方二维码；不自动往用户联系人发送链接。
- 两端都区分未安装、链接失效、用户取消、系统已接受、目标视频已确认。操作系统仅接受
  Intent/ShellExecute 时不能谎报“播放成功”；没有官方回调时保留这个观测边界。

## 状态与缓存

播放：`unknown / checking / available / playing / paused / restricted / failed`。
跳转：`idle / resolving / requesting / requested / confirmed / failed`。
网络超时是 `failed`，没有返回媒体字段是当前响应的 `unknown`，不是永久不支持；
明确平台限制才是 `restricted`。

缓存稳定短链接、标题、封面、源码版本与已测能力；临时跳转参数只保存在当前请求内。
每次显示封面无需重新请求；用户播放/跳转才校验时效。协议变更只影响对应适配器，不清
登录态、不阻塞群聊，不自动切换到未测试协议。

## 验收门槛

| 目标 | 必须确认 |
|---|---|
| 一龙内播放 | 同一视频真实首帧、持续时间、可听音频、暂停/继续、拖动进度、返回停止 |
| APK 微信打开 | 新 APK 卡片进入同一视频，不创建阅读器；返回原群聊；过期/未安装处理 |
| Win 微信打开 | 当前安装版本进入同一视频，而不是仅微信主窗口 |
| 迭代兼容 | 接口无媒体、HTTP 200 业务拒绝、过期、导航切换、连续点击均不误报成功 |

两条路线分别登记结果；在其中一条尚未打通时，不能报告“双端两种方式已完成”。
