# 游戏收益证明与奖励预算 V1

外部执行器可通过[备付来源 API](esk-game-funding-source.md)按编号读取已预留预算及签名结算，或分页扫描待备付预算；查询本身不授权付款。

本模块在主项目记录已对账收益、奖励预留和链上备付证据。独立于 ESK Paper、购买登记、量化 QSHARE、客户本金及游戏会话。当前仅允许测试网策略；没有发行 ESK、交易、提现或生产签名私钥。

## 处理顺序

1. 对账适配器出具签名 `Settlement`：原主用户 ID、经核验的受益钱包及绑定证据摘要、逐用户连续序列、上一份报告摘要、结算时刻、累计净利润及对账材料摘要。净利润须扣除成本、弥补前期亏损、留足已承诺准备金；主项目不接受玩家自报利润。
2. 正式管理员会话录入报告。公钥固定在运营配置中，签名覆盖用途及全部字段。历史相同报告可重放；乱序、缺页、改钱包、改金额及同序号不同报告被拒绝。
3. 管理员创建 `BudgetIntent`，固定受益人、创作者、许可、六种品质面额/数量及余款可直接领取时间。总额必须等于票券合计，并不超过最新累计净利润扣除历史已预留额。预留在 SQLite 同一事务中完成，两个写入者不能超分。
4. 外部金库执行器才可以根据已预留意图构造 Sui 注资交易。此仓库接口不持有金库密钥、不自动广播。交易发送前应持久化实际交易摘要；未知状态保留原意图，不重建第二笔注资。
5. 独立链观察器核验固定网络、包/Registry/完整币种类型、Budget BCS 的全部意图字段、实际初始余额和最终 checkpoint 后，以另一把固定公钥对应的密钥签 `FundingEvidence`。主项目核对意图摘要、金额、受益人及对象唯一性后记为 `funding_attested`。
6. 游戏签发者仍必须读取当前链上预算并由 Move 合约扣减实际余额。主项目历史备付证明不是当前可掉落余额、当前宝物持有人或付款授权；所有响应的 `offchain_payment_authorized` 均为 false。

`direct_claim_after_ms` 必须由明确的产品条款决定，没有生产默认期限。当前没有释放未知预留或管理员收回已分配预算的接口；纠错需要后续有证据的独立状态转换，不能删行或减计数。

## 金额与信任边界

全部金额为十进制字符串，单位是策略指定的**同一种链上币种最小单位**，限制在非负 i64 范围；累计净利润可以为负。禁止浮点数、科学记数法和隐式汇率。若量化以 USDT 结算而奖励用 ESK，必须先有经审批且已执行的兑换/库存划拨与对账，才能出具 ESK 单位的奖励报告，不能将“2000 U”直接写成“2000 ESK”。

可再分配额度：`max(累计净利润 - 历史奖励预留, 0)`。负收益不冲销已发宝物；之后的盈利必须先追回累计亏损和历史分配水平，才重新增加可分配额。资金尚未注入链上时只产生预留记录，不能当作有价掉落额度。

对账签名证明是指定对账方的陈述，不能单独证明交易所真实成交或盈利；链观察签名也不是主项目自行验证委员会签名的轻客户端。必须将对账材料、收益归属、兑换与实际资金证明连成审计链。签名方失实或密钥被盗仍是信任风险，不应在界面表述为数学保证收益。

游戏“存入价值 10 USDT 的 ESK、按 10 USDT 金额保障退出”是独立的本金负债与准备金产品。这里没有实现或启用本金担保，ESK 本身仍不是固定 USDT 锚定币。不能从奖励预算挪用资金填补本金或交易损失。

## 策略与接口

`ELON_GAME_REWARDS_CONFIG` 指向至多 16 KiB 的运营 JSON，缺省关闭。字段对应 `server/src/esk_platform/game_rewards/policy.rs::PolicyInput`：版本、主发行者、testnet、完整 genesis、链标识、奖励包、Registry、完整 payout 币种类型与精度，以及两把不同的 Ed25519 公钥。主项目只保存公钥。首次写入固定策略；改变部署或密钥不能直接换配置重解释已有账本。

| 接口 | 权限/结果 |
| --- | --- |
| `POST /api/admin/game-rewards/v1/settlements` | 正式管理员原主会话 + 对账方签名；录入连续报告 |
| `POST /api/admin/game-rewards/v1/budgets/prepare` | 正式管理员原主会话；原子预留 |
| `POST /api/admin/game-rewards/v1/budgets/confirm-funding` | 正式管理员原主会话 + 独立观察器签名；记录历史备付 |
| `GET /api/me/game-rewards/v1/account` | 仅原主账号自己的额度和最近 100 个意图；汇总覆盖全部记录 |

仅原生 Rust TLS 路由提供传输权限；伪造转发头不能授权。静态 owner/admin token、虚拟 local-owner、Paper 身份、其他账号 token 均不能替代真实会话。数据库事务开始和结束都会检查会话状态；撤销、到期和数据库错误均拒绝，不降级放行。

V293 是追加式独立迁移，包含报告、意图、备付和固定策略。禁止 UPDATE/DELETE/INSERT OR REPLACE 覆盖历史。备份按主项目 SQLite/WAL 流程执行，不能只复制正在写入的数据库主文件。

## 规范签名

使用 Ed25519 strict 验签。签名对象为 UTF-8：`ESK_GAME_REWARDS_V1\n` + 用途（`settlement` 或 `funding`）+ `\n` + 按 Rust 结构声明顺序序列化的紧凑 JSON，无尾换行。字段顺序、全部数字字符串及 bool 类型必须保留；未知字段拒绝。摘要为该完整字节序列的 SHA-256 小写十六进制。`intent_digest` 用同一规则的用途 `intent`；策略摘要用途为 `policy`。签名 envelope 的 `signature_hex` 为 64 字节签名的小写十六进制。

当前对账/链观察签名适配器和游戏 BFF 预算接口仍需接入，不提供“提交任意 JSON 后签名”的生产工具。核心测试直接复用生产源码，HTTP 测试使用真实 Store 与 TLS 路由；合成签名不会作为生产信源。
