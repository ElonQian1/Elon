# 咖啡商户真实服务器订单闭环验收

## 验收目标

验证 `cofficethinking` 商户运行时不只存在契约和测试替身，而能在真实服务器、真实 PostgreSQL 和原 ERP 订单模型中完成一笔消费者风格的签名订单。

本验收对应的是商户侧子链：

```text
消费者风格签名信封
  -> 咖啡商户真实运行时
  -> 服务端报价与签名确认下单
  -> 真实 PostgreSQL
  -> 原 ERP 统一订单 API 回读
```

它不替代一龙平台的消费者身份、Grant 签发、动作确认和 Invocation 账本，也不证明公网平台到商户的完整纵向链。

## 已验证结果

2026-08-14 首次闭环及正式脚本复跑均通过：

| 检查项 | 结果 |
|---|---|
| 服务端报价 | HTTP 200，金额由商户服务端生成 |
| 签名确认下单 | HTTP 200，订单状态 `confirmed` |
| 支付边界 | `payment_status=unpaid`，没有资金移动 |
| 库存事务 | 验收商品库存由 5 减至 3 |
| 幂等重放 | 相同下单信封返回同一结果，库存未再次扣减 |
| 开放商业状态查询 | 返回同一开放商业订单 |
| 真实数据库 | 写入开放商业订单、ERP 统一订单和 ERP 明细 |
| 原 ERP 回读 | `/api/v1/orders` 返回同一 `unified_order_id` |
| 调用回执 | 同一提交幂等键只有一条成功回执 |

咖啡仓的可重复入口为：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\test_open_commerce_real_server.ps1 `
  -AcknowledgeProductionWrite
```

## 发现并修复的问题

验收前服务器二进制构建于 2026-08-07，早于 2026-08-12 合入的“平台签名确认权威”合同。旧二进制仍要求业务输入自报确认字段，导致当前 `order.commit` 信封返回 `400`。部署当前咖啡项目提交后，真实订单闭环通过。

因此，商户运行时验收必须同时记录 Git 提交和线上二进制哈希；只看健康接口不能证明运行合同与当前源码一致。
