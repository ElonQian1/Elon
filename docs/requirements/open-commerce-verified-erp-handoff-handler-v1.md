# 开放商业 ERP 写入与回读验证处理器 V1 需求

## 1. 目标

在现有开放商业接入器任务领取、续租、释放和完成工作器之上，提供一个厂商无关的 ERP
处理器。处理器把平台已经签发的终态业务证据、标准业务回执和 Invocation 级幂等身份交给
商户自有 ERP 插件；插件写入后，处理器必须再次调用独立回读接口，并核对外部记录保存的
项目、商户、Invocation、数据接入、业务证据摘要和来源摘要。只有全部绑定一致，工作器才能
提交 `applied` 回执。

本批解决的是每个商户重复实现“证据转换、幂等来源、写入、回读和绑定核对”的问题，不实现
任何美团、抖音、京东、淘宝闪购或具体生产 ERP 适配器，也不把插件自报的回读结果提升为平台
独立签名证明。

## 2. 强制边界

1. 新处理器必须复用 `createAdapterHandoffWorker` 的租约、续租、释放、完成和稳定幂等键，
   不建立第二套队列或任务状态。
2. 输入必须绑定现有活动 Claim，并要求成功终态证据、有效标准业务回执、可用结果和 64 位
   SHA-256 结果摘要；项目、商户和 Invocation 任一不一致都失败关闭。
3. 处理器向 ERP 插件传递版本化、不可变的来源信封。信封必须包含项目、商户、Invocation、
   数据接入、机器凭据及版本、业务证据摘要、标准业务回执引用和 Invocation 级幂等键，并形成
   SDK 自有的确定性来源摘要。
4. ERP 插件的写入入口必须返回有界目标记录号；插件必须以来源幂等键重复安全地写入，同一
   Invocation 重试不得创建第二条业务记录。
5. 写入完成后必须调用独立 `readBack` 入口。回读结果必须返回同一目标记录号及完整来源绑定；
   处理器不得仅凭写入函数的返回值、HTTP 200 或本地内存状态提交 `applied`。
6. 回读缺失、暂不可见或任一绑定不一致时，处理器必须抛出临时失败，使现有工作器释放租约
   等待重试；不得伪装为成功、忽略或永久拒绝。
7. ERP 插件可以使用现有 `AdapterHandoffRejectError` 明确表达不可恢复的业务拒绝；处理器不得
   把普通异常静默转换成永久拒绝。
8. 来源信封、写入输入和回读证明均不得携带 Token、租约密钥、生产凭据或支付密钥；所有边界
   固定不移动资金，也不声明支付、履约、退款或外部平台授权成功。

## 3. 验收标准

1. SDK 导出一个可与 `createAdapterHandoffWorker` 直接组合的 ERP 处理器工厂，且不修改现有
   自定义 handler 的兼容行为。
2. 正常用例证明写入只发生一次、随后执行独立回读，回读完整匹配后返回 `applied` 和目标记录号。
3. 相同任务重试向插件提供相同幂等键和来源摘要，不依赖 Claim ID、尝试次数或租约密钥。
4. 项目、商户、Invocation、数据接入、凭据版本、结果摘要、来源摘要或目标记录号任一回读篡改
   都阻止 `applied`，并由工作器走临时释放路径。
5. 缺少有效标准业务回执、缺少结果摘要、错误证据 Schema 或 Claim 绑定错误均失败关闭，且不
   调用 ERP 写入函数。
6. 插件显式业务拒绝沿用现有永久拒绝回执；写入、回读、取消和网络异常保持可重试语义。
7. Node 全量测试、源码体积和文档模块化门禁通过；SDK 文档明确幂等要求、回读证明层级与
   生产适配器未实现边界。

## 4. 非目标

- 不实现具体 ERP/CRM、外部平台、支付、物流、营销发布或财务适配器；
- 不修改服务端数据库、HTTP、MCP、PC、APK、Sui 或链上状态；
- 不重新计算或替代服务端现有 `result_sha256`，SDK 只绑定服务端随 Claim 返回的结果摘要；
- 不证明插件的 `readBack` 来自独立可信硬件、第三方签名或生产环境；
- 不自动部署商户项目，不读取商户私有数据库，也不保存外部 ERP 原始记录。
