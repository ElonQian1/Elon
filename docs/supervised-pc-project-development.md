# Codex 桌面监督、一龙 PC 执行的通用项目开发协议

最后更新：2026-08-08
状态：paused_for_automatic_dispatch（自动派发/续跑仍暂停；Win 语义控制与诊断能力建设已获本次显式授权）

> 暂停期间不得把新任务派发到监督闭环，也不得自动等待、验收、改进、续跑或变更已有监督任务。已有记录、journal、隔离 worktree 与租约保持原状，等待用户明确处置。普通项目任务由当前代理直接按目标仓库规则执行。本文保留为历史协议与恢复参考，只有用户明确取消暂停后才能重新启用。

> 2026-08-08 范围化授权：用户明确要求持续完善“Codex 直接调用 Win 页面和 Tauri 功能、语义化操控 Win 客户端、统一前端/Rust/CLI/网络日志”。因此只恢复这些控制面与可观测性能力的设计、实现、验证和发布；不因此恢复跨项目任务自动派发、后台自进化、自动等待、自动验收或自动续跑。新控制能力必须使用动作白名单、短期会话、用户审批、脱敏事件、journal 和可撤销回执，不能开放任意脚本、任意 Tauri command 或浏览器 Cookie。

本文记录一套与具体业务项目无关、当前已暂停的协作模式：Codex 桌面端负责分析、派发、监督和独立验收；一龙 PC 端负责把写任务路由到项目绑定节点，由节点上的 Codex CLI 或其它获准执行器完成修改、验证、提交和发布。暂停前，BB64A、Android 项目、Web 项目、Rust 服务或其它 Git 项目使用同一协议。

一句话原则：

> Codex 桌面端是监督与验收控制面；一龙 PC 端和绑定节点是执行面；目标项目的 Git、测试、journal 与构建产物是共同事实来源。

这套模式也称为“受监督的双闭环”：一条闭环交付用户项目需求，另一条闭环从真实任务中发现并修复一龙 PC 端的能力缺口。这里的“进化”是平台工具、流程和可靠性的持续改进，不代表模型自行训练，也不允许系统无边界地修改自己。

## 1. 适用范围与权威边界

出现以下任一情况时，应读取并应用本文：

- 用户在 Codex 桌面端讨论某个项目的功能修改，并希望实际写入由一龙 PC 端完成。
- 远程开发者通过一龙绑定的 PC 节点开发 BB64A 或其它项目。
- 需要在完成业务任务的同时，记录一龙 PC 端的慢点、失败点或缺失能力。
- 原业务任务因一龙平台能力不足而阻塞，需要修复平台后恢复原任务。

权威边界：

1. 本文只定义跨项目的监督、派发、证据、复盘和恢复协议。
2. 目标项目自己的 `AGENTS.md`、`README.md`、仓库脚本和发布手册决定该项目如何修改、验证、提交与发布。
3. 一龙仓库的 `WF-*`、`scripts/ai-task-preflight.*` 和 `scripts/finish-ai-task.*` 只适用于一龙自项目，不能复制到 BB64A 或其它用户项目。
4. 用户当前明确指令始终高于本文的默认路由。用户若明确要求桌面端直接修改，监督者应先说明会绕过 PC 实测闭环，再按授权执行。

## 2. 四个职责面

| 职责面 | 默认承担者 | 职责 | 不应承担 |
|---|---|---|---|
| 监督控制面 | Codex 桌面端 | 理解需求、只读检查、形成任务单、选择节点、监督进度、审批高风险动作、独立验收 | 与 PC 节点同时写同一 checkout；仅凭“已完成”文字验收 |
| 项目执行面 | 一龙 PC 端、绑定节点、Codex CLI | 读取目标仓库规则、隔离工作区、修改、测试、构建、提交、推送、按项目规则发布 | 擅自改一龙平台；绕过目标仓库规则 |
| 事实与证据面 | Git、测试、构建产物、journal | 证明实际修改、验证结果、版本、失败原因、恢复位置和人工介入 | 用聊天总结替代可核对证据 |
| 平台改进面 | 一龙仓库的独立改进任务 | 修复调度、上下文、工具、恢复、发布、UI 或节点能力，并做回归和版本化发布 | 把平台改进混入用户项目提交 |

同一次合作可以同时推进“用户任务”和“平台改进”，但必须拆成不同任务、不同仓库或独立 worktree、不同提交和独立验收。逻辑上是一条连续闭环，Git 现场不能混在一起。

## 3. 启动前门禁

监督者派发写任务前必须确认：

- 目标项目身份明确，包括项目 ID、仓库、默认分支和当前基线。
- 目标项目已经绑定正确 PC 节点，节点在线且工作区身份与目标仓库一致。
- 本轮执行路线明确；本机已登录 Codex CLI 时优先 `route_a`，其它路线必须由用户或项目策略授权。
- 目标仓库的规则入口可以读取；未知项目先找 `AGENTS.md`、`CODEX.md`、`README.md` 或等价入口。
- PC 端能够返回至少一种真实证据：Git diff/提交、验证输出、构建产物或结构化 journal。
- 桌面端与 PC 节点不会同时写同一个 checkout；写任务必须使用目标项目认可的隔离方式。

任一关键条件不满足时，状态应为 `PC_EXECUTION_UNAVAILABLE` 或 `PC_EXECUTION_BLOCKED`。桌面端不得静默改为自己写代码并假装完成了 PC 实测；可以修复连接、请求用户补充授权，或在用户明确同意后采用桌面直写的例外路径。

## 4. 标准用户任务闭环

```text
用户需求
  → 桌面端只读分析并定义验收标准
  → 通过一龙 PC 任务入口派发到绑定节点
  → 节点上的 Codex CLI 在隔离现场执行
  → 回传 journal、diff、测试、提交和产物
  → 桌面端独立复查
  → 通过：交付并复盘
  → 不通过：继续派发修正，或进入平台能力改进闭环
```

### 4.1 桌面端只读分析

桌面端先确认需求、非目标、风险、目标仓库规则和最小验证范围。此阶段允许读取文件、历史、日志和现有证据，不直接编辑目标项目。

如果需求本身含糊，先把可以安全确定的部分整理进任务单；只有会显著改变结果或授权范围的问题才暂停询问用户。

### 4.2 形成可执行任务单

任务单必须让 PC 执行器不依赖桌面端隐含上下文也能工作，至少包含：

- 用户目标与用户可见结果。
- 明确的非目标和禁止修改范围。
- 目标项目、绑定节点和预期分支/基线。
- 必读规则入口，但不复制目标仓库的整套文档。
- 验收标准、必须运行的验证和是否需要发布。
- 风险、权限、密钥和人工审批边界。
- 完成时必须回传的证据。

推荐的结构化任务头：

```yaml
mode: supervised_pc_first
target_project: <project id or name>
target_repository: <repo identity>
execution_route: route_a
desktop_write_allowed: false
objective: <用户目标>
non_goals:
  - <不在本轮处理的事项>
acceptance:
  - <可核对的验收条件>
required_evidence:
  - git_diff_or_commit
  - validation_results
  - task_journal_summary
release_required: <true|false|follow-project-policy>
```

这是一份协作合同，不要求所有实现使用同一种 API 字段。PC UI、MCP、CLI 或后续监督接口可以采用自己的 wire format，但不得丢失这些语义。

### 4.3 派发到一龙 PC 端

监督者使用当前可用的一龙 PC 任务入口，把任务交给目标项目绑定节点。派发后记录任务 ID、节点 ID、工作区身份、起始 Git SHA 和执行路线。

默认选择目标项目的本机 AI 路线 `route_a`，由节点上的 Codex CLI 自己读取项目规则并执行。若项目选择 `route_b`、`route_c*` 或其它执行器，仍需遵守本文的隔离、证据和验收合同。

### 4.4 PC 节点执行

PC 执行器必须：

1. 在目标仓库内读取该仓库自己的规则。
2. 运行该仓库要求的预检，确认唯一编辑现场。
3. 只在隔离现场修改，不碰桌面端正在审查的 checkout。
4. 执行与风险匹配的验证、构建和发布。
5. 只提交本任务文件，保存提交 SHA、验证结果和产物身份。
6. 对失败、审批和恢复点写入 journal，不把密钥写入日志或任务回传。

目标项目没有成文流程时，执行器应采用保守的 Git 分支/worktree、最小验证和可回滚提交；同时把“项目缺少规则入口”记录为项目上下文改进项，而不是把一龙仓库规则强套过去。

### 4.5 桌面端监督

桌面端按结构化进度和证据监督，不与执行器争抢写权限。监督重点包括：

- 是否派发到正确节点和工作区。
- 是否读取了目标项目规则。
- 是否出现长时间无进度、重复失败、审批等待或恢复失败。
- 修改范围是否偏离任务单。
- 验证、构建、发布和 Git 状态是否真实完成。
- 本轮是否暴露了一龙 PC 端的能力缺口。

普通进度慢或短暂等待不是平台失败。监督者应先看 journal、进程状态和最后证据，再决定继续、补充任务、取消或进入能力改进闭环。

### 4.6 证据回传与独立验收

PC 端的“完成”只是一项声明。桌面端至少核对下列证据中的适用项：

```yaml
task_id: <id>
node_id: <id>
workspace_identity: <repo/path fingerprint>
base_sha: <sha>
head_sha: <sha>
commits:
  - <sha and subject>
changed_files:
  - <path>
validations:
  - command: <safe summary>
    result: <passed|failed|not_run>
artifacts:
  - <version, hash, or download identity>
release_result: <published|code-only|not-required|failed>
journal_summary: <关键阶段、审批、恢复和失败>
remaining_risks:
  - <risk>
platform_improvement_candidates:
  - <candidate>
```

验收失败时，桌面端应把具体差异和新验收条件作为后续任务继续派发。除非用户明确改变模式，否则桌面端不直接接管目标项目写入。

## 5. 平台能力改进闭环

每次任务复盘都要先分类，避免把业务代码问题误判为平台问题。

| 分类 | 例子 | 默认处理 |
|---|---|---|
| 目标项目问题 | 业务 bug、测试失败、依赖冲突 | 在原项目任务中修复 |
| 项目上下文问题 | 缺少规则入口、验收条件不清、文档过期 | 先完成可完成部分，再为目标项目补上下文 |
| 一龙 PC 平台问题 | 派发失败、错误节点、journal 缺失、恢复失败、工具不可用、UI 无法监督 | 建立独立的一龙改进任务 |
| 环境或外部依赖 | 节点离线、网络、第三方服务、凭据过期 | 恢复环境或请求授权，不擅自改代码掩盖问题 |
| 安全或权限问题 | 需要密钥、生产写入、越权、不可逆操作 | 暂停并请求明确批准 |

### 5.1 不阻塞原任务的缺口

如果缺口不影响本次正确交付：

1. 原项目任务继续完成。
2. 在复盘中记录一龙改进候选、证据、影响和建议优先级。
3. 任务完成后再在一龙仓库建立独立改进任务。
4. 改进完成后用回归测试和下一次真实任务验证效果。

### 5.2 阻塞原任务的缺口

如果确认是一龙能力缺口且原任务无法继续：

```text
保存原任务快照、Git 基线和 journal
  → 标记 PC_EXECUTION_BLOCKED
  → 在一龙仓库创建独立平台改进任务/worktree
  → 修复并运行平台回归
  → 提交、推送并按一龙规则发布所需组件
  → 确认目标节点获得新能力
  → 从原快照或 Codex session 恢复
  → 重新执行未完成步骤
  → 桌面端再次独立验收
```

恢复前必须确认原项目现场未被其它任务覆盖。无法安全恢复时，基于已提交 SHA 和 journal 创建新的续跑任务，不能假装热恢复成功。

### 5.3 需要人工批准的改进

以下改进不得为了“自动续跑”而自行扩大权限：

- 安全策略、认证、密钥或跨用户授权变化。
- 发布系统、生产数据或不可逆迁移。
- 大规模平台架构替换。
- 会影响其它正在运行任务的节点升级。
- 需要读取用户未授权仓库、日志或隐私数据。

### 5.4 独立低优先改进队列

非阻塞平台改进不得继续占用原用户任务的 task、conversation、worktree 或执行资源。原任务必须先到终态并回传用户结果；随后由节点把 `post_task_improvement` 放入持久化低优先队列，并遵守以下顺序：

1. 验证当前监督协议，以及父任务已终止且 owner、node、project、root、workspace 全部一致。
2. 为改进建立独立 task 和 conversation；调度前实际创建、验证并持久化该代独立 worktree/branch，不能只在模型里声称隔离。同一 root 的后续代只复用该改进自己的受监督 worktree 与 root lease。
3. 当前台用户任务、发布 owner、节点更新或构建资源压力出现时，先持久化 action intent 与 `requested_by/source/reason/requested_at_ms/interruption_source`，再取消后台执行器；审计或取消失败时保持原状态并 fail-closed，不能从异常退出码猜测来源。
4. 让路条件消失后自动续跑下一代；配额、限流和 credit 错误按上限与退避自动重试。成功进入审查队列，Desktop 可以 approve、reject 或要求下一代修正，审查必须保留 reviewer/provenance/time。
5. PC UI 必须同时显示实际 worktree、改进队列、重试、让路原因、审查来源、更新恢复状态、发布 batch/owner/waiters/stages 和取消来源，不能只显示一个笼统的“运行中”。

本地任务优先使用节点本地可信身份。远程 v1 只有在身份、能力、live lease 和连接连续性都成立时才能执行；缺一项即 fail-closed，不得用本地兼容路径绕过。

## 6. 跨项目接入方式

仅把本文提交到一龙仓库，并不会让另一个项目里的 Codex 桌面任务自动知道或自动执行这套模式。外部项目必须通过以下至少一种方式接入：

1. 一龙 PC 端在派发时注入本文对应的监督合同版本和目标项目身份。
2. 远程开发者在开始任务时读取本文的当前版本或 commit-pinned 链接。
3. 目标项目在自己的 `AGENTS.md` 或等价入口放置下面的最小规则，并指向本文。

BB64A 或其它外部项目首次接入时可以先采用第 2 种；稳定使用后应升级为第 1 或第 3 种。目标仓库的相对规则入口和平台注入的协议版本才是长期事实来源，不应要求用户在每次新任务中反复粘贴某台电脑上的绝对文档路径，也不能只靠聊天记忆。

### 6.1 不同开发者路径与本机直读

项目身份与本地目录是两层数据：

- 项目 ID、仓库 URL 和默认分支用于识别“这是同一个项目”。
- `project_pc_workspace_bindings` 按用户、PC 节点和项目保存各自的本地目录。同一个 BB64A 可以在甲开发者机器上位于 `D:\work\bb64a`，在乙开发者机器上位于其它路径。
- 任务派发必须使用目标节点自己的绑定，不能把最近一次由其它节点更新的绝对路径当成所有机器的公共路径。
- 协议文档应通过仓库内相对入口、commit-pinned 链接或平台合同版本引用；只有当前机器确实需要直接读取平台仓库文件时，才使用该机器自己的绝对路径。

Codex Desktop 无需打开浏览器即可查询当前登录账号及当前 PC 节点的项目绑定：

```powershell
$helper = '.agents\skills\codex-pc-supervisor\scripts\invoke-supervised-task.ps1'
powershell -NoProfile -ExecutionPolicy Bypass -File $helper -Action Projects `
  -ProjectFilterId '<project-id>'
```

该命令只访问 `127.0.0.1` 的受保护本地接口；NodeAgent 再使用 `direct_reqwest_no_proxy` 读取一龙云端，并携带当前节点 ID 解析本机绑定。响应不包含登录 token。这样既不依赖浏览器登录态，也不会因浏览器代理无法访问一龙云端而失败。

### 6.2 手工交接指令

用户可以把下面这段话与本文一起交给 BB64A 或其它项目的开发者/Codex 桌面端：

```text
请先完整阅读《Codex 桌面监督、一龙 PC 执行的通用项目开发协议》，并把它作为本轮跨项目协作协议。

你仍必须遵守当前目标仓库自己的 AGENTS.md、README、验证和发布规则；不要把一龙仓库脚本复制到目标项目。

涉及实际写入时，默认由你在 Codex 桌面端完成只读分析、任务派发、过程监督和独立验收；把修改任务交给一龙 PC 端绑定节点执行。不要与 PC 节点同时写同一 checkout。

开始前请先确认并回复：目标项目、目标节点/执行路线、桌面端是否保持只读、验收证据、PC 入口不可用时的处理方式。未确认前不要修改代码。

任务结束时分别报告 USER_TASK_STATUS、PC_EXECUTION_STATUS、SUPERVISOR_REVIEW_STATUS、PLATFORM_IMPROVEMENT_STATUS 和 REMAINING_RISKS。
```

开发者读完后的有效确认至少应说明：

- 当前目标是 BB64A 还是其它项目，以及所读目标仓库规则入口。
- 写任务将派发到哪台绑定节点、使用哪条执行路线。
- Codex 桌面端是否保持只读监督；若有例外，例外由谁批准。
- 将用哪些 Git、测试、journal 或产物证据验收。
- 一龙平台缺口是任务后改进还是阻塞修复后续跑。

只有回复“已阅读”而没有这些确认，不算完成交接。

推荐放入外部项目的最小规则：

```markdown
## 一龙 PC 优先执行

当本项目通过 Codex 桌面端讨论写任务，且一龙 PC 任务入口可用时：

- Codex 桌面端默认只做分析、派发、监督和独立验收。
- 实际修改优先派发到本项目绑定的一龙 PC 节点，由节点执行器完成。
- 桌面端与节点不得同时写同一 checkout；以 Git、测试、journal 和产物为验收事实。
- 必须遵守本仓库自己的开发、验证和发布规则，不复制一龙自项目脚本。
- 一龙平台缺口必须另建一龙改进任务；阻塞时保存本项目现场，平台修复验证后再续跑。
- 若 PC 任务入口不可用，明确报告，不得静默切换为桌面直写。
```

外部项目可以增加自己的验证和发布规则，但不应改写“监督端与执行端分离、证据验收、平台改进隔离”这三个不变量。

## 7. BB64A 使用示例

假设用户在 BB64A 的 Codex 桌面任务中要求新增一个功能：

1. 桌面端读取 BB64A 自己的规则和相关代码，只读形成需求、非目标和验收标准。
2. 桌面端通过一龙 PC 任务入口选择 BB64A 项目及其绑定节点，派发 `supervised_pc_first` 任务。
3. 节点上的 Codex CLI 在 BB64A 认可的隔离现场修改、测试、构建并按 BB64A 规则提交或发布。
4. 一龙 PC 端返回任务 journal、BB64A diff/提交、测试结果和产物。
5. 桌面端独立审查。发现业务实现问题就继续派发 BB64A 修正任务。
6. 如果发现一龙 PC 端缺少某个构建工具但 BB64A 仍可交付，先完成 BB64A，再建立一龙改进任务。
7. 如果该缺口阻塞 BB64A，先保存 BB64A 现场；在一龙仓库的独立 worktree 修复、回归并发布 PC/节点能力，然后恢复 BB64A 任务。

BB64A 的代码提交中不能夹带一龙平台代码；一龙的改进提交中也不能夹带 BB64A 代码。

## 8. 真实使用指标

长期 dogfooding 应按任务记录可核对指标，而不是只保留成功案例：

- 派发到正确节点的成功率。
- 首次有效进度时间和总完成时间。
- 用户任务完成率与桌面端首次验收通过率。
- 测试、构建和发布成功率。
- 断线或重启后的恢复成功率。
- 人工介入率、取消率和回滚率。
- 每类失败的次数、平均恢复时间和复发率。
- 每次真实任务产生的平台改进候选数、完成数和回归结果。

指标只能来自任务状态、Git、journal、验证和发布证据。不同项目难度必须分组比较，不能用简单任务的高成功率掩盖复杂任务缺口。

## 9. 完成定义与最终报告

一次受监督任务只有同时满足以下条件才算完整结束：

- 目标项目结果达到任务单验收标准。
- PC 执行现场和 Git 状态按目标项目规则收尾。
- 桌面端已独立核对适用证据。
- 未完成风险、外部阻塞和人工审批已明确列出。
- 平台能力缺口已分类；阻塞项已修复并验证，非阻塞项已进入独立改进候选。
- 没有把用户项目与一龙平台改进混入同一提交或工作区。

推荐最终报告固定区分：

- `USER_TASK_STATUS`：用户项目需求是否完成。
- `PC_EXECUTION_STATUS`：是否真正由一龙 PC 节点执行，节点与任务证据是什么。
- `SUPERVISOR_REVIEW_STATUS`：桌面端验收是否通过，依据是什么。
- `PLATFORM_IMPROVEMENT_STATUS`：本轮发现、已修复或待办的一龙能力缺口。
- `REMAINING_RISKS`：仍需用户、环境或外部系统处理的事项。
