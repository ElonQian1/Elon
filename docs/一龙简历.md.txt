# AI Agent Harness 产品经理 / 创业项目介绍

## 个人定位

我正在独立研发一套 AI Agent Harness 产品：**一龙云端 APK 开发平台**。

最初做这套 Harness 的动机很朴素：让工具先把庞大项目通过 repo map、RAG、符号索引、task pack 等方式压缩成 AI 容易理解的上下文，从而减少用户 token 消耗。

后来这套系统逐渐演进成完整的 Agent Harness：不仅帮助模型理解项目，还负责工具调用、隔离执行、代码修改、验证、构建、发布、审计和结果回传。

一句话概括：

> 模型负责推理，Harness 负责让模型在真实项目里安全、低成本、可验证地干活。

## 项目链接

- GitHub: [https://github.com/ElonQian1/Elon](https://github.com/ElonQian1/Elon)
- APK 下载: [http://43.139.149.158:8080/app/ElonSpeed-latest.apk](http://43.139.149.158:8080/app/ElonSpeed-latest.apk)
- Web / PC 端: [http://43.139.149.158:8080/pc](http://43.139.149.158:8080/pc)

## 产品简介

一龙是一个 AI 驱动的云端开发平台。用户可以在 Android APK 或 Web 端用自然语言描述需求，系统将任务交给 Codex、Copilot、AI CLI 或自定义模型，在真实 Git 工作区中完成代码修改、验证、构建、部署，并把最新 APK 下载链接返回给用户。

APK 侧的产品表达：

这不是简单封装模型 API，而是把模型接入真实工程生产流程。

## 我的 Harness 理解

我认为 Agent Harness 的核心不是“接入更多模型”，而是解决以下问题：

- 如何让模型理解一个大型项目，而不是每次从零读代码；
- 如何把用户模糊需求转成可执行的工程任务；
- 如何让模型在隔离环境里修改真实代码；
- 如何让每一步工具调用、构建、发布都有记录；
- 如何在失败时给模型足够上下文继续修复；
- 如何降低 token 成本、误改风险和重复探索成本。

所以我的 Harness 设计重点是：

- 项目理解：repo map、RAG、符号索引、task pack；
- 执行隔离：Git worktree、用户项目隔离、节点隔离；
- 工具编排：AI CLI、构建脚本、发布脚本、PC 节点；
- 验证闭环：编译、测试、部署校验、APK 发布；
- 可审计：commit、版本、计费、节点执行记录；
- 多场景扩展：代码项目、群聊内容、足球比赛分析、手机/电脑自动化工作流。

## 其他场景扩展

除代码开发 Harness 外，我还做了微信群聊和业务内容 Harness。

例如群聊场景中，系统会对用户聊天内容做类似代码项目的 repo map、RAG 和结构化索引，让 AI 可以自动总结群聊、沉淀到项目中，并支持多人围绕同一个项目协作。

在足球世界杯场景中，我设计了专门的业务 Harness，将群聊观点、比赛信息、赔率/订单等数据通过多层工具分析后交给模型，用于复盘比赛、总结经验，并为下一轮分析补充工具和上下文。

系统还包含 ASR / TTS 和用户授权下的手机/电脑自动化能力，可以通过语音触发工作流，例如查询商品价格、整理公开信息、生成表格，并沉淀到个人项目中。

## 当前仍在增强的部分

我也清楚这套 Harness 还没有到完全企业级标准化阶段，后续重点包括：

1. 远程 embedding provider 和多模型检索策略；
2. 索引增量更新和检索质量回归集；
3. 更标准化的多 Agent 调度策略；
4. 更明确的工具权限、安全沙箱和用户项目隔离策略；
5. Harness 自身评测体系，例如成功率、误改率、修复率、平均完成时间。

## 为什么我适合 Harness 产品经理

我不是从概念上理解 Harness，而是自己从 0 到 1 做了一套可运行产品。

我既理解用户为什么需要它，也理解底层工程为什么难：上下文压缩、工具调用、任务拆解、隔离执行、验证闭环、发布链路、成本控制、审计追踪，每一层我都实际做过。

我对 Harness 的理解是：

> 模型决定能力上限，Harness 决定模型能不能稳定进入真实生产流程。
