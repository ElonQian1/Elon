# 双 APK 移动设计系统 V2

## 0. 本次变更的性质

这是设计规范重建，不是维护旧皮肤。用户已明确要求取消两个 APK 的错误规范。
旧的轨道金属主题、强制深色、旧调色板、胶囊导航、旧页面字体和 GridStyle 外观，不再具有设计优先权。
保留的是经过重新核查的业务能力、安全边界和可访问性要求，而不是旧页面的几何和审美。

本文件记录已接受的设计要求。规范接入不代表 UI 已改造、已美观、已编译或已验收；主线是否已采用以合并状态为准。
正式品牌色、组件代码和页面母版尚待按本文件实现并验证；没有取得证据的部分不能写成“完成”。

## 1. 依据、决策和证据必须分开

- **官方依据**：采用 Android 官方移动设计、Material 3、可访问性和窗口适配指南；移动 PWA 采用 WCAG 2.2 AA 作为目标。来源见 [官方依据](mobile-design-sources.md)。[S01–S07]
- **项目决策**：本文件明确选择的默认值和产品组织方式。它们可在保证可用性与一致性的前提下变更，不是行业唯一答案。
- **验收证据**：与具体提交、构建、设备、页面和状态绑定的截图、交互、语义和性能测试结果。

不存在“选对一个配色就符合行业标准”的结论。组件库、skill、Figma 和截图各自解决不同问题，不能互相替代。

### 设计规则冲突的处理顺序

先保证业务安全、真实数据、用户明确授权和兼容边界；再保证平台行为与可访问性；在此前提下执行 V2 设计系统和经验证的产品扩展。
旧文档、历史截图、旧组件实现及 AI 默认审美不能推翻上述顺序。
工程工作区隔离、保护其他代理修改、签名与发布机制不因视觉规范重建而取消。
对于发布前 UI 证据等本次明确修订的设计交付规则，必须同时修订旧指令入口，不能让冲突长期并存。

## 2. 废止与保留

| 旧要求或隐含前提 | V2 处理 |
|---|---|
| 全应用必须真空黑、枪灰、钛色渐变、雾蓝信号 | 废止其强制地位；不自动沿用旧 HEX |
| 轨道、舱体结构缝、星讯、校准刻度是产品必备语言 | 废止；不得为履行旧规范继续添加装饰 |
| 所有主要入口都采用胶囊或悬浮模糊导航 | 废止；按导航语义与平台组件选择形态 |
| 新页必须继承好友页、我的页或旧 GridStyle 的外观 | 废止；旧组件要经过 V2 审核，未通过则替换 |
| DARK / CREATE / TRADE 的页面配色分裂天然正确 | 废止；业务模式不是突然切换整页明暗的理由 |
| 每个页面只能有一个功能或一个动作 | 改为清晰的主次；允许合理的辅助操作和不同任务区 |
| APP 与 Web 每次都必须改同一 HTML、同一提交、像素一样 | 改为共同语义与受影响功能对齐，平台布局和实现可不同 |
| 编译或静态测试通过便可说明 UI 已交付 | 废止；系统级 UI 改造必须有运行时证据 |
| 未读旧规范不得设计、已有组件必须无条件优先 | 改为读 V2；优先复用符合 V2 的组件 |
| 48dp、可读文字、安全区、真实数据和敏感操作确认 | 重新依据官方指南或业务安全边界采纳，不因为旧文档也写过就删除 |

不把“全部禁止渐变”“全部禁止阴影”“全应用必须同一种卡片”等相反口号再写成新教条。
品牌表现可以存在，但必须服务信息或识别，不能损害对比度、交互、性能和一致性。

## 3. 总体设计方向〔项目选择〕

主项目采用清晰的移动协作工具方向；量化采用可核对、易扫描的数据工具方向。
共同基础是明确的信息层级、稳定导航、适度留白、可识别的交互、完整状态和可信数据。
二者共享基础组件、文字和语义规则，不强迫业务首页采用相同结构或相同密度。

默认背景为清晰的主题表面，装饰不进入最小可交付功能；不以“高级感”“工程感”替代具体设计要求。
深浅主题默认跟随系统，并提供显式选择。用户选定的主题在应用内保持连续；特别的图表或外部网页表面要明确边界。
主项目动态取色属于可选增强；量化的涨跌、风险和订单状态颜色不得被动态取色改变含义。[S04]

## 4. 颜色与 Token

采用用途命名，不采用页面名或材质名作为新 Token 的主体。
基础角色包括 `surface`、`surfaceContainer`、`onSurface`、`onSurfaceVariant`、`primary`、`onPrimary`、`outline`、`error`。
扩展业务角色区分 `status.pending`、`status.success`、`status.warning` 与 `financial.positive`、`financial.negative`、`financial.neutral`。
“等待审批”不默认等于错误；“上涨”不默认等于安全；“数据缺失”不等于零。[S04；业务语义为项目规则]

### 初始实施方式

从锁定版本的 Material 3 默认主题与组件出发，作为可运行基线；它不是最终品牌方案。
完成两套代表页面的浅色、深色、长文本和状态检查后，再把品牌方案通过 Theme Builder 或等价受控流程生成并登记。
没有经过对比度与代表页面验证的 HEX 不得升级为正式品牌规范。旧色值也不享有豁免。

### 单一来源

语义规则使用同一 V2 版本。正式色值与度量由一个版本化 Token 来源维护，Android/PWA 消费各自格式；不在页面文件中重复维护调色板。
两个仓库可先以相同版本和内容摘要同步基础规则，不强制为了共享样式迁移到 monorepo。
旧资源名可作为限期兼容别名存在，但必须映射新语义；不能成为恢复旧设计的入口。

## 5. 排版与信息密度

使用系统可读字体和系统字体缩放。标题、正文、辅助文字、数值和按钮标签各有语义角色，不直接沿用旧页面字号。
以下是 V2 的**项目起始映射**，不是所有页面都必须精确使用这些数字：

| 内容 | 起始字号 / 行高 | 使用限制 |
|---|---:|---|
| 页面主标题 | 22sp / 28sp | 大标题页面可用 24sp / 32sp；不要为装饰占满首屏 |
| 分组标题 | 16sp / 24sp | 用字重和间距区别，不只改颜色 |
| 聊天正文、常规输入 | 16sp / 24sp | 中文多行必须实测，不锁死文本容器高度 |
| 次要正文、字段标签 | 14sp / 20sp | 仍需满足可读性；关键说明不能降格为弱提示 |
| 时间戳等低优先级元信息 | 12sp / 16sp | 不用于交易风险、金额单位、确认后果等关键内容 |
| 主数值 | 从 24sp / 32sp 起评估 | 使用数值语义，不靠极端放大制造“专业”效果 |

行高是初始值，不允许用固定父容器裁剪字体放大后的文本。中文、拉丁字符、负号、小数点和货币单位一起验收。
同列数值按位对齐；可用等宽数字特性，但不强制整个中文界面使用等宽字体。
窄屏或大字时允许换行、单列和详情展开；不通过关闭字体缩放解决布局问题。

## 6. 布局、导航与系统交互

布局按当前窗口可用空间组织，不以某一台手机截图作全局绝对坐标。处理旋转、分屏和声明支持的大屏；不通过机械缩放整页适配。[S05]
项目默认间距阶梯为 4/8/12/16/24/32dp；普通手机页横向边距可从 16dp 起，较宽区域从 24dp 起评估。
这些是布局起点，不是禁止其他数值的规则，也不能压过 Material 组件默认触控与文字需求。

一级导航用于稳定目的地，页内标签用于同一对象的不同内容，操作按钮用于执行动作，三者不得混淆。
窄屏优先采用标准带文字的底部导航模式；更宽窗口可以使用导航侧栏或列表–详情结构。数量与分组由用户任务决定，不为满足模板增加假入口。
详情页返回到原任务位置；输入草稿、列表位置和筛选应在合理生命周期内恢复。退出账号后不得恢复不属于当前账号的数据。

系统状态栏、导航栏、刘海、手势区域和软键盘必须处理正确。只由明确的一层负责消费对应 inset，避免重复 padding。
输入框、错误说明和最终动作在键盘展开后仍可到达。不能把“不符合某个 Compose skill 前置条件”当成 View 无法处理安全区的理由。[S06]
可提供滑动等便捷手势，但关键功能必须有可发现的点击路径；不会要求用户学会隐藏手势才能使用。

## 7. 通用组件规则

优先采用所选 Material 3 实现的按钮、输入、导航、菜单、对话框和 Sheet；不重新绘制一整套通用控件来模仿截图。
自定义组件必须有明确业务价值，并提供状态、语义、尺寸与交互测试。

| 类别 | 合同 |
|---|---|
| 按钮 | 动作名称清楚，主次可辨；可同时存在合理的次要动作；加载时避免重复提交 |
| 图标按钮 | 图形与热区分开；提供可读名称，不能让读屏只念机器 ID |
| 输入 | 持续可见标签、格式/单位、就近错误、可恢复草稿；占位文字不代替标签 |
| 列表 | 高效扫描、稳定数据身份；长列表复用或惰性渲染，不默认把每行做成重卡片 |
| 卡片 | 用于确有独立边界的对象或内容；嵌套由信息结构决定，不为装饰套层 |
| Sheet/对话框 | 说明对象、动作、影响和恢复；有重要后果时使用明确动词；普通简单提示无需人为复杂化 |
| 数值与图表 | 单位、范围、时间与来源可核对；图表有文字摘要或可访问替代，颜色不是唯一编码 |
| 状态 | 正常、加载、空、失败、离线、无权限、部分/陈旧数据分别设计，不只设计成功态 |

按钮使用组件默认形态或经验证变体；不再要求所有控件同一圆角或都是胶囊。
反馈包括适用的按压、选中、焦点、错误与禁用状态。动效解释状态变化，并尊重系统设置；不把模糊、发光和持续动画作为默认装饰。

## 8. 无障碍交付门槛

Android 的交互元素采用至少 48×48dp 的实际触控目标，视觉图标可以更小。需要同时验证父容器、命中区域与焦点区域；只声明 minimumHeight 不构成证明。[S02–S03]
相邻热区不得重叠。密集列表可减少非交互留白，不得靠缩小关键热区提高密度。

普通正文对比度至少 4.5:1；为便于执行，本项目关键金额、风险说明和按钮文字也以 4.5:1 为目标，不利用“大字例外”降低关键内容要求。
对识别操作和状态必需的非文本图形采用至少 3:1 的可见对比；不是要求所有装饰分割线都达到 3:1。[S02、S07]

读屏名称、角色、状态和焦点顺序应准确。装饰图不重复播报；带文字控件不机械重复 contentDescription。
自动化定位使用资源 ID、测试 tag 或明确的检查器字段；现有机器 ID 迁移须联动测试/检查器，不得永久挤占用户语义。

关键流程测试 100%、150%、200% 系统字体缩放或目标系统对应可用级别；视口与数值是项目验收矩阵，不是对所有系统的同一 API 承诺。
PWA 还需按 WCAG 2.2 AA 的适用条款检验键盘、焦点、重排、输入错误等；只通过对比度不能称整体 AA 通过。[S07]

## 9. 产品能力与数据真实性

重建信息架构可以移动和组合入口，但每项既有能力要有旧→新路径映射。保留能力不等于保留旧位置、旧卡片或旧布局。
无法确认的新能力不做假按钮，不把计划中的功能显示为已经可用。
缓存可以改善阅读，但应明确陈旧状态；需要新鲜授权、余额或风险判断的写操作不能依据过期展示直接执行。
数据未知、未加载、读取失败和确为零分开呈现。聚合数值注明覆盖范围，不把部分来源展示成全量。
视觉改造不修改金额真源、账户权限、会话凭据、交易模式或人工确认边界。

## 10. Android 实现方向

新组件和承担系统级重构的新页面优先使用 Jetpack Compose + Material 3；现有 View 页面可以过渡运行。
这是结合当前官方方向作出的项目选择。官方已说明 Compose-first、View 维护模式与互操作支持；不能再把无限期扩建自绘 View 组件库作为默认长期方案。[S08–S10]

按页面或组件边界渐进迁移，先做代表页面；对旧设备测量启动、内存、滚动、输入和恢复行为，再推广。
不要求一次性重写整个 APK，不为使用某个 skill 切换到 Expo/Flutter/React Native。
WebView 会话与原有 Rust/服务端能力不因 Compose 迁移而重做；保留已验证的认证和业务适配边界。
SDK、依赖版本和构建升级独立核查，不因示例要求更高 SDK 就在 UI 任务里盲目更改全部目标版本。

## 11. 先母版，后推广

先做可运行的组件目录与两套产品代表页面，不再从几百个局部 padding 修改开始。
主项目代表流程：项目列表 → AI 对话 → 查看执行/发布结果。
量化代表流程：网格列表 → 详情 → 参数检查/确认；仅在离线或授权测试环境验证敏感步骤。

代表页面必须包含浅/深主题、长中文、空/错/加载/离线和字体放大；使用脱敏或标记清楚的模拟数据。
验证通过后，将形态固化为共享组件与页面模式，再覆盖其他页面。
Figma/参考图可以指导视觉；只有真实 Android 构建截图和交互能证明 APK 实现。没有参考图也可以用 Material 基础和运行母版建立基准。

## 12. 新的验收与发布规则

系统级 UI 重构不适用“先公开发布、视觉验证可选”的快速通道。先产生可测试工件，再取得关键页面运行证据，最后进入原有正式发布流程。
内部测试包不等于公开发布，也不能被报告为已经正式交付。签名、版本分配和保留数据的安装流程继续由项目受控机制负责。

项目验收矩阵至少覆盖：窄窗口约 320dp、常用 360/411dp，浅深主题，字体缩放，键盘，返回和状态恢复。
若声明支持平板/折叠/分屏，额外测试实际窗口变化与对应布局；不以一个像素差阈值代替全部可用性。
优先使用可复现的模拟器真帧做批量检查；在代表性低端真机上补性能和交互证据。

证据必须分列：规则检查、代码测试、构建、运行截图、交互/读屏、性能、发布/装机、用户验收。
缺少环境时可以继续交付文档或代码，但必须报告未执行项，不能把它们改写成通过。
旧截图不作为新设计金标准；金标准更新需说明理由，不能更新截图来掩盖回归。

## 13. 规范治理

统一规则只在本文件维护；产品文件补充信息架构与业务展示，不重复复制整套基础规范。
两仓库相同 V2 文本用版本和摘要校验；项目扩展不能降低基础门槛。
审美变更要能定位到 Token、组件、页面与证据；不再新增一批相互覆盖的长 Prompt。
skill 是执行入口，不是独立的设计权威；按适用平台和任务选择，不用“安装数量”证明设计质量。
