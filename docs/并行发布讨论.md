# 多 AI 代理并行开发——防冲突工作流说明

> 2026-06-09 更新：一龙项目已经改为“代码先进入 `origin/main`，发布跟随服务器和最新主线”的流程。旧的“任务前必须 `git pull --rebase`、Android 版本号提交进 git、发布失败后重新运行脚本”规则已废弃；只有 `git push` 被 non-fast-forward 拒绝时才 rebase 一次。

## 背景与挑战

本项目同一台 PC 上同时运行多个 AI 代理（Copilot、Claude 等），它们会并发修改同一个 Git 仓库。如果没有规则约束，极易发生：

- A 代理的未提交改动被 B 代理的构建打包进去
- 两个代理同时写 versionCode，互相覆盖
- 某代理直接在主工作区构建，导致 `git status` 污染

下面的规则体系用来解决这些问题。

---

## 一、三大核心原则

| 原则 | 含义 |
|---|---|
| **先 fetch 再改** | 每次任务开始先 `git fetch origin main` 了解远端；工作区干净时可 `git pull --ff-only`，不要为了追最新提交反复 rebase |
| **commit 即 push** | 每次 commit 后立即 push，永不在本地堆积 commit |
| **发布不追车** | 代码 push 成功就是本代理的硬完成；发布被更新 main 超越时交由后续最新 main，不反复重跑 |

---

## 二、任务开始——状态检查决策树

每个 AI 代理接到任务后，**动代码前**强制执行：

```powershell
cd "d:\rust\active-projects\elon cli"
git fetch origin main
git status --short
```

根据结果走不同路径：

```
git status --short
        │
        ├─ 干净（无改动）─────────────────────► ✅ 主工作区直接改代码
        │
        ├─ 只有本 AI 自己已改的文件────────────► ✅ 继续，提交时只 add 自己的文件
        │
        └─ 有【其他 AI】未提交的改动──────────► ⚠️ 必须创建独立工作树（见第三节）
```

---

## 三、并发隔离——独立工作树方案

当检测到主工作区已有其他代理的未提交文件时，**禁止**在主工作区继续改代码，而是：

```powershell
# 1. 创建本会话专属工作树（基于 main 最新提交）
git worktree add ..\elon-session-<id> -b ai/session-<id> origin/main

# 2. 在独立工作树中修改代码（完全隔离，不干扰主工作区）
Set-Location ..\bb64a-session-<id>
# ... 修改文件 ...

# 3. 提交本会话的改动
git add -p   # 按 hunk 精确挑选，不夹带他人改动
git commit -m "feat(session-<id>): 描述"

# 4. 第一时间把本会话提交推入远端 main
git push origin HEAD:main
# 如被拒绝：git fetch origin; git rebase origin/main; 解决冲突后重推
powershell -ExecutionPolicy Bypass -File scripts\check-task-complete.ps1 -Kind CodePushed
```

**为什么用独立工作树而不是新分支？**  
因为 `git add -p` 只能按 hunk 粒度选择，当两个代理的改动在同一文件同一区域时无法安全拆分。独立工作树从文件系统层面彻底隔离，是唯一可靠方案。

---

## 四、构建部署——临时工作树隔离

代码提交到远程后，**编译和部署步骤必须在临时工作树中进行**，原因是：

- 避免构建产物（`target/`、`build/` 等）污染主工作区的 `git status`
- 确保构建基于明确的 commit SHA，不含任何未提交改动
- 多个代理可以同时用不同 SHA 创建各自的临时工作树并行构建

```powershell
# 提交后获取 SHA，创建临时工作树
$sha = git rev-parse --short HEAD
$tmp = "..\bb64a-deploy-temp-$sha"
git worktree add --detach $tmp HEAD   # detached HEAD，不创建新分支

# 在临时工作树里编译（例如后端）
Push-Location "$tmp\backend"
cargo zigbuild --release --target x86_64-unknown-linux-musl
Pop-Location

# 部署完成后必须清理
git worktree remove $tmp --force
```

> **例外**：`bb64a-build-windows` 是持久工作树（保留增量编译缓存），**禁止手动删除**。

## 五、Android 版本号——服务器原子分配

Android 的 `versionCode` 是整数，必须全局单调递增，多代理并发时最容易冲突。当前解决方案：

**由服务器 `/api/release/claim` 原子分配版本号**，`build.gradle` 里的版本只作为冷启动兜底，不提交进 git。流程如下：

```
代理 A 提交代码改动 → push origin main → CodePushed 通过
    └─► 运行 publish-apk.ps1
            ├─ 服务器 claim 分配 versionCode/versionName
            ├─ 临时写入 build.gradle
            ├─ 编译 + 打包 + 上传 APK
            └─ 还原 build.gradle，不产生 release-only commit
```

**并发冲突防护**：  
若代理 A 和代理 B 同时修改代码，先 push 成功的一方进入 `origin/main`；另一方只有在 push 被拒绝时 rebase 一次再推。
若代理 A 和代理 B 同时发布 APK，脚本只允许发布当前最新主线。慢构建如果发现 `origin/main` 或服务器 APK 已前进，就停止上传并汇报“发布交由后续最新 main”，不要求当前代理重新运行脚本。

```
代理 A: commit #1 push 成功，开始构建 APK
代理 B: commit #2 push 成功，稍后触发/接管最新 main 发布
  ↓
代理 A: 构建完成时发现 origin/main 已包含 Android 新改动 → 停止上传旧 APK
代理 B 或发布协调者: 基于最新 main 发布一次
```

## 六、完整流程图（一次典型任务）

```
任务开始
  │
  ├─ git fetch origin main
  ├─ git status --short
  │       │
  │       ├─ 干净 ──────► 主工作区改代码
  │       └─ 有他人改动 ─► 创建 session 工作树改代码
  │
  ├─ 修改代码
  ├─ rustfmt（仅本次改动的 .rs 文件）
  ├─ git add（仅自己的文件）
  ├─ git commit
  ├─ git push origin HEAD:main ◄── 必须立即 push
  ├─ check-task-complete -Kind CodePushed
  │
  ├─ [后端/前端] 创建 deploy-temp-$sha 工作树
  │       ├─ 编译
  │       ├─ scp 上传
  │       ├─ ssh 重启服务
  │       ├─ 验证健康检查
  │       └─ git worktree remove 清理
  │
  └─ [Android] 运行 publish-apk.ps1（需要发布时）
          ├─ 服务器 claim 版本号
          ├─ 编译 Rust + Kotlin → APK
          ├─ scp 上传 + 生成 version.json
          └─ 若被更新 main 超越则停止上传，不追车重跑
```

## 七、任务结束清理（防残档）

每次会话结束前必须确认：

```powershell
# 1. 临时工作树已全部清理
git worktree list
# 不应出现 bb64a-session-* 或 bb64a-deploy-*

# 2. 临时分支已删除
git branch -a | Select-String "session|copilot"
# 应为空

# 3. 清理遗留终端进程（防止内存泄漏）
$selfPid = $PID
Get-WmiObject Win32_Process -Filter "Name='pwsh.exe'" |
  Where-Object { $_.CommandLine -match '-noexit' -and $_.ProcessId -ne $selfPid } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force -ErrorAction SilentlyContinue }
```

## 八、关键规则速查

| 规则 | 原因 |
|---|---|
| 任务前 `git fetch origin main` | 了解远端状态；push 被拒绝时再 rebase |
| 有他人未提交改动→独立工作树 | 文件级隔离，防止 add 时夹带无关改动 |
| 构建必须在临时工作树 | 防止构建产物污染主工作区 |
| commit 后立即 push | 本地 commit = 无备份，磁盘故障即丢失 |
| Android 并发发布被超越→停止上传 | 避免旧 APK 覆盖新提交，发布交由后续最新 main |
| 禁止 `git push --force` | 会覆盖他人已推送的提交 |
| 禁止 `cargo fmt`（无参数） | 会格式化 486+ 历史文件，产生大量无关 diff |
