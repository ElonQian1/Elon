我现在做了一个app，已经集合有了，Codex、Claude Code、Copilot CLI 这类工具，

但是我还自研了一套大模型，但是我没有它们的背后的 Agent Harness。



我现在的愿景是，用户发来请求，我们先用我们的自研本地大模型，跑我们自己开发的Agent Harness，以rust代码开发为主，



得到我们自己的repo map，符号索引等一系列工具的产出，然后我们用自己的自研本地大模型或者我们写好的死工具，生成最适合ai了解的MD格式+XML边界的文档上下文，结合本地大模型对用户需求的理解，发给调用高级模型，把任务给更好的完成，



当高级大模型比如它们cli自带了一套Agent Harness，发现我们给的上下文不够，它们再跑一趟它们的Agent Harness从而更精确的修改，重构我们的用户需求的大项目代码。



你觉得我这一套流程怎么样？

我觉得你这套流程**方向非常好**，而且不是简单“再造一个 Codex / Claude Code / Copilot CLI”。你真正要做的是：

> **一个面向 Rust 大型项目的上游 Context Compiler / Meta Agent Harness。**
> 你的系统先把项目和需求“编译成高级模型最容易理解、最容易执行、最不容易误改的上下文包”，然后再交给 Codex、Claude Code、Copilot CLI 或你自己的模型执行。

这个思路是成立的，而且有产品壁垒。

但我会建议你对架构做一个关键升级：

> **不要只生成 MD + XML 文档塞给高级模型。**
> 更好的形态是：
> **短文档上下文 + 结构化索引文件 + 可查询 MCP 工具 + 下游 CLI 自己的 Agent Harness。**

原因是：大型项目里，静态文档很容易过长、过时、漏信息；但如果你把 repo map、符号索引、引用搜索、影响面分析做成工具，下游高级 agent 发现上下文不够时，可以直接调用你的工具按需查。

## 1. 你的整体架构是对的

你现在想做的是这个流程：

```text
用户需求
  ↓
你的本地大模型理解需求
  ↓
你的 Rust Agent Harness / 工具系统分析项目
  ↓
产出 repo map、符号索引、影响面、测试建议、上下文包
  ↓
生成适合高级模型阅读的 MD + XML 边界文档
  ↓
交给 Codex / Claude Code / Copilot CLI / 高级模型
  ↓
高级模型用自己的 Harness 继续读文件、改代码、跑测试
  ↓
完成大型项目修改
```

这很合理。

因为 Codex、Claude Code、Copilot CLI 本身确实都有自己的工具和上下文系统。Codex 官方文档说 Codex 可以读取、编辑和运行代码；Codex 还支持 `AGENTS.md` 自动加载项目说明，也支持 MCP 把外部工具和上下文接进来。([OpenAI开发者][1]) ([OpenAI开发者][2]) ([OpenAI开发者][3]) Claude Code 官方文档也明确说它能读取代码库、编辑文件、运行命令，并集成开发工具。([Claude API Docs][4]) GitHub Copilot CLI 文档也说它可以执行 shell 命令、读写文件、搜索代码库、抓取 web 内容、委托子 agent，并通过权限控制避免意外修改。([GitHub Docs][5])

所以你的系统不需要完全替代它们。你可以变成它们前面的“高质量上下文生产层”。

## 2. 你的定位应该是：Rust 项目上下文编译器

我建议你把自己产品的核心定位改成这个：

```text
不是重新做一个 Claude Code
不是重新做一个 Codex
而是做一个 Rust-aware Context Compiler + Preflight Agent
```

也就是：

> **在高级模型真正开始动手改代码前，你先帮它把项目地图、相关符号、影响范围、测试命令、风险点、架构约束整理好。**

这个价值非常大。

高级模型虽然强，但它每次进项目还是要自己搜索、读文件、猜结构、跑命令。你如果提前给它一份高质量的“任务上下文包”，它会少走很多弯路。

尤其是 Rust 项目，你可以做出通用 CLI agent 很难做到的专业能力：

```text
cargo workspace 解析
crate 依赖图
feature flags 分析
trait / impl 关系
函数引用关系
模块公开 API
宏使用位置
错误类型传播链
async 边界
测试影响面
clippy / fmt / check 验证建议
```

Rust 这块非常适合做确定性分析，因为 `cargo metadata` 本来就可以输出 workspace 成员和依赖解析信息；`rust-analyzer` 也提供 go-to-definition、find-all-references、重构、补全等代码智能能力。([Rust 文档][6]) ([Rust Analyzer][7])

## 3. 但你现在方案里有一个风险：不要让本地模型“总结事实”成为唯一依据

你说：

> 用本地大模型或者死工具生成最适合 AI 了解的 MD + XML 文档上下文。

这里要小心。

**repo map、符号索引、引用关系、调用关系、测试命令这些东西，最好不要主要由 LLM 生成。**

应该是：

```text
确定性工具产出事实
本地大模型负责解释、压缩、排序、组织
```

也就是说：

```text
cargo metadata         -> 工作区和依赖事实
rust-analyzer LSP      -> 定义、引用、类型、诊断事实
tree-sitter            -> AST 结构事实
ripgrep / git grep     -> 文本搜索事实
cargo check / test     -> 编译和测试事实
git diff / git status  -> 修改状态事实
本地 LLM              -> 把这些事实整理成适合 agent 阅读的上下文
```

不要反过来：

```text
本地 LLM 猜测项目结构
本地 LLM 猜测符号引用
本地 LLM 猜测影响范围
```

因为一旦本地模型总结错了，高级模型会被带偏。

你应该在发给高级模型的上下文里明确写一句：

```text
The generated context is an index and briefing, not the source of truth.
Before editing, verify the listed files and symbols by reading the actual files.
```

中文意思就是：

> **这份上下文是导航地图，不是真实代码本身。修改前请读取真实文件确认。**

这句话很重要。

## 5. 最关键的升级：把你的能力暴露成 MCP，而不是只生成文档

你现在想生成 MD + XML 文档，这是可以的，但还不够。

我建议你把你的 Rust Harness 也暴露成 MCP Server。

Codex 文档明确说 MCP 可以把模型连接到工具和上下文，Codex CLI 和 IDE extension 都支持 MCP servers。([OpenAI开发者][3]) Copilot 也有 MCP 支持，GitHub 文档说 Copilot CLI 支持本地和远程 MCP servers。([GitHub Docs][8])

所以你的系统可以提供一个本地 MCP server：

```text
rust-context-mcp
```

里面提供这些工具：

```text
get_repo_map()
get_crate_graph()
get_module_summary(path)
search_symbols(query)
find_definition(symbol_or_path)
find_references(symbol_or_path)
find_trait_impls(trait_name)
find_callers(function_name)
find_tests_for_symbol(symbol)
get_relevant_context(task_description)
get_impact_analysis(change_plan)
get_validation_commands()
read_file_spans(file, ranges)
```

这样下游 agent 的工作方式就会从：

```text
请阅读我塞给你的 30,000 token 上下文
```

变成：

```text
这是任务 brief。
如果你需要更多信息，请调用 rust-context-mcp 的工具。
```

这比单纯塞文档强很多。

## 6. MD + XML 仍然有价值，但应该是“入口 brief”，不是全部上下文

你生成的 MD + XML 最适合做成一个短的任务入口文件。

例如：

```markdown
# Task Brief

<task>
用户想把登录模块的 token 过期逻辑从固定时间改成配置驱动。
</task>

<repo_snapshot>
git_sha: abc123
branch: feature/auth-config
workspace_type: cargo workspace
primary_crates:
- crates/api
- crates/auth
- crates/config
</repo_snapshot>

<likely_relevant_files>
- crates/auth/src/token.rs
- crates/auth/src/session.rs
- crates/api/src/routes/login.rs
- crates/config/src/lib.rs
- crates/auth/tests/token_expiry.rs
</likely_relevant_files>

<important_symbols>
- auth::token::TokenClaims
- auth::token::validate_token
- auth::session::SessionManager
- config::AuthConfig
</important_symbols>

<constraints>
- Do not introduce unwrap().
- Preserve public API unless necessary.
- Add or update tests.
- Run cargo fmt, cargo check, and relevant auth tests.
</constraints>

<verification>
Recommended commands:
- cargo fmt --check
- cargo check --all-targets
- cargo test -p auth
</verification>

<instruction_to_agent>
Treat this context as a navigation aid, not as ground truth.
Before editing, read the listed files and verify the relevant symbols.
Use rust-context-mcp tools if more context is needed.
</instruction_to_agent>
```

这种格式非常适合高级 agent。

它不只是告诉模型“项目是什么”，而是告诉模型：

```text
你应该先看哪里
哪些符号重要
不要做什么
怎么验证
如果不够该怎么查
```

这比普通 RAG 摘要有用得多。

## 7. 不建议一开始就把所有 repo map 全塞进去

这个地方很容易踩坑。

很多团队做 AI coding agent 的第一个错误就是：

```text
我们有 repo map
我们有符号索引
我们有 RAG
那就全部塞给模型
```

这会让高级模型上下文爆炸，而且注意力被稀释。

更好的方式是三层上下文：

```text
第一层：任务 brief
第二层：相关文件 / 符号 / 影响面
第三层：可查询工具
```

也就是：

```text
默认给 2,000 - 6,000 tokens 的高质量 brief
必要时附加 10,000 - 30,000 tokens 的相关片段
更多信息通过 MCP / CLI 工具按需查
```

对于大型项目，**少而准的上下文比多而乱的上下文强**。

Codex 官方最佳实践里也强调，`AGENTS.md` 应该包含 repo 布局、运行方式、build/test/lint 命令、工程约定、约束和完成标准；同时也提醒短而准确的 `AGENTS.md` 比冗长模糊的规则更有用。([OpenAI开发者][9])

所以你生成的上下文包也应该遵循这个原则：

```text
短
准
可验证
可跳转
可按需扩展
```

## 8. 你应该把产物分成四类

我建议你的系统每次任务生成一个目录：

```text
.ai/tasks/<task_id>/
  brief.md
  repo_map.md
  relevant_spans.json
  symbols.json
  references.json
  impact.md
  validation.md
  agent_prompt.md
```

### 第一类：给模型直接读的

```text
brief.md
agent_prompt.md
impact.md
validation.md
```

这些用自然语言 + XML 标签。

### 第二类：给工具读的

```text
symbols.json
references.json
relevant_spans.json
crate_graph.json
```

这些不要写成 MD，应该是结构化 JSON。

### 第三类：给下游 CLI 读取的项目规则

根据不同 agent 生成不同入口。

Codex 可以用：

```text
AGENTS.md
```

Codex 官方文档说它会在开始工作前读取 `AGENTS.md`，并且可以按全局、项目、子目录层级合并规则。([OpenAI开发者][2])

Claude Code 可以用：

```text
CLAUDE.md
```

Claude Code 文档里也有 memory / `CLAUDE.md` 相关机制，会把项目记忆和规则作为上下文来源。([Claude API Docs][10])

Copilot 可以用：

```text
.github/copilot-instructions.md
```

或者直接通过 CLI prompt / skills / MCP 给上下文。

### 第四类：给下游 agent 动态查的工具

```text
MCP server
```

这是最关键的护城河。

## 9. 你的本地大模型应该做什么？

你的本地大模型不一定要比 Claude / GPT 更会写代码。它应该专注在这几个低成本但高价值的任务上：

```text
理解用户需求
判断任务类型
决定需要哪些上下文
压缩工具产出的事实
生成任务 brief
生成 agent prompt
选择调用哪个高级 CLI
判断修改风险
审查最终 diff
```

比如用户说：

```text
帮我把订单状态机重构一下，支持退款中状态
```

你的本地模型应该先判断：

```text
任务类型：业务逻辑重构
语言：Rust
可能涉及：
- order state enum
- transition validation
- database serialization
- API schema
- tests
风险：中高
建议下游 agent：Claude Code 或 Codex，高 reasoning
需要上下文：
- enum 定义
- match 分支
- 状态迁移函数
- DB model
- API DTO
- 所有相关测试
```

然后你的确定性工具负责找出真实文件和符号。

本地模型负责把这些整理成：

```text
高级模型可执行的作战地图
```

这很有价值。

## 10. 高级模型应该做什么？

高级模型应该负责：

```text
真正的代码修改
复杂推理
跨文件重构
根据编译错误修复
补测试
处理边界情况
```

也就是说：

```text

高级模型：高级工程师
下游 CLI Harness：工程师的手脚
你的 Validator：质检员
```

这个分工非常清晰。

## 11. 你的流程里最值得保留的部分

我认为这几件事非常值得做：

```text
1. 用本地模型理解用户需求
2. 用 Rust 专用工具生成 repo map
3. 用 rust-analyzer 做符号索引
4. 用 cargo metadata 做 crate / workspace 依赖图
5. 用 RAG 找语义相关代码
6. 用 MD + XML 生成高级模型可读上下文
7. 让高级 CLI 自己再跑一遍 Agent Harness
8. 用本地 validator 审查最终修改
```

尤其是第 7 点：

> **不要阻止高级 CLI 自己再探索项目。**

你的上下文应该是“减少探索成本”，不是“替代探索”。

也就是说，不要对高级模型说：

```text
这是完整上下文，直接按这个改。
```

而应该说：

```text
这是高置信度导航上下文。请先验证关键文件，再修改。
```

这会安全很多。

## 12. 你的流程里我会修改的部分

### 修改一：不要叫“死工具”，要叫 deterministic tools

你说“我们写好的死工具”，这个方向是对的，但产品上应该把它们设计成：

```text
deterministic analyzers
deterministic context providers
Rust static analysis tools
```

它们应该输出可审计事实：

```json
{
  "symbol": "auth::token::validate_token",
  "defined_at": "crates/auth/src/token.rs:42",
  "references": [
    "crates/api/src/routes/login.rs:88",
    "crates/auth/tests/token.rs:17"
  ],
  "confidence": "tool_verified",
  "source": "rust-analyzer"
}
```

而不是输出模糊描述：

```text
validate_token 好像在 auth 模块里被 login 调用了。
```

---

### 修改二：不要只生成一个大文档

不要这样：

```text
context.md  80,000 tokens
```

要这样：

```text
brief.md                 入口摘要
repo_map.md              项目地图
symbols.json             符号事实
references.json          引用事实
relevant_spans.md        关键代码片段
validation.md            验证命令
mcp://rust-context       动态查询入口
```

---

### 修改三：不要让下游 agent 修改你的索引产物

你的 `.ai/tasks/<task_id>/` 目录应该默认只读，或者放在临时目录，不要让下游 agent 把它当项目源码乱改。

下游 agent 应该改：

```text
src/
crates/
tests/
Cargo.toml
```

不应该改：

```text
.ai/tasks/<task_id>/symbols.json
.ai/tasks/<task_id>/repo_map.md
```

除非你明确允许它更新上下文。

---

### 修改四：所有下游修改都应该在 worktree / sandbox 里执行

因为你会同时集成 Codex、Claude Code、Copilot CLI，很容易出现多个 agent 改同一批文件的冲突。

Codex app 文档里也提到内置 worktree 和 Git 功能，用来隔离并行代码修改。([OpenAI开发者][11])

你自己的 app 也应该默认：

```text
每个任务一个 git worktree
每个 agent 一个 branch
每次执行前记录 git status
每次执行后保存 diff
失败可回滚
```

推荐：

```bash
git worktree add ../repo-task-123 -b ai/task-123
```

然后让 Codex / Claude / Copilot 在这个 worktree 里执行。

## 13. 你可以做一个“Agent Router”

因为你已经集成了 Codex、Claude Code、Copilot CLI，又有自研模型，所以可以加一个路由层。

例如：

```text
简单局部修改：
  你的本地模型 + 本地 Harness 直接完成

中等 Rust 修改：
  你的本地 Harness 生成上下文
  调 Codex CLI / Claude Code

大型跨模块重构：
  先用你的本地 Harness 做影响面分析
  再交给 Claude Code / Codex
  最后用另一个 agent review

GitHub issue / PR 类型任务：
  交给 Copilot / Codex cloud / GitHub 集成

只读分析任务：
  本地模型 + repo map + RAG 即可
```

也就是：

```text
Task Router
├── Local-only
├── Local + Codex
├── Local + Claude Code
├── Local + Copilot CLI
├── Multi-agent review
└── Human approval required
```

这会让你的产品比单纯“包一层 CLI”强很多。

```text
- module graph

P2:
- tree-sitter AST
- call graph
- trait impl graph
- test impact analysis
- RAG 语义搜索

P3:
- MCP server
- agent router
- worktree execution
- automated validation
- diff reviewer
- feedback memory
```

最小可行闭环是：

```text
用户请求
-> 找相关文件和符号
-> 生成 brief
-> 调下游 CLI
-> 跑测试
-> 生成 diff 报告
```

只要这个闭环打通，你就有产品雏形。

## 15. 你生成给高级模型的 prompt 应该这么写

可以用这种模板：

```markdown
You are working inside a Rust repository.

<role>
You are the implementation agent. A local Rust analysis harness has prepared context for you.
Use it as a navigation aid, not as ground truth.
Before editing, verify important facts by reading the actual files.
</role>

<user_request>
{{用户原始需求}}
</user_request>

<interpreted_task>
{{本地模型对需求的解释}}
</interpreted_task>

<repo_snapshot>
- git_sha: {{sha}}
- branch: {{branch}}
- workspace_root: {{root}}
- rust_toolchain: {{toolchain}}
</repo_snapshot>

<context_files>
- .ai/tasks/{{task_id}}/brief.md
- .ai/tasks/{{task_id}}/repo_map.md
- .ai/tasks/{{task_id}}/relevant_spans.md
- .ai/tasks/{{task_id}}/impact.md
- .ai/tasks/{{task_id}}/validation.md
</context_files>

<important_rules>
- Do not rely solely on summaries.
- Read the actual source files before editing.
- Prefer minimal, high-confidence changes.
- Preserve public APIs unless the task requires changing them.
- Add or update tests when behavior changes.
- Do not touch secrets or production configuration.
</important_rules>

<recommended_workflow>
1. Read the task brief.
2. Inspect the listed files and symbols.
3. Make a short plan.
4. Edit code.
5. Run cargo fmt.
6. Run cargo check.
7. Run relevant tests.
8. Review git diff.
9. Summarize changes and remaining risks.
</recommended_workflow>
```

这比直接说“帮我改代码”强很多。

## 17. 我对你这套流程的最终评价

我的判断是：

> **这套流程方向正确，而且很适合你已经集成多个 CLI agent 的现状。**

但我建议你把它从：

```text
本地模型 + 工具 -> 生成大文档 -> 发给高级模型
```

升级成：

```text
本地模型 + 确定性 Rust 工具
  -> 生成短 brief + 结构化索引
  -> 暴露 MCP 查询工具
  -> 注入下游 CLI 的项目规则
  -> 下游高级 agent 在 worktree 里执行
  -> 你的 validator 做最终验收
```

最核心的一句话：

> **你的系统不要试图替代 Codex / Claude Code / Copilot CLI 的 Agent Harness；你应该做它们前面的“Rust 项目情报层”和“任务上下文编译层”。**

这样你既能利用高级模型已有的执行能力，又能形成自己的差异化能力。
