# APK 记录二次打开缓存

能力：`android_wechat_record_cache_reopen_v2`。仅修改 Android 记录阅读器，不改微信、代理核心、群消息或 PC 缓存协议。

## 根因

旧版已有磁盘缓存，但每次命中仍同步等待网络 304。`ChatRecordCache.read` 在全局锁内执行网络请求，一个旧页面的视频下载可以阻塞新页面正文。正文、媒体与视频解码还共用单线程；关闭页面只调用 shutdown，队列和网络请求并未取消。因此“本地已有文件”并不等于“二次打开无需等待”。

## 当前规则

- 最近 5 分钟成功经服务器验证的正文先从本地显示，再后台条件请求。时间从成功 200/304 起算，本地读取不延长权限窗口；系统时钟回退不视为新鲜。
- 超过 5 分钟必须先复核权限；正文独立客户端连接超时 5 秒、整次请求上限 8 秒。网络失败只能保留仍在上述短窗口内的缓存；401/403/404 立即清除当前记录缓存和已显示正文。
- 这是明确的短期权限租约，不承诺远端撤回瞬间同步到离线设备。不会永久展示未经重新验证的撤回记录。PC/PWA 继续每次复核，不受此 Android 策略影响。
- 缓存按服务器、账号、登录会话及记录隔离；磁盘名称仅用摘要，不保存 token。旧缓存命名与新记录级范围不同，升级后的首次查看需要重新取一次。
- 网络不持有全局磁盘锁；正文和媒体各自排队，媒体最多 2 个任务，同附件请求合并。关闭页面取消 HTTP 调用并中止队列；过期回调不能修改新页面。
- 内容未变化时不重建列表，保留当前图片和滚动位置。已授权记录的本地附件可复用，无需每张图片重复等待网络。缓存包含正文、图片、视频、缩略图和元数据，不是每次重新下载 ZIP。
- 总量 128 MiB，按最久未使用优先回收，7 天未使用条目在写入、缩略图生成或统计时清理；媒体和元数据一起回收。不增加后台定时轮询。
- 右上角“更多 → 缓存管理”显示当前/全部大小，可确认后清理当前或全部。管理使用独立存储队列，不等待媒体下载或正文校验。清理不删除群消息、导入草稿或登录信息；退出登录清理记录缓存。代次校验防止清理后的在途请求重新写回。登录会话或服务器变化时结束加载并清空正文，不再静默丢弃回调而一直转圈。

## 验证

- 26 项 Android 定向测试通过，包含 ZIP/卡片/展示回归、缓存完整性和账号隔离、5 分钟边界、304 续期、阻塞媒体不挡正文、撤回范围、容量/老化、清理与下载/缩略图竞争。
- 真实环回 HTTP + ReaderModel 测试：第二次请求被服务端阻塞时正文已显示；403 到达后正文清空；关闭 API 不用等待服务端即取消阻塞请求；校验中会话变化终止加载；校验阻塞期间仍可查询及清理缓存。
- Debug APK 已构建。上述 JVM/HTTP 证据不等同于真机耗时或正式安装结果；正式交付结果在此报告后续追加。
- 真机只读语义工具 `ChatRecordUiAcceptance` 支持打开指定群、记录、重复打开和缓存管理检查，只输出状态及可访问树就绪时间，不导出聊天内容。`ChatRecordReader` 日志仅包含 local/validated 与相对毫秒数，不包含记录、账号或 URL。
- 用户打开目标记录后，旧版 1.1.1830 二次打开可访问树就绪耗时 1095 ms。本次正常网络未复现用户此前的长时间卡住，不能以此宣称原卡顿已在真机重现或计算加速比。
