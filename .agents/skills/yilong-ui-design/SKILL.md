Trigger when a developer asks Codex Desktop to create or modify visible Android UI, supplies a UI sketch or annotated screenshot, says spacing/color/size/typography/layout should change, or asks to fit the app to a design. Do not trigger for click behavior, networking, data, permissions, business logic, or nonvisual bugs unless the request also contains a visual UI change.

# Yilong UI design workflow

1. For repository write tasks, complete the project's preflight first and bind the MCP project root to the returned `EDIT_ROOT`; no UI import, `.elon` artifact, source edit, build, commit, or publish may target the sync-only main checkout.
2. Use the `yilong_ui_live` MCP before repository-wide reading or source edits. For PWA work, discover and prefer `ui_capture_pwa_runtime`: bind the session to `EDIT_ROOT`, pass a local/project-approved absolute URL, fixed viewport, wait/capture scope, safe source/route revisions, and only an `authProfile` label when authentication was explicitly prepared. Treat its PNG path, SHA-256, dimensions, sanitized route, browser identity and cleanup metadata as the real pixel proof; never substitute a DOM/CSS summary or require Codex Desktop Browser. If it returns a machine-readable diagnostic, follow `nextStep` and never report a login page as success. If only `ui_bridge_*` tools are visible, call `ui_bridge_status` and `ui_bridge_reconnect`; do not silently degrade to repository scanning or manual ADB. After reconnection use the refreshed tools, or `ui_bridge_proxy` if the desktop client has not refreshed them yet. If the client exposes no callable bridge tool and a shell fallback is unavoidable, write arguments as a UTF-8 JSON file and use `node scripts/call-yilong-ui-mcp.mjs`; never pipe JSON through Windows PowerShell 5.1 because it can silently replace Chinese text with `?`.
3. If the request includes local images, call `ui_import_desktop_task` with the user request and absolute image paths. Preserve whether each image is a clean target, an annotated request, a current screenshot, or a style reference.
4. Call `ui_get_design_task` and bind a `TARGET_DESIGN` attachment with `ui_bind_target_design`. Then call `ui_get_project_profile`, `ui_get_runtime_status`, and `ui_check_capabilities`. Normally omit `requiredCapabilities`; when supplied it only adds requirements and can never remove capabilities derived from the structured task or project parity policy.
5. Treat `TRANSPORT_UNAVAILABLE` as a bridge/runtime recovery state, `PREPARATION_REQUIRED` as renderer preparation, and only a proven inability to represent, render, measure, commit, or verify as `PLATFORM_GAP`.
6. For an existing screen, use the smallest runtime node/subtree and local FitRun tools. For a new screen, create the Preview-first skeleton, compile once, prepare the real renderer, then fit.
   For ordinary visual UI work, call `ui_verify_with_fallback` with a 60-second physical-device budget, `fastFailPhysicalVisualProbe=true`, `fallbackToEmulator=true`, and `autoStartEmulator=true`. One failed availability/visual probe, a lock screen/AOD/notification shade, an authorization or install prompt, or a Runtime preparation failure/timeout ends the physical attempt; acquire a specific idle emulator slot and continue unattended. Do not spend the task repairing ADB. Set `realDeviceRequired=true` and disable fallback for OEM, permission, keyboard, launcher, hardware, sensor, Bluetooth, camera, performance, or other device-specific acceptance.
   Never select the first online emulator blindly. Every build/install/start/click/frame/FitRun chain stays on the returned `sessionId`, `deviceIdentity`, `rendererResourceId`, and lease evidence. A busy renderer is unavailable; another idle slot may run in parallel. Emulator proof is accepted only when package, generation, source revision/fingerprint, Runtime build and zero-Patch proof all agree. Report `REAL_DEVICE_STATUS` and `ANDROID_RENDERER`; a deferred real-phone check is a user follow-up, not a blocker for ordinary visual acceptance.
7. Let `ui_start_fit_run` perform numeric trials locally. Use Codex source edits only for structure, missing bindings, or unsupported properties.
8. Accept a candidate only after deterministic/source write-back and patch-free build verification pass. For PWA, retain the real iframe route/source-revision check and associate the `ui_capture_pwa_runtime` PNG with the same route/revision; context packs pass only its path/hash metadata and never embed Base64 by default. Keep inspected, path-sanitized `.elon/ui-standards/fit-cases.v1.json` and `fit-priors.v1.json` changes as durable project learning in the task commit; their generated `*.json.bak` recovery copies are local ignored output. A clean target normally requires an `ACCEPTED` FitRun, and APK/Web parity requires the cross-platform visual verification artifact named by the gate.
9. If `ui_check_capabilities` or a FitRun proves the workbench itself lacks a required capability, classify it before calling `ui_report_capability_gap`: use `DELIVERY_BLOCKING` when the requested UI cannot yet be represented, rendered, measured, written, or verified; use `DELIVERY_NON_BLOCKING` only when the requested UI source and fresh patch-free Runtime proof already pass the visual thresholds and the gap affects platform efficiency, automation, resilience, or future reuse. Do not bypass the workbench with an untracked workaround.
10. A business UI task always reports a gap with `executionMode=BUSINESS_THREAD` and its current Codex `originThreadId`. It must never call `START_UPGRADE`, edit platform source, publish the node agent, or wait for platform evolution in that task. Commit and push the final business source first, establish the final Runtime/source proof on that stable revision, then report a non-blocking gap so its evidence cannot become stale.
11. For `DELIVERY_NON_BLOCKING`, call `ui_check_workflow_completion` and require `businessDeliveryReady=true`; `completionReady` intentionally stays false while evolution is pending. Finish the business repository workflow normally and report the UI result immediately. Then use Codex Desktop project tools (`list_projects`, then `create_thread` with `environment=worktree`) to create the user-visible background task from `threadHandoff`; the project owner has explicitly authorized this automatic handoff. Do not wait for it and do not replace it with a hidden subagent. If thread creation fails, business delivery remains valid but the final report must expose the pending gap and exact handoff payload.
12. For `DELIVERY_BLOCKING`, create the same independent Worktree evolution task immediately, leave the original UI task paused, and return its link. The original task resumes only after the evolution task reports success; it must not hold the user conversation open while doing platform work.
13. An evolution task recreates the gap with the supplied `executionMode=EVOLUTION_THREAD`, `deliveryImpact=EVOLUTION_ONLY`, and `originGapId`, then follows `APPROVED -> UPGRADING -> PUBLISHED -> COMPLETED`. It makes the smallest platform change, follows repository commit/push/publish rules, reports revision/commit/version/files, reconnects the MCP, rechecks, sends the outcome to `originThreadId`, and never redoes the business UI.
14. Background evolution has lower priority than foreground UI. Before taking a real Android renderer/device lease, publishing the node agent, or restarting it, inspect active project tasks; while a foreground UI task is active, wait without holding shared resources. Stop for device authorization instead of creating debug-suffix retry loops. Publishing platform evolution alone never changes the original business acceptance result.
15. Before any final UI report, call `ui_check_workflow_completion`. Copy its evidence and report `FIT_RUN_STATUS`, `FINAL_VISUAL_LOSS`, `VISUAL_ACCEPTANCE_THRESHOLD`, `CROSS_PLATFORM_VISUAL_PARITY`, `BUSINESS_DELIVERY_READY`, `PLATFORM_EVOLUTION_PENDING`, and `EVOLUTION_THREAD`; then report repository finish fields separately: `BUSINESS_STATUS`, `LOCAL_MAIN_STATUS`, `TASK_WORKTREE_STATUS`, `MAIN_UNTRACKED_STATUS`, and `FINALIZABLE`. Do not treat unrelated repositories or arbitrary paths as trusted. Stop when a circuit breaker moves an evolution gap to `HUMAN_REQUIRED`, or when product/security judgment is required.

Read [references/platform-gap.md](references/platform-gap.md) only after a platform capability gap is reported.
