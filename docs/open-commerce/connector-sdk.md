# 开放商业连接器 SDK

本文定义厂商数据如何进入商户自有数据边界，以及连接器兼容性测试如何阻止“登记了平台名称就宣称已经接通”的错误。

## 目标

连接器 SDK 统一四类接入来源：

1. 官方 API。
2. 商户授权导出。
3. 商户本机适配器。
4. 人工导入。

这些来源必须输出相同的健康证据、分页变更和同步回执。具体平台可以采用不同授权方式，但不能改变开放商业的 Merchant、Integration、Capability 和 Invocation 主干。

同一 SDK 还提供衔接任务客户端，把已经形成的商户业务证据安全交给真实 ERP/CRM 适配器。任务客户端与数据同步契约相互独立：同步解决“外部数据如何进入商户边界”，衔接租约解决“平台终态业务结果如何由指定机器接手处理”。

## 运行边界

```text
平台 / POS / 文件
  -> Connector.describe / health / sync
  -> 商户选择的数据存储
  -> 有界 Sync Receipt
  -> Integration 健康状态
  -> Capability 对外暴露最小能力
```

原始订单、客户、财务和库存值不写入一龙的同步回执。控制面只保存扫描数量、变更数量、游标摘要、状态、错误代码和时间证据。连接器凭据只能存在于服务器或节点凭据存储中，不进入 Manifest、AI 开发上下文或审计元数据。

## 兼容性门禁

`sdk/open-commerce-connector` 提供无第三方依赖的 Node.js SDK 和兼容性测试。连接器进入试点前至少证明：

- Manifest 使用当前 `open_commerce.connector.v1` 契约。
- 单页不超过 500 条变更。
- 相同 `runKey` 重放得到相同同步回执。
- 回执不包含原始经营值。
- Manifest、健康证据和回执不存在 Token、Cookie、密码和 API Key 字段。
- 健康状态有明确时间与证据代码。

通过兼容性测试只代表技术契约合格。官方授权、字段完整性、限流、风控、长期稳定性和平台条款仍需针对每个适配器单独验收。

## 衔接租约客户端

`createAdapterHandoffClient` 封装领取、续租、完成和主动释放四个机器入口。它强制 60–900 秒租约、把续租限制在首次领取后 1 小时硬期限内、限定释放原因、限制响应体为 256 KiB，并对非本机地址强制 HTTPS。调用方只提供一次性机器 Token；项目、商户和接入器边界不进入请求体，防止适配器冒充其他商户。

只有显式包含 `business_handoff.claim` 的凭据可领取任务。SDK 不保存 Token 或租约密钥，也不会自动把处理器异常伪装成完成；调用方应在真实 ERP 写入成功后提交 `applied`，明确忽略或拒绝时提交对应回执，临时故障则主动释放等待重试。

`createAdapterHandoffWorker` 在同一客户端之上提供顺序执行的通用工作器：自动领取与续租、向商户处理器传入 Invocation 级稳定幂等键、生成稳定回执键、重试完成请求，并在临时故障或进程停机时释放任务。它只消除每个商户重复实现租约协议的成本，不替代 ERP 自身的事务、幂等和权限校验，也不内置任何大厂凭据。

## 商户可携带身份

`createMerchantIdentityProof` 使用商户本地 RSA 私钥，生成绑定项目 ID、商户 ID 和 SPKI SHA-256 指纹的持有证明。`verifyMerchantIdentityProof` 可在上传前本地复核。SDK 不生成、保存或上传私钥；密钥生命周期始终属于商户。

公钥指纹用于跨环境对比“是否持有同一私钥”，不是工商认证，不会自动合并商户、恢复授权或代替人工确认。

## 开发者 Webhook 验签

`verifyDeveloperWebhookSignature` 使用一次性展示的 `whsec_` 密钥，对 `x-yilong-webhook-timestamp + "." + 原始请求体` 执行 HMAC-SHA256 验证，并以常量时间比较签名。接收端必须先读取并保留原始请求字节，完成签名与时间偏差检查后再解析 JSON；不要对重新序列化后的对象验签。

Webhook 负载只携带终态事件摘要。完整结果仍通过 App 自己的测试 Token 查询。验签成功只证明请求由持有当前订阅密钥的平台实例发出，不证明真实支付、履约、ERP 入库或跨运营方身份。

新订阅首次激活前会收到 `open_commerce.developer_webhook_verification.v1` 负载。接收端使用相同方式验证签名后，可调用 `createDeveloperWebhookVerificationResponse` 生成原样回显的 JSON。只有验证成功后的事件才会进入该订阅；创建到验证之间的历史继续通过终态事件轮询接口恢复。

订阅密钥可以显式轮换。轮换后旧密钥立即失效，订阅回到待验证状态，接收端必须保存本次唯一显示的新密钥并重新完成 challenge。SDK 不推导或保存密钥版本；接收端应把平台返回的 `whsec_` 值作为不透明凭据管理。

自动重试耗尽后的死信可由 App 所有者显式重新排队。重试沿用原投递 ID 和调用 ID，不代表订单或支付重新执行；接收端必须继续执行幂等去重，并通过终态结果查询接口读取当前结果。

创建订阅时可以固定选择成功事件、失败事件或两者。未选择的终态事件不会创建投递；V1 不支持原地扩展筛选范围，需要新建并验证订阅后再停用旧订阅。

## 服务端发现

第三方开发者可调用：

```http
GET /api/open-commerce/connector-contract
```

响应包含契约版本、限制、允许状态和控制面端点。SDK 常量必须与该端点保持一致；升级破坏性契约时应发布新的 schema 和 SDK 主版本，不静默改变 V1 行为。
