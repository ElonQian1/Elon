# 开放商业开发者签名 Webhook V1 验收

## 当前状态

`verified_local_store_and_http_subset`

Rust 服务端已编译，并在全新临时 SQLite 数据库上执行到当前迁移版本。2 项存储专项验证了订阅验证前失败关闭、App 与事件范围隔离、终态入队、单租约领取、死信确认、人工重试和成功完成；另有 6 项进程内 Axum 专项验证 App 所有者双重边界、列表/健康/投递读取、停用与幂等停用、死信确认与人工重试、最多 100 条的历史补发，以及创建、启用、验证和轮换在权限或前置状态不足时失败关闭且不泄露密钥。真实 HTTPS 外呼、历史库升级、并发压力和 PC 页面仍未验证。

## 本批验证结果

- 修复创建、启停、验证和密钥轮换在提交事务后再次获取同一 SQLite 互斥锁导致的自锁。
- 成功专用订阅只接收本 App 的匹配沙箱终态事件，验证前历史、其他 App 和失败专用订阅不产生该成功投递。
- 同一投递只能由一个租约领取；死信确认不可覆盖，人工重试会清除确认并复用原投递 ID，成功完成后旧租约失败关闭。
- Webhook 管理 HTTP 要求调用者同时具备项目编辑权和 App 所有权；项目 owner、其他编辑者、普通成员、项目外用户及未加入项目的平台管理员均不能读取或管理该 App 的订阅。
- 列表、健康、投递、停用和失败响应不返回完整签名密钥或开发者 Token；无效创建不增加订阅，待验证订阅不能启用，不具备生产资格的订阅不能轮换密钥且版本不变化。
- 死信确认绑定 App、订阅和投递；无效理由及跨订阅确认不改变状态，同一理由可幂等重试，不同理由不能覆盖已固定证据。确认后的人工重试会清除确认、复用原投递 ID 并只增加一次重试计数，`pending` 投递不能重复排队。
- 历史补发要求项目编辑权与精确 App 所有权，拒绝负游标、0 条、超过 100 条及跨 App 订阅；合法请求按终态序号分页，重复请求只报告既有投递，不重复入队或混入其他 App 的事件。

## 已形成代码

- V145 订阅表、投递表、唯一约束、到期租约恢复索引和终态事件触发器。
- 项目编辑者与 App 所有者双重边界，以及每个 App 最多 5 个订阅。
- HTTPS、精确主机白名单、无账号/查询/片段和禁止重定向的外呼边界。
- 由主密钥派生且只显示一次的订阅签名密钥；服务端数据库不保存原始密钥。
- App 终态摘要签名投递、30 秒领取租约、指数退避、最多 8 次、死信和自动停用。
- App 停用时同步停止订阅；订阅重新启用不补发停用期间历史事件。
- PC 开发者门户的 App 选择、订阅创建、一次性密钥展示、启停和最近投递列表。
- Node SDK 的原始请求体 HMAC 验签、时间偏差检查和常量时间比较。
- V156 已另行形成环境绑定生产订阅代码；本文件其余条目仍需和新环境边界一起统一回归。
