# 模块化功能交付闭环

把需求从真实现状推进到可验证、可交付、可继续维护的结果。先遵守项目权威规则，再用本 Skill 编排完整生命周期。

用户说“请使用模块化功能交付闭环”时，按本流程执行。显式调用名为 `$deliver-feature-end-to-end`。

## 组合而非替代

- 本 Skill 负责任务认领、能力基线、实现、验证、发布、验收和证据收尾。
- 领域 Skill 负责专项细节；Android WebView 使用 `$android-webview-feature-delivery`，大型文件治理使用 `$modular-long-term-dev`。
- 项目内 `AGENTS.md`、发布脚本、安全规则和完成合同始终优先。
- 对一行修复、只读分析或用户明确要求不发布的任务，按风险缩小流程，不强制制造无关步骤。

## 1. 定义真实完成条件

1. 确认用户要完成的真实工作流，而不只复述页面、接口或文件名称。
2. 写清范围、非目标、约束、数据安全、兼容要求和是否需要发布。
3. 从当前代码、配置、数据库、线上行为或设备状态取证；不要用旧结论代替低成本的当前验证。
4. 为每个用户可观察能力写出验收条件和失败表现。
5. Bug 修复先复现并沿输入、领域逻辑、持久化、输出和用户界面定位失败层。
6. 重构、迁移或替换数据源时先记录旧能力基线、输入输出合同和回滚路径；功能等价前不删除旧路径。

## 2. 认领边界并查重

1. 读取当前 Goal、最新任务消息、活动 worktree、Git 状态和相关近期提交。
2. 比较具体文件、符号、协议、数据库对象和 Git 祖先关系，不用“两个任务名字相似”判断重复。
3. 已进入当前基线的能力作为可复用基础，不重复实现。
4. 其他任务尚未提交的同一符号或同一所有权边界由原任务继续负责；发送交接信息后再处理不相交部分。
5. 边界无法分开时停止编辑该区域，不覆盖、不回退、不顺手提交来源不明的改动。
6. 按项目流程创建隔离 worktree；主工作区只作为同步基线。

## 3. 建立交付矩阵

为每项能力独立记录：

- `implementation_status`
- `verification_status`
- `delivery_status`
- `acceptance_status`
- `owner` 与模块边界
- 当前证据、剩余缺口和下一动作

不要把编译通过当成用户验收，不要把环境缺失当成代码缺失，也不要把代码已推送当成已经部署。详细状态词和模板见 [references/delivery-matrix.md](references/delivery-matrix.md)。

## 4. 设计完整纵向切片

沿真实链路设计：输入或触发 -> 解析与验证 -> 领域服务 -> 存储或外部适配 -> API/事件 -> UI/消费者 -> 可观测性与恢复。

- 入口只做组装、路由和依赖连接。
- 按领域责任拆分模块，不建立无边界的 `utils`、`common` 或巨型 `manager`。
- adapter 只负责外部合同转换；manager 或 service 负责调度、优先级、状态和策略。
- 使用稳定、版本化的内部合同隔离外部变化。
- 对写操作提供幂等键、明确状态机、重试语义和可审计结果。
- 数据库迁移和修复脚本可重复执行，并有升级和回退边界。
- 简单来源优先配置化，复杂来源才写专用 adapter，但统一注册和管理。
- 未覆盖能力必须显式降级、回退或报告，不能静默丢字段、丢状态或伪造成功。

## 5. 发布编辑计划

编辑前列出：

- 新建和修改文件
- 每个文件的责任和预计规模
- 是否触碰大型入口、共享协议、迁移或生产路径
- 对应测试和验收用例
- 与并行任务的所有权边界

把工作拆成可独立验证的纵向批次。一次批次应完成一个连贯能力，而不是在多个层留下互不连通的半成品。

## 6. 实现并保护兼容性

1. 先建立失败测试、合同 fixture 或可复现证据，再修实现。
2. 同时覆盖正常、空数据、重复、超时、部分失败、重试和版本变化。
3. 重构时用兼容测试证明旧能力仍存在；字段、状态、API 和 UI 行为不得因统一架构而静默消失。
4. 多源或多实现合并时保留来源身份、优先级、健康状态、错误原因和确定性去重规则。
5. 让错误停留在正确层，并向调度器、日志或用户暴露可行动的结构化原因。
6. 日志、fixture、截图和回执不包含密码、token、Cookie、个人内容或生产敏感数据。

## 7. 按证据阶梯验证

按风险从低到高推进：

1. 格式、语法、静态合同和生成物一致性。
2. 单元测试和模块合同测试。
3. 跨模块、数据库、网络替身或端到端集成测试。
4. 生产构建、安装包或部署工件验证。
5. 目标环境、设备或线上只读 smoke。
6. 用户可见主路径和恢复路径验收。

先跑最小有效验证，再按影响面扩大。长命令使用项目的有日志、有限超时和可恢复执行器；重启前先查询运行状态，禁止因无输出重复启动同一构建或发布。

环境暂不可用时继续完成可离线验证的工作，并把缺口标为 `deferred` 或 `user_action_required`。不能执行的检查要明确报告，不能改写成“已通过”。

## 8. 精确提交与交付

- 只暂存计划内文件，按责任形成可审查提交。
- 使用项目规定的 push、rebase、发布和 finish 流程；只在真实 non-fast-forward 后 rebase。
- 一轮验收绑定一个明确提交和一个工件，记录版本、Git SHA、来源和哈希。
- 本地构建成功不等于发布成功；必须验证真实部署身份、健康状态和用户入口。
- 文档或明确的代码同步任务可不发布，但必须按项目完成合同收尾。

## 9. 按风险分批验收

1. 安全只读：版本、健康、查询、列表、结构化状态和导航。
2. 可逆写入：测试记录、临时配置、可撤销操作；先记录恢复方法，验收后恢复。
3. 敏感或破坏性：登录、付款、删除、生产迁移、余额、权限、真实通知；逐项取得用户授权和监督。

不要为了提高自动化覆盖率降低风险级别。对生产问题优先使用只读取证；已被人工处理的对象不得重复产生副作用。

## 10. 失败时从正确层恢复

- 根据最新证据停在失败层，不从头重复整个流程。
- 代码通过但环境失败时保留工件和日志，修环境后只补环境验收。
- 外部服务变化时先确认合同差异，再更新 adapter 和兼容测试。
- 发布失败时先核对提交、工件、租约和线上版本，避免重复发布。
- 新方案无法保持能力等价时回到兼容路径，不用 UI 掩盖后端或数据错误。

## 11. 用可交接证据收尾

最终报告至少包含：

- 已完成的用户能力和明确未完成项
- 根因或关键架构决策
- 修改文件或模块
- 测试、构建、设备和线上证据
- commit、push、工件和部署身份
- 四类状态及剩余风险
- 主工作区、任务 worktree 和来源不明文件状态
- 下一任务的准确入口、所有权和恢复步骤

只有项目收尾合同允许、所需能力不再是 `partial` 或 `failed`、且强制验收已完成时，才宣告整体完成。否则完成当前批次并保持更大的 Goal 或功能项继续有效。
