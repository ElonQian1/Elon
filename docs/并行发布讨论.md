# 多 AI 代理并行开发——防冲突工作流说明

> 2026-06-09 更新：一龙项目已经改为“代码先进入 `origin/main`，发布跟随服务器和最新主线”的流程。旧的“任务前必须 `git pull --rebase`、Android 版本号提交进 git、发布失败后重新运行脚本”规则已废弃；只有 `git push` 被 non-fast-forward 拒绝时才 rebase 一次。
>
> 2026-06-24 更新：主工作区 `main` 只作为共享同步基线，**即使干净也不再直接编辑业务文件**。所有 AI 代理开始任务先运行 `scripts\ai-task-preflight.ps1 -CreateWorktree` / `scripts/ai-task-preflight.sh --create-worktree`，并切到脚本输出的 `WORKTREE_PATH` 后再修改。本文是历史讨论和背景说明；若与 `AGENTS.md`、`.github/copilot-instructions.md`、`.github/instructions/git-deploy-workflow.instructions.md` 或脚本行为冲突，以权威入口和脚本为准。
>
> 2026-07-14 更新：任务结束统一使用 `finish-ai-task.*`。主工作区普通未跟踪文件与已跟踪基线同步分开处理，不再因为遗留测试/诊断文件让本地 `main` 长期落后。

## 背景与挑战

本项目同一台 PC 上同时运行多个 AI 代理（Copilot、Claude 等），它们会并发修改同一个 Git 仓库。如果没有规则约束，极易发生：

- A 代理的未提交改动被 B 代理的构建打包进去
- 两个代理同时写 versionCode，互相覆盖
- 某代理直接在主工作区构建，导致 `git status` 污染

下面的规则体系用来解决这些问题。

---

## 一、三大核心原则

| 原则 | 含义 |
|---|---|
| **预检建 worktree** | 每次任务开始先运行 `ai-task-preflight -CreateWorktree`，脚本同步本地 `main` 基线并从最新 `origin/main` 派生独立任务 worktree |
| **commit 即 push** | 每次 commit 后立即 push，永不在本地堆积 commit |
| **发布不追车** | 代码 push 成功就是本代理的硬完成；发布被更新 main 超越时交由后续最新 main，不反复重跑 |

### rebase 只由 push 拒绝触发

`origin/main` 前进是多 AI 并行开发的正常现象，不是错误，也不是自动 rebase 条件。合理流程是：

1. 开工前：从当时最新 `origin/main` 派生独立 worktree。
2. 提交后：立即 `git push origin HEAD:main`。
3. 只有 push 被 non-fast-forward 拒绝：才 `git fetch origin` + `git rebase origin/main`，解决冲突后再 push。
4. 自己的 commit 已经进入 `origin/main` 后：任务代码层面完成；后续 `origin/main` 再前进，不应该为了“保持自己是最新 HEAD”反复 rebase。
5. 发布阶段：如果构建产物被更新的 main 超越，停止上传旧产物，汇报“代码已合并，发布交给最新主线”，而不是重跑。

禁止规则：不要因为 `git fetch` 后看到 `origin/main` 前进，就中断当前任务去 rebase；不要因为发布脚本提示被更新 main 超越，就让同一个代理追最新主线重跑。多个代理都这么做会互相追车，导致并行任务活锁。

---

## 二、任务开始——状态检查决策树

每个 AI 代理接到任务后，**动代码前**强制执行仓库脚本，而不是手动 `git fetch` / `git pull`：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\ai-task-preflight.ps1 -CreateWorktree
```

Linux/macOS/服务器 CLI 使用：

```bash
bash scripts/ai-task-preflight.sh --create-worktree
```

根据脚本输出走不同路径：

```
ai-task-preflight
        │
        ├─ WORKTREE_CREATED=true ───► ✅ 切到 WORKTREE_PATH 后再改代码
        │
        ├─ 当前已是干净且未落后的任务 worktree ─► ✅ 可继续当前任务
        │
        └─ 主工作区脏 / 远端变更 / 来源不明 ───► ⚠️ 不在原目录 pull/rebase，使用脚本创建的隔离 worktree
```

---

## 三、并发隔离——独立工作树方案

当前规则下，业务修改默认都进入预检脚本创建的独立 worktree。不要手写分支名、不要在主 `main` 工作区直接编辑，避免不同 AI 代理互相占用。

```powershell
# 1. 让脚本同步 main 基线，并从最新 origin/main 创建本会话专属工作树
powershell -ExecutionPolicy Bypass -File scripts\ai-task-preflight.ps1 -CreateWorktree

# 2. 在脚本输出的 WORKTREE_PATH 中修改代码（完全隔离，不干扰主工作区）
Set-Location "<WORKTREE_PATH>"
# ... 修改文件 ...

# 3. 提交本会话的改动
git status --short
git add <本任务相关文件>
git commit -m "feat(session-<id>): 描述"

# 4. 第一时间把本会话提交推入远端 main
git push origin HEAD:main
# 如被拒绝：git fetch origin; git rebase origin/main; 解决冲突后重推
# 若本轮不发布，到任务末尾运行 finish-ai-task.ps1 -Kind CodePushed
```

**为什么用独立工作树而不是新分支？**  
因为 `git add -p` 只能按 hunk 粒度选择，当两个代理的改动在同一文件同一区域时无法安全拆分。独立工作树从文件系统层面彻底隔离，是唯一可靠方案。

---

## 四、构建部署——临时工作树隔离

代码提交到远程后，**编译和部署默认交给仓库发布脚本**。不要手搓 rsync/scp/build 临时目录，脚本会基于已提交 SHA、发布锁、服务器版本和最新 `origin/main` 做并发保护。原因是：

- 避免构建产物（`target/`、`build/` 等）污染主工作区的 `git status`
- 确保构建基于明确的 commit SHA，不含任何未提交改动
- 多个代理可以同时用不同 SHA 创建各自的临时工作树并行构建

```powershell
git push origin HEAD:main
powershell -ExecutionPolicy Bypass -File scripts\check-task-complete.ps1 -Kind CodePushed

# 后端运行代码变更由脚本发布和验证
powershell -ExecutionPolicy Bypass -File scripts\publish-server.ps1

# Android 用户可见改动默认发布；明确只同步代码的并行任务可跳过
powershell -ExecutionPolicy Bypass -File scripts\publish-apk.ps1 -Changelog "<用户可见改动>"
```

> 发布脚本若发现被更新的 `origin/main` 或服务器版本超越，应汇报“代码已合并，发布交给最新主线”，不要反复 rebase 重跑。

## 五、Android 版本号——服务器原子分配

Android 的 `versionCode` 是整数，必须全局单调递增，多代理并发时最容易冲突。当前解决方案：

**由服务器 `/api/release/claim` 原子分配版本号**，`build.gradle` 里的版本只作为冷启动兜底，不提交进 git。流程如下：

```
代理 A 提交代码改动 → git push origin HEAD:main → CodePushed 通过
    └─► 运行 publish-apk.ps1
            ├─ 服务器 claim 分配 versionCode/versionName
            ├─ 临时写入 build.gradle
            ├─ 编译 + 打包 + 上传 APK
            └─ 还原 build.gradle，不产生 release-only commit
```

**并发冲突防护**：  
若代理 A 和代理 B 同时修改代码，先 push 成功的一方进入 `origin/main`；另一方只有在 push 被拒绝时 rebase 一次再推。已经 push 成功的一方不得因为 B 后续也 push 了更新提交，就回头 rebase 或重跑自己的构建。
若代理 A 和代理 B 同时发布 APK，脚本只允许发布当前最新主线。慢构建如果发现 `origin/main` 或服务器 APK 已前进，就停止上传并汇报“代码已合并，发布交给最新主线”，不要求当前代理重新运行脚本。

```
代理 A: commit #1 push 成功，开始构建 APK
代理 B: commit #2 push 成功，稍后触发/接管最新 main 发布
  ↓
代理 A: 构建完成时发现 origin/main 已包含 Android 新改动 → 停止上传旧 APK
代理 B 或发布协调者: 基于最新 main 发布一次
```

## 六、完整流程图（一次典型任务）

```
任务开始
  │
  ├─ 运行 scripts\ai-task-preflight.ps1 -CreateWorktree
  ├─ 如果 WORKTREE_CREATED=true，切到 WORKTREE_PATH
  ├─ 主工作区 main 只做同步基线，不直接编辑业务文件
  │
  ├─ 修改代码
  ├─ format-rust 脚本（仅本次改动的 .rs 文件）
  ├─ git add（仅自己的文件）
  ├─ git commit
  ├─ git push origin HEAD:main ◄── 必须立即 push
  ├─ [发布前需要时] check-task-complete -Kind CodePushed
  │
  ├─ [后端/前端] 需要发布时运行 publish-server.ps1/.sh
  │       ├─ 脚本 claim 版本
  │       ├─ 编译和上传
  │       ├─ 重启服务
  │       └─ 验证健康检查和 /api/server/version
  │
  └─ [Android] 默认运行 publish-apk.ps1（明确只同步代码时跳过）
          ├─ 服务器 claim 版本号
          ├─ 编译 Rust + Kotlin → APK
          ├─ scp 上传 + 生成 version.json
          └─ 若被更新 main 超越则停止上传，不追车重跑
```

## 七、任务结束清理（防残档）

每次会话结束前运行统一收尾：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\finish-ai-task.ps1 -Kind <Kind>
```

Linux/macOS 使用 `bash scripts/finish-ai-task.sh --kind <Kind>`。它同步已跟踪 `main`、审计未知文件并回收已合并且干净的任务 worktree；来源不明文件不会自动提交或删除。不要把“清理工作流”理解为主动杀终端或删除现场。

---

## 八、关键规则速查

| 规则 | 原因 |
|---|---|
| 任务前运行 `ai-task-preflight -CreateWorktree` | 同步 main 基线，并从最新 `origin/main` 创建隔离任务 worktree |
| 主工作区 `main` 不直接编辑业务文件 | 让多个 AI 代理共享同一个最新基线，避免互相占用 |
| 发布必须走仓库脚本 | 防止构建产物污染主工作区，并使用服务器版本/发布锁做并发保护 |
| commit 后立即 push | 本地 commit = 无备份，磁盘故障即丢失 |
| Android 并发发布被超越→停止上传 | 避免旧 APK 覆盖新提交，发布交给最新主线 |
| 禁止 `git push --force` | 会覆盖他人已推送的提交 |
| 禁止 `cargo fmt`（无参数） | 会格式化 486+ 历史文件，产生大量无关 diff |
