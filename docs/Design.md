# 一龙项目 Design.md

最后更新：2026-08-05

本文是给 AI、设计师和开发者共同使用的项目级设计约束。它不替代 `docs/APP 颜色规范.md`，而是作为更高一层的设计工作流和判断标准：先确定产品气质、组件策略和页面扩展规则，再落到颜色、字号、圆角和具体组件。

如果任务涉及 APP 页面、Web 镜像页面、项目空间、聊天、列表、卡片、导航、弹窗、状态标签或任何视觉调整，必须先读本文，再读 `docs/APP 颜色规范.md`。如果改动 APK UI，还必须按 `.github/instructions/apk-web-ui-sync.instructions.md` 同步检查 Web 镜像页。

## 现有约束结论

本项目已经有 UI 约束，而且不只是颜色约束：

- `docs/APP 颜色规范.md`：实际内容已经升级为完整的 APP UI 设计规范，定义了颜色 token、字体层级、布局栅格、圆角、导航、搜索、筛选、列表、项目广场卡片、项目空间、弹出菜单、悬浮操作、图标、图片、交互状态和可访问性。
- `default-project-docs/files/github/instructions/ui.instructions.md`：提供通用 UI 与交互任务约束，强调信息层级、移动端适配、状态覆盖和优先复用现有组件。
- `.github/instructions/apk-web-ui-sync.instructions.md`：约束 APK UI 与 Web 镜像页面保持同步。

当前缺口是：已有规范偏“执行层”，缺少一份让 AI 在新增页面和扩展产品时使用的“设计 DNA”。本文补齐这个入口。

## 设计定位

一龙项目的主产品体验是一个云端 APK 开发平台：用户通过手机 APK 与 AI 对话，管理项目、发起修改、查看构建与发布结果。界面应该像一个安静、可信、长期使用的项目工作台，而不是营销页、炫技 Demo 或彩色工具箱。

核心风格定义：

- 产品气质：专业、克制、稳定、工程感、移动端优先。
- 视觉基调：深蓝石墨工作台为全局底色；项目广场以更深的近黑虚空、冷白星光和单一青蓝信号构成“深空静默观测站”标志场景。
- 信息表达：让用户清楚知道项目状态、下一步动作和 AI 正在做什么。
- 交互目标：手机用户不需要懂开发，也能安全地发起、跟踪和接收结果。

一句话原则：

> 不让 AI 猜审美；所有新增页面都必须继承一龙 APP 的静谧夜空项目工作台语言。

## 组件策略

### 优先级

1. 优先复用项目已有组件、资源、颜色 token、布局模式和页面结构。
2. 其次参考 `docs/APP 颜色规范.md` 中已经定义的组件形态。
3. 只有现有规范无法表达新需求时，才新增组件或 token。
4. 新增 token 必须先写入规范文档，再进入代码实现。

### UI Kit 使用原则

如果项目某一端已经引入成熟组件库，应优先使用组件库的基础能力，不从零手写通用控件。AI 实现时必须遵守：

- 按钮、输入框、弹窗、列表、导航、标签、开关、菜单优先使用现有组件或系统控件。
- 不为了“看起来高级”新增泛用渐变、光效、装饰背景或复杂嵌套卡片。项目广场可使用规范限定的静态低对比星讯与观测弧线，但不得扩散为其他页面的通用装饰。
- 不混用多个视觉语言差异很大的组件来源。
- 组件库只解决局部一致性；产品气质仍以本文和 `docs/APP 颜色规范.md` 为准。

## 页面设计规则

### 信息层级

每个页面只允许有一个最主要的用户目标。页面结构应按以下顺序组织：

1. 用户当前在哪里。
2. 当前对象是什么，例如项目、会话、发布、成员。
3. 当前状态是什么，例如构建中、需审批、可安装、失败。
4. 用户下一步能做什么。
5. 次要信息和历史记录。

不要把状态、操作、说明、历史和装饰放在同一视觉重量里。标题、状态、主动作、辅助信息必须能一眼区分。

### 页面结构

- 一级页面保持稳定的顶部区域、内容区和悬浮底部导航；底部导航与聊天输入胶囊共用同一底边基准。
- 列表页优先扫描效率，不把每一行都做成重卡片。
- 项目广场、项目详情这类对象页可以使用更明显的卡片和容器。
- 空状态必须给出可执行下一步，不只显示一句说明。
- 错误状态必须说明原因和恢复路径，不只显示失败。
- 加载中、空数据、成功、失败、无权限、离线都要有布局预案。
- 已经成功加载过的对象列表必须缓存优先呈现；页面重入不得先清空有效内容再等待网络。只有首次无缓存且请求超过短延迟时才显示骨架，后台刷新失败应保留旧内容并给出非阻断提示。

### 移动端优先

- 所有关键操作必须适配单手操作和小屏宽度。
- 按钮、标签、卡片标题不得因为中文变长而溢出。
- 点击目标不小于 `48dp x 48dp`。
- 页面底部操作必须避开系统导航栏和安全区。
- 不用桌面端信息密度直接压缩到手机页面。

## 编程工具对话框与审批卡

编程工具里的对话框不是普通提示弹窗，而是 AI 在关键节点请求用户确认风险边界的决策界面。适用范围包括写文件审批、命令审批、依赖安装、Git 操作、任务恢复、终端接管、维护操作确认和冲突解决。

P0 硬规则：

- 审批卡必须先说明将要执行什么，包括写哪些文件、运行什么命令、影响哪个项目、会在哪个工作区生效。
- 删除、覆盖、写文件、执行命令、安装依赖、权限扩大、`git push` 等高风险操作必须确认，不能伪装成普通提示。
- 审批必须提供细节入口，例如查看 diff、查看命令、查看日志、打开文件或跳转任务卡。
- 历史审批、失效审批、任务结束后的审批按钮必须禁用，并说明原因，避免用户批准一个已经不可执行的动作。
- 按钮文案必须是明确动作，例如“批准写入”“拒绝执行”“查看 diff”“基于快照继续”，禁止只写“确定 / 取消”。

P1 规则：

- 默认推荐动作可以突出，但必须允许用户先查看细节或选择更保守路径。
- 文案要工程化：少形容词，直接说明范围、风险、后果和可恢复状态。
- 错误和恢复状态必须说清楚，例如可重连、只能快照继续、已失效、无权限、本机节点离线。
- 不要为低风险信息频繁打断用户；只有继续执行存在代价、风险或分歧时才弹出审批。

暂不在本文细化快捷键、权限记忆粒度和动画样式；这些属于 PC 工作台或具体组件实现规则，只有稳定复用后再沉淀。

## 视觉语言

具体颜色、字号、圆角和组件数值以 `docs/APP 颜色规范.md` 为准。本文只定义更高层的方向。

### 颜色

- `#0B1017` 深蓝石墨画布和 `#111923` / `#172231` 不透明表面承载常规页面结构，不临时新增相近色阶。
- 项目广场是唯一场景化例外：复用 Win 端 `#0C0E12` 暖石墨深画布、`#111318` / `#171A20` 观测舱表面与 `#8EA7D5` 雾蓝信号，把“宇宙感”表达为大面积安静黑场、稀疏静态星讯、精密暖金属边界，而不是彩色银河壁纸。
- 常规页面的 `#7AA7FF` 雾蓝只承担主操作、选中和焦点；项目广场使用 Win 同源 `#8EA7D5` 信号轨与操作面。两套品牌色占屏幕面积都保持克制。
- `#73C7E8` 只表达信息与连接提示；普通标题不使用彩色。
- `#5AC8A0` 只表达成功、在线、可安装、无需审批或完成。
- `#E7B86A` 只表达注意、项目进度或待处理。
- `#F07884` 只表达需审批、失败、危险或异常。
- 禁止使用大面积彩色渐变、彩色装饰块和持续发光；APK 保持不透明表面与清楚边界。项目广场仅允许 Win 同源的低色差暖石墨舱体渐变、雾蓝到灰青的主操作渐变，以及一个不动画、不抢文字对比度的低透明静态星场和观测弧线。

### 字体

- 使用系统中文字体，不引入花体、衬线体或品牌展示字体。
- 字号层级复用现有好友页和我的页标准。
- 页面内最多保留清晰的标题、正文、辅助信息、小元信息四类层级。
- 不使用负字距，不通过夸张大字制造层级。

### 圆角与容器

- 胶囊用于搜索、筛选、主操作和 AI 会话入口。
- 卡片用于项目广场、详情容器、弹窗和重复对象，不用于包裹所有内容。
- 禁止卡片套卡片，除非内部卡片是明确的重复列表项且视觉重量更低。
- 不使用拟物投影、发光边框或玻璃拟态作为默认风格。

## AI 执行流程

Android UI Tuner、真实 Renderer、React 数字孪生和 APK/PWA 统一 Token 的权威流程见
[`docs/android-real-renderer-ui-workflow.md`](android-real-renderer-ui-workflow.md)。React 数字孪生只负责即时草稿，最终结果必须由无 Runtime Patch 的 Android 构建真帧证明。

AI 接到 UI 任务时，按以下顺序执行：

1. 判断任务是否涉及 APP UI、Web 镜像 UI 或两者同步。
2. 读取本文、`docs/APP 颜色规范.md`，必要时读取 `.github/instructions/apk-web-ui-sync.instructions.md`。
3. 在代码中查找已有同类页面和组件，优先复用。
4. 明确页面的主目标、主状态和主操作。
5. 按已有 token 实现，不临时发明颜色、字号和组件形态。
6. 覆盖加载、空数据、错误、无权限或离线等关键状态。
7. 在小屏和常见宽屏下检查文字、按钮、列表和底部区域是否可读可点。
8. 如改动 APK UI，同步检查 Web 镜像页面。

如果需求和现有规范冲突，AI 不应直接覆盖规范。应先说明冲突点，并把规范更新作为单独、明确的改动。

## Figma 与 MCP 协作

当设计师提供 Figma 页面或参考图时，AI 应把它们转化为项目规范，而不是只照抄单个页面。

推荐流程：

1. 设计师先定义关键页面，例如首页、项目列表、项目空间、聊天页、设置页。
2. AI 通过 Figma/MCP 读取页面结构、组件、间距、颜色和状态。
3. AI 将可复用规则沉淀到本文或 `docs/APP 颜色规范.md`。
4. 后续页面基于规则扩展，而不是每次重新解释审美。
5. 如果 Figma 与现有代码不一致，优先明确是“更新规范”还是“按旧规范实现”。

设计师负责方向和规则，AI 负责扩展和落地。两者是协作关系，不是替代关系。

## 禁止项

- 禁止让 AI 从零自由设计整套 UI。
- 禁止没有读取规范就新增颜色、字号、圆角、阴影或按钮样式。
- 禁止为了区分页面而给每个页面做不同配色。
- 禁止将绿色、红色、黄色用作普通装饰色。
- 禁止在移动端堆叠过多同权重按钮。
- 禁止把说明文字当作交互设计，用长文解释本该清楚的界面。
- 禁止只实现正常态，不考虑加载、空数据、失败、无权限和离线。
- 禁止 APK 和 Web 镜像页面在同一功能上出现明显视觉语言偏差。

## 什么时候更新本文

需要更新本文的情况：

- 产品定位或视觉气质发生变化。
- 引入新的 UI Kit 或设计系统。
- Figma 关键页面沉淀出新的项目级规则。
- 多个页面反复出现同一类设计问题。
- 现有规范无法指导新增模块。

不需要更新本文的情况：

- 只是在现有规范内新增一个页面。
- 只调整某个具体颜色 token、字号或圆角数值。
- 只修复一个页面的布局 bug。

具体 token 和组件数值仍应更新在 `docs/APP 颜色规范.md`。
