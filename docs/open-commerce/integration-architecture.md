# 一龙开放商业融合架构

本文定义现有 AI 开发平台、群体 AI、开放商业网络、共享节点和候选 Sui 经济层如何组合为一套系统。详细字段和接口仍由各专题文档负责。

## 架构目标

用户可以在手机或 PC 描述一个经营目标；系统把目标拆成可审计的开发或经营任务，选择合适的 AI、API 和计算节点执行，生成应用、营销内容或经营结果。商户可以把经过授权的能力暴露给消费者 AI 和第三方应用，而不必把全部数据迁移给新的中心化平台。

## 分层结构

```text
消费者 App / 商户 App / 一龙 APK / PC 工作台 / 第三方 AI
                           |
                    意图与应用交互层
         对话、Demo、应用生成、ERP、海报、视频、小游戏
                           |
                      任务协作层
       Matter、Assignment、Agent、审核、Git 工作区、产物
                           |
                    开放商业协议层
 Merchant、Capability、Grant、ActionConfirmation、Invocation、Meter、Audit
                           |
                     资源执行层
     云模型、用户 API Token、PC 节点、闲置算力、外部服务
                           |
                  回执、计量与结算层
       当前链外账本和审计回执 -> 候选 Sui 结算适配器
                           |
                      数据所有权层
      用户数据、商户数据、项目 Git、凭据保险箱、授权记录
```

## 两条核心闭环

### 应用开发闭环

```text
用户需求
  -> 一龙 AI 澄清和预演
  -> 创建 Matter
  -> 分配 Assignment
  -> AI 或节点在 Git 工作区执行
  -> 审核与验证
  -> 构建和发布应用
  -> 成功经验进入项目文档和上下文
```

这条闭环承接“一个 APK 让用户直接开发应用”和“群体成员一起开发应用”。微信群式沟通是交互入口之一，真正可复用的协作事实必须落入项目成员、Matter、Assignment、产物和审核记录。

### 开放商业闭环

```text
商户发布结构化商业能力
  -> 消费者 AI 或第三方 App 发现能力
  -> 用户授权或商户策略校验
  -> 平台签名调用已验证的商户运行时
  -> 商户 ERP 生成报价并在用户确认后执行交易
  -> 记录计量与审计回执
  -> 商户系统返回结果
  -> 可选进入链外或 Sui 结算
```

平台连接的是能力和授权，不拥有消费者与商户之间的全部关系。基础公开信息可以被发现，客户、订单、财务等私有数据只能在明确授权和最小权限下调用。

## 统一领域对象

| 领域对象 | 作用 | 当前落点 |
|---|---|---|
| Identity | 标识用户、商户、Agent、节点和服务账户 | 现有用户、项目成员与节点身份 |
| Project | 承载应用源码、文档、配置和发布历史 | 项目空间与 Git 工作区 |
| Matter | 表达一个需要协作完成的业务或开发目标 | `server/src/group_ai/` |
| Assignment | 把可执行步骤分配给 Agent、节点或外部能力 | `server/src/group_ai/` |
| Capability | 描述商户或服务提供者可被调用的能力 | `server/src/open_commerce_model.rs` |
| Capability Contract | 用有限 Schema 配置约束能力输入和输出；无效输入不创建调用，无效输出失败并释放预算，不把结构正确解释为业务真实 | `server/src/open_commerce_capability_schema.rs` |
| Runtime Binding | 将能力受控绑定到商户自有 HTTPS 后端；保存地址、服务端凭据引用、Manifest 摘要和验证状态 | `server/src/open_commerce_runtime_model.rs` |
| Merchant Runtime | 由商户维护商品、价格、库存、报价与订单事实，通过统一签名协议接受平台调用 | `contracts/open-commerce/merchant-runtime-v1.json` |
| Grant | 描述谁可在何种范围和时限内调用能力 | 开放商业 V1 |
| Action Confirmation | 记录当前用户对具体动作请求的短时独立确认；绑定 App、商户、能力、Grant、幂等键和输入摘要，与 Invocation 创建原子消费，不保存原始输入值 | 服务端动作确认 V1 |
| Consumer Relationship | 记录消费者主动建立、限时、可撤销及安全续期的匿名商户关系；续期轮换别名且内部链不向商户公开，不保存偏好值、联系方式或订单，也不授予能力调用权限 | 消费者关系凭证与安全续期 V1 |
| Consumer Preference Disclosure | 保存消费者本人低敏结构化偏好，并把明确选择的字段固化为关系级匿名快照；商户只读取有效关系，档案更新和关系续期不自动扩张访问 | 消费者偏好档案与关系级披露 V1 |
| Consumer Data Request | 记录消费者对匿名关系发起的删除请求、关系撤销和商户履约声明；不承载待删除数据，也不把声明解释为外部删除证明 | 消费者关联数据删除请求 V1 |
| Consumer Portability Export | V3 在 V2 关系、续期链、删除请求、低敏偏好和披露之外，加入本人账户级终态调用凭证；总包及每条凭证均以 SHA-256 复核，并兼容旧 V1/V2 原摘要。凭证可含本人已收到的商户结果，但不含原始输入，也不是完整订单、支付或跨运营方导入 | 消费者可携带数据包 V3 |
| Invocation | 记录一次真实商业能力调用 | 开放商业 V1 |
| Developer App | 表达项目内第三方测试应用身份；凭据只保存摘要 | 消费者与开发者沙盒 V1 |
| Authorization Request | 表达第三方 App 对受限能力的申请、用途和商户决定 | 消费者与开发者沙盒 V1 |
| Integration | 描述商户授权的数据来源、接入方式、范围和健康状态 | 开放商业接入控制面 |
| Sync Receipt | 记录适配器同步数量、摘要、结果和时间，不保存原始经营值 | 开放商业接入控制面 |
| AI Resource Policy | 描述项目允许的资源类型、优先级、回退、隐私倾向和成本上限 | `server/src/ai_resource_control/` |
| AI Route Preview | 在不执行任务的前提下解释候选资源和回退 | `server/src/ai_resource_control/` |
| Compute Supply Policy | 由节点所有者显式限定可共享模型、并发和每日阈值，并在派发前原子占位 | `server/src/node_compute_sharing.rs` |
| Usage Receipt | 记录模型、节点、商业能力或任务的可计量事实 | 节点账本、调用审计、链外影子账本 |
| Settlement Intent | 把 Assignment 与真实用量来源绑定，等待人工验收或取消 | `server/src/task_settlement/` |
| Settlement Receipt | 记录验收后不可重复的影子经济判断及双分录 | `server/src/task_settlement/` |
| Settlement Adapter | 把已经确认的回执映射到具体结算网络 | 当前仅实现无网络副作用的 Sui 信封，网络适配器仍是提案 |

## 区块链的适用边界

区块链只在多个独立主体缺乏共同信任、且关键事实不能由单一平台随意修改时提供额外价值。对一龙而言，候选链上层适用于商户向外部 AI 授权数据能力、用户授权 AI 代为交易、AI Agent 之间购买服务、数据调用后的收益结算、商户与节点及协议方分账，以及需要跨平台验证的授权和回执。它承担的是**可信、授权与结算**，不是整个业务系统。

| 候选链上层负责 | 必须继续由链外系统负责 |
|---|---|
| 商户、Agent、能力或结算对象的所有权 | 海量订单和用户行为日志 |
| Agent 能力范围以及授权方、被授权方和有效期 | 图片、视频及其他大文件 |
| 跨平台可验证的授权状态、关键回执和状态摘要 | 实时库存、订单和经营数据库 |
| 已确认交易、收益结算与多方分账 | AI 推理、代码构建和媒体生成 |
| 防止单一参与方静默篡改的关键检查点 | 复杂商业查询、分析和搜索 |
| 最小必要的哈希、时间和争议证据 | 商业数据清洗、脱敏和匿名化 |

Sui 只能作为上述链上职责的候选实现，不能独自完成数据治理。匿名化、最小化、撤销后的链外处置和隐私计算仍是应用与数据层责任；把数据哈希或密文写上链不等于完成匿名化。即使未来接入 Sui，生产数据库、推理系统和经营主链也必须在链上层故障时继续运行。

## 可融合与不可混合的边界

可以融合：

- AI 应用生成与商户 ERP、营销活动、小游戏和内容生产共用工程执行链路。
- 群体 AI 的 Matter/Assignment 与节点算力调度共用任务事实。
- API Token、云模型和闲置节点共用资源选择、预算和用量回执。
- 消费者 App、开发者测试 App 和商户授权共用 Capability、Grant、Action Confirmation、Invocation 与 Audit。
- 开放商业调用与未来结算共用 Invocation 和 Usage Receipt。

不能直接混合：

- API Token 所有权、节点算力贡献、商户数据权利、公司股权和合同收入权不是同一种资产。
- “AI 能生成内容”不代表已具备各平台的发布权限和订单数据接口。
- “多个普通 GPU 的总计算量”不等于“企业级 GPU 集群的同步训练性能”。
- Sui 对象和代币不能成为核心业务数据库的唯一真源；链上层故障时，授权、经营和开发主干仍应可运行。
- 开放协议不等于公开全部数据，也不等于取消身份、隐私、质量审核和争议处理。

## Sui 的候选位置

Sui 适合放在已经产生确定业务事实之后：

1. 将 Project、Task、Capability 或 RevenuePosition 表达为拥有明确所有者的对象。
2. 对同一项目内的大量对象使用动态字段组织状态，避免单个全局账户成为争用点。
3. 对可并行的任务回执和微支付使用对象级并行执行。
4. 使用可编程交易块把验证回执、分配费用和更新状态组合成原子操作。
5. 对共享规则使用共享对象，对用户凭据、商户私有数据和敏感权限仍保留链下控制。

第一步不是发币，而是实现链外 `Usage Receipt -> Settlement Intent -> Settlement Receipt`，证明计量、对账和争议流程成立。随后再接入 Sui 测试网适配器；网络资产、服务 Credit、收入权益和公司融资必须继续分层。

## 多平台接入路径

```text
商户授权或导出
  -> 经审核的平台 / POS 适配器
  -> Integration 接入记录
  -> 有界 Sync Receipt
  -> 商户自有数据存储与 Capability
  -> AI 开发上下文 / Matter / Assignment
```

控制面已实现，但具体平台适配器必须逐项验收。登记一个平台标识只表达准备接入，不代表已获得该平台的官方权限。开发代理读取的上下文只包含能力契约、数据域、授权范围和同步健康度，密钥与原始经营数据不进入代码提示或协作文档。

消费者发现与第三方应用已通过商户主动发布的脱敏目录形成跨项目沙盒闭环；消费者可以建立最长 366 天、可撤销且对商户隐藏账号身份的关系凭证，并主动安全续期或发起删除请求。消费者可保存低敏结构化偏好，显式带入一次发现，或对有效关系选择字段生成匿名快照；关系失效和续期不会自动延续商户访问。消费者还能把本人关系、私有续期链、请求回执、当前低敏偏好和历史披露保存为可验证 V2 快照，旧 V1 摘要继续兼容，但数据包仍不能跨运营方导入，也不包含订单、联系方式或支付。商户能力的输入和输出现按有限 Schema 配置强制校验，结构违例不会被计量为成功；这仍不证明价格、库存或评价真实。商户的完成状态只是链外声明，不能代替 App 调用 Grant 或真实外部删除证明。`cofficethinking` 已作为首个商户自有运行时验证商品、报价、确认下单和订单查询，但尚未形成生产公共网络。生产 App 审核、跨运营方身份互认、偏好跨运营方迁移、外部通知、动态风控和联邦滥用处置仍必须独立实现，不能从参考节点或沙盒状态推导为公共网络已经完成。AI 资源控制面同样只负责真实来源盘点、策略和预演；真实任务继续由现有聊天、AI CLI、节点与计量链路执行。

## 模块依赖方向

```text
产品与行业模板
      -> 群体任务与工程执行
      -> 开放商业领域服务
      -> 资源计量与审计
      -> 可选结算适配器
```

上层可以组合下层能力，下层不得依赖某个具体行业页面、某一种代币或某一家外部平台。这样既能支持当前 APK 开发体验，也能逐步演进到开放商业网络，而不需要重写现有系统。
