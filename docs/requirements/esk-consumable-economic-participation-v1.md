# ESK 可消费经济参与权 V1 需求

## 用户规则

- 用户在主项目持有唯一的 ESK 余额，可用它购买一龙 AI、代理等已上架服务。
- 当前余额同时决定未来治理与团队可分配利润快照权重；支付或转出后，未来权重同步下降。
- 页面必须同时展示当前余额、当前可用余额、占用余额和最近一次分配资格，不得把历史购买额冒充当前权重。
- 页面不得把 ESK 描述为永久 `1 USDT` 锚定、保本、固定年化、交易所账户的直接份额或法定公司股份。

## 会计与接口不变量

1. ESK 余额继续由主项目唯一追加式账本管理；子项目只能消费版本化授权或只读证明。
2. 每次服务支付必须生成独立订单/发票、ESK 资产变动和交付状态，三者共享不可重放的幂等引用。
3. 利润分配必须先固化不可变快照，至少包含政策版本、截止时间、合资格总量、逐账户合资格余额、排除账户、利润池来源和精确舍入余数处理。
4. 协议金库、回收、销毁及未解锁团队余额默认排除；不能通过把用户支付的 ESK 转入金库来增加团队自身分配权重。
5. 已经完成的历史分配不因之后消费而追溯撤销；之后的快照只读取之后的余额事实。
6. `QSHARE` 是量化基金份额，按已对账 NAV 申赎；ESK 不作为 NAV、基金份额或客户本金会计单位。
7. 交易所对账盈亏先影响 `QSHARE` NAV；只有已确认团队费用收入经审批后才能进入 ESK `distributable_profit`。
8. 未核对的客户 USDT 必须进入待对账队列，不自动铸造 ESK、不自动申购 `QSHARE`、不自动向交易所下单。

## AI 实施门禁

任何代理实现 ESK、服务支付、量化接入、治理或利润分配前，必须同时读取本需求、对应 ADR、`docs/decisions/esk-asset-naming-v1.md` 和 `docs/yilong-quant-integration.md`。代理不得自行拆出第二枚团队权益币，也不得因为单币多效用而合并订单、资产、基金和利润分配账本。

运行时必须逐级启用：`paper -> shadow_accounting -> approved_live`。本需求和量化核心代码只达到前两级设计/测试能力；没有独立资金对账、权限分离、风险限额、审计和发布验收时，`approved_live` 必须保持不可选。
