# 一龙 Sui 原生 AI 项目经济与开放商业网络架构草案

## 文档状态

本文把一龙现有 AI 开发平台、群体 AI、共享节点、开放商业网络和未来融资构想整理为阶段四候选架构。它用于后续产品讨论、领域建模和测试网任务拆分，不授权 AI 代理直接发币、迁移现有账本或改变当前生产路径。

本文不改变开放商业网络 V1，也不代表区块链、代币、收入份额、去中心化存储或分布式 GPU 已经实现。现行产品与协议边界以 `AI_PROJECT.md`、`AI_ARCHITECTURE.md`、`docs/decisions/open-commerce-network-v1-architecture.md` 和对应实现证据为准。

已确认的长期边界只有三项：

1. Sui 只作为候选所有权、授权、结算、信誉和治理层。
2. Sui 不承载模型计算、Git 工作区、实时聊天和原始经营数据。
3. 链上经济层必须建立在真实产品、真实调用、真实回款和可执行争议流程之上。

其余代币名称、发行量、收入分配比例、组织结构和流动性方案均为待验证提案。

## 一句话定位

> 一龙让用户在手机或 PC 发起项目，由多人、多个 AI 和授权计算节点共同完成软件交付；Sui 候选层把项目、能力、贡献、合同和收入变成可编程的所有权与结算对象。

项目目标不是单纯发行代币，而是建立 AI 原生项目经济网络：项目成员、消费者 Agent、商户 Agent、技能开发者、审查者和算力节点可以使用不同 App，通过统一对象和协议发起任务、授权能力、完成交付并自动结算。

## 当前能力基线

后续 AI 代理必须区分“代码中已有主路径”“已有核心但仍需产品化”和“阶段四设想”。

### 已有主路径

- Android APK 和 PC 工作台可以作为项目、对话、任务进度和交付入口。
- 项目空间已有成员、角色、频道、消息、邀请、AI 开发任务和权限边界。
- AI 可以进入真实 Git 工作区修改代码，并经过验证、构建和发布流程交付 APK 或网页。
- 群体 AI 已有 Matter 计划、任务分工、审批、审查和合并门禁等核心模块。
- Windows 节点可以执行本地 CLI、文件、Git、构建和设备任务。
- 开放商业网络 V1 已实现商户节点、能力发布、发现、授权调用、计量审计以及 HTTP/MCP/PC 同源服务闭环。

### 已有核心但仍需继续收口

- `route_c2` 和 `route_c3` 已支持授权使用其他用户 PC 上的 API runtime 或已登录 CLI；不同产品入口的覆盖和失败恢复仍需统一。
- 公共开发节点已有授权、运行时握手、用量记录和提供者收益账本；它属于任务级远程执行，不等于任意 GPU 的张量级分布式计算。
- 用户自带 API Key 已采用加密保存和远程能力调用思路。产品对外应称为“共享 AI 能力”，不得共享或暴露明文 Token。
- 多用户、多节点、多 Agent 的核心闭环已有实现，但规模化调度、统一市场体验、争议仲裁和服务等级仍需验证。

### 尚未实现

- Sui Move 包、链上项目对象、收入份额资产、网络代币和链上治理。
- 大量闲置 GPU 聚合成等效企业级 GPU 的通用训练或推理系统。
- 法币回款证明、稳定币兑换、月度链上分配和独立审计。
- Walrus、Seal、DeepBook、链上身份与现有账号体系的生产集成。
- 任何形式的代币化公司股权。

## 与现有路线的关系

```text
现有底座：APK/PC + 项目空间 + 群体 AI + Git 交付 + Windows 节点
  -> 开放商业 V1：商户节点、能力发布、授权调用、计量审计
  -> 阶段二：标准化商户节点和可迁移数据
  -> 阶段三：跨 App 发现、调用与真实结算
  -> 阶段四：评估 Sui 项目对象、收入份额、网络激励和治理层
```

Sui 方案不能成为前三阶段的依赖。只有真实商户密度、稳定调用量、真实结算和争议处理得到验证后，才进入原型研究。

## 候选分层架构

```text
Android APK / PC / 项目频道 / 第三方 App
                      |
        项目空间、Matter、权限和人工决策
                      |
       群体 AI 规划、执行、审查和合并
                      |
 自有 PC / 自有 Key / 平台 AI / 授权远程节点
                      |
       Git、测试、构建、APK/网页发布
                      |
       开放商业 API、SDK、MCP 和商户节点
                      |
        Sui 候选所有权与结算适配层
            |                    |
  对象、托管、分账、信誉       链外执行与数据
  治理、收入份额、摘要       PC/GPU/Git/云/Walrus
```

模型推理、代码构建、图片视频生成和 GPU 任务在链外执行。链上只登记资产归属、能力凭证、任务状态、支付条件、结果摘要、信誉与争议证据。

## Sui 原生设计原则

前期架构是“可以部署在 Sui 上”，目标架构应进一步做到“Sui 原生”：

1. 一个主网络币、多个有明确类型的权利对象、稳定币结算，不用一个币承载所有权利。
2. 每个项目、合同、任务、节点和收入池分别建模，不建立承载全网状态的单一共享对象。
3. 优先使用地址所有对象和能力对象；只有多人必须共同修改的状态才使用共享对象。
4. 权限由 `OwnerCap`、`AgentCap`、`ReviewerCap`、`NodeCap` 等能力对象表达，而不是只依赖地址白名单。
5. 可编程交易块只负责需要原子性的授权、托管、验收、分账和凭证生成。
6. 原始代码、聊天、客户数据和模型结果不上链；链上保存最小摘要、哈希、权限和结算事实。
7. 资本贡献、劳动贡献、专业审查和产品使用分别记账，不能简单退化为“一币一票”。

核心产品原则可以概括为：

> 一枚网络币协调全网信任；不同对象表达不同权利；稳定币支付真实服务；Git、AI 和商业数据继续在链外高效运行。

## Sui 特性与项目映射

| Sui 能力 | 项目中的候选用途 | 设计约束 |
|---|---|---|
| 对象模型 | Merchant、Agent、ComputeNode、SkillPackage、Job、Escrow、DataCapability、ResultReceipt、Reputation | 不把所有状态集中在单一全局对象 |
| 并行执行 | 每任务独立建模，市场按区域、行业或能力分片 | 压测共享对象热点、延迟和成本 |
| 可编程交易块 | 原子完成托管、授权、验收、分账和信誉更新 | 争议和复杂验收仍需链外服务 |
| zkLogin 类入口 | 使用熟悉账号进入 | 用户不直接处理助记词 |
| 赞助交易 | 平台或套餐代付 Gas | 需要额度、限流和防滥用 |
| Kiosk 类机制 | 技能、模板、小游戏和 Agent 插件的授权与版税 | 可交易性不能替代质量审核 |
| Walrus/Seal 类能力 | 保存并按策略开放加密模型、记忆、代码和媒体 | 原始经营数据不上链，访问可撤销、可审计 |
| Nautilus/TEE 类能力 | 验证部分链外任务环境和结果 | 不等于任意 GPU 任务都可验证 |
| DeepBook 类流动性 | 网络代币确有兑换需求时提供流动性 | 不作为商户使用产品的前置条件 |

实施时必须按届时 Sui 官方文档和测试结果重新核验这些能力。

## 候选对象模型

对象名用于表达领域边界，不是已经冻结的 Move 类型名。

本文中的插件、模板或 `SkillPackage` 指未来可授权的商业能力包候选，不改变 `AI_PROJECT.md` 的当前决策：平台内部 AI-to-AI Skill 继续由官方维护，不建设第三方 Skill 买卖市场。若未来需要第三方插件生态，必须与内部 Skill Registry 分开建模和决策。

| 对象 | 表达的事实 | 主要状态变化 |
|---|---|---|
| `HumanProfile` | 用户身份、公开资料和关联项目 | 创建、授权、注销 |
| `Reputation` | 不可购买、不可转让的履约和贡献记录 | 验收、争议、处罚 |
| `ProjectObject` | 一个可拥有资金、任务、能力和收入来源的 AI 项目 | 创建、融资、交付、归档 |
| `MemberCap` | 成员在项目中的角色和最小权限 | 签发、降权、撤销 |
| `AgentObject` | AI 代理的模型、能力、运行范围和提供者 | 注册、升级、停用 |
| `AgentCap` | AI 在特定项目和期限内可执行的动作 | 签发、使用、撤销 |
| `MatterObject` | 用户目标、子任务、预算、验收和争议规则 | 草案、批准、执行、验收 |
| `Assignment` | Matter 中分配给某个 Agent 或节点的子任务 | 承接、交付、失败 |
| `ComputeNode` | PC、API runtime、CLI 或未来 GPU 节点的能力和 SLA | 上线、报价、执行、退出 |
| `ResultReceipt` | Git 提交、构建产物、测试结果和任务摘要 | 提交、审查、接受 |
| `MerchantCapability` | 商户对外发布的可发现、可授权商业能力 | 发布、授权、调用、撤销 |
| `CustomerContract` | 客户合同的摘要、期限、回款规则和证据引用 | 登记、履约、暂停、终止 |
| `RevenueSeries` | 一个合同或合同组合对应的收入份额池 | 创建、入池、分配、到期 |
| `RevenuePosition` | 持有人在收入池中的份额与领取进度 | 拆分、合并、转让、领取 |
| `DistributionEpoch` | 某月实际回款、储备、费用和每份可分配收益 | 证明、确认、开放领取 |
| `ProtocolConfig` | 网络费用、质押、处罚和升级参数 | 提案、表决、延时生效 |

### ProjectObject：链上微型项目经济体

每个项目不是发行一枚独立空气币，而是形成一棵可审计的对象树：

```text
ProjectObject
  |- ProjectTreasury
  |- MemberCaps
  |- AgentCaps
  |- MatterObjects
  |- NodeAssignments
  |- RevenueSeries
  |- GovernancePolicy
  `- EvidenceRoot
```

项目空间仍在现有服务端管理实时消息、成员体验和任务过程。Sui 候选层只镜像需要跨主体验证的权利、资金和结果，不替代现有数据库。

## AI 任务与算力结算闭环

1. 项目成员在 APK、PC 或项目频道提出目标，现有协调器生成 Matter 草案。
2. 有权限成员批准 Matter，并声明预算、权限、期限、验收和争议规则。
3. 预算进入 Escrow；自有节点、公共开发节点或技能 Agent 报价并承接 Assignment。
4. 系统签发最小权限、限时、可撤销的 AgentCap 或 DataCapability。
5. 节点在现有 Git worktree、PC、云端、GPU 或可信执行环境完成任务。
6. Git 提交、构建、测试和结果文件继续留在链外，链上登记摘要、索引和 ResultReceipt。
7. Reviewer、规则引擎或人工完成验收；不能用执行者自报成功代替验收证据。
8. 可编程交易块原子释放费用，向节点、开发者、审查者和协议服务方分账。
9. 成功、失败和争议更新不可转让 Reputation；作恶可触发质押惩罚。

一次项目交付的候选原子交易为：

```text
验证验收凭证
  -> 释放客户或项目托管款
  -> 支付执行 Agent
  -> 支付计算节点
  -> 支付独立审查者
  -> 提取协议服务费和风险储备
  -> 更新 Reputation
  -> 生成不可重复的结算回执
```

## 资产与权利分层

### NET：主网络安全与治理资产

NET 是主网络代币的占位名，品牌候选可使用 `YILONG`。候选用途是节点、开发者、审查者和商户服务商质押，承担作恶惩罚、协议治理、使用折扣及长期网络激励。它不直接承担商户日常服务计价，也不自动获得公司全部收入，避免币价波动传导到 AI 使用成本和合同现金流。

### CREDIT：稳定服务计量单位

CREDIT 为闭环、价格稳定的服务积分，用于 AI Token、GPU 时间、构建、存储和能力调用。用户可充值或通过完成真实算力任务获得；发行、赎回、退款和兑换规则须单独验证。

### RevenuePosition：特定合同收入份额

收入份额不是 NET 的附加承诺，而是绑定特定 `RevenueSeries` 的独立期限资产。持有人只按规则分享该收入池的实际到账净现金，不自动取得公司股权、其他合同收益或协议治理权。

### FounderPass：早期社区身份

FounderPass 可表达早期测试、产品额度、讨论和提案资格，不承诺固定收益。创始人作为 AI KOL 形成的社区信任属于冷启动和分发优势，不能替代合同证据、资产定价、锁仓和多签约束。

### Reputation：不可购买的信誉

商户、Agent、开发者和算力节点的履约、争议和能力认证进入不可转让信誉对象，不能通过购买 NET 或 CREDIT 获得。

### Stablecoin：真实结算资产

节点报酬、开发者收入、收入份额分配和退款优先使用被系统接受的稳定币结算。NET 负责质押与协调，不能强迫贡献者承担网络币价格波动。

网络价值的核心指标是：

```text
活跃项目和商户节点数量
  x 可调用 Agent、技能和节点数量
  x 验收通过的有效任务量
  x 真实结算与复购量
```

代币价格不属于产品价值验证指标。早期收入继续来自商户 AI 经营系统、托管、能力调用、任务执行、结算和插件市场服务。

## 合同收入融资候选模型

### 当前创始人陈述

创始人当前陈述：项目已有一份期限十年的客户订单，合同约定每月收入人民币 2 万元，并希望出售部分未来收入份额支持产品开发。该信息在进入任何产品展示、融资计算或链上对象之前，必须核验合同、服务义务、终止条款、回款记录、付款方风险和可分配净现金。

文档不得把“已签合同”直接写成“无风险保证”。只有预付、托管、独立担保或已经实际到账的现金，才能提高确定性；区块链不能消除客户违约和项目履约风险。

### 现金流与融资边界

```text
合同名义收入 = 20,000 元/月 x 120 个月 = 2,400,000 元
```

名义总额不等于当前融资价值。估值必须考虑资金时间价值、服务成本、客户违约、退款、运营储备和证据可信度。

首期候选结构不是出售全部十年收入，而是：

- 只出售未来 36 至 60 个月的一部分实际到账净现金；
- 为公司保留持续运营收入；
- 设置 3 至 6 个月风险储备；
- 每月按实际回款分配，不用新投资款补足旧投资人的收益；
- 投资人通过 `RevenuePosition` 持有份额，通过 `DistributionEpoch` 领取稳定币。

以下数字只用于说明结构，不是已接受融资参数：

```text
实际月回款：20,000 元
候选出售比例：40%
投资人可分配上限：8,000 元/月
公司保留及服务资金：12,000 元/月
候选期限：60 个月
```

新增每月 10 万元或其他长期合同应创建新的 `RevenueSeries`，不能无偿加入旧收入池。成熟后可以建立多合同指数池，但新增份额必须按风险调整后的净现值和当前每份净资产值发行，避免稀释和利益转移。

### 月度分配对象

```text
DistributionEpoch
  |- revenue_series_id
  |- period
  |- gross_receipt
  |- servicing_cost
  |- reserve_amount
  |- distributable_amount
  |- payout_per_unit
  |- evidence_hash
  |- attestors
  `- status
```

`RevenuePosition` 保存 `units`、`last_claimed_epoch` 和累计领取状态。拆分、合并或转让时必须同时携带收益进度，防止重复领取和分配日前短期套取收益。

## 公司、协议与社区的候选关系

长期结构不应让一个主体同时控制客户合同、代币增发、回款证明和资产分配：

```text
运营公司 OpCo
  |- 签订客户合同
  |- 持有并开发核心产品
  |- 提供交付和售后
  `- 接受传统股权融资

协议基金会或 DAO
  |- 管理开放协议和 NET 金库
  |- 制定节点、开发者和商户规则
  `- 资助公共基础设施

独立 RevenueSeries
  |- 绑定特定合同或合同组合
  |- 保存回款与分配规则
  `- 向 RevenuePosition 持有人结算
```

合同收入份额更接近应收账款份额或收入权；NET 更接近网络参与和治理资产；公司股权代表运营公司的剩余所有权。只有当链上资产获得公司剩余利润、表决、增发、清算和并购权利时，它才在经济上接近代币化股票。

项目的候选终局不是用一个币替代公司，而是让公司股权、合同收入份额、网络功能资产和稳定币结算各自表达清晰权利。

## 分层治理候选模型

单纯“一币一票”会让资本购买全部产品和技术决策权。候选治理可以分为：

| 治理层 | 依据 | 适合决定 |
|---|---|---|
| 资本层 | NET 质押和锁定时间 | 金库预算、网络费率、经济参数 |
| 贡献层 | 不可转让 Reputation | 节点标准、贡献奖励、社区提案 |
| 专业层 | ReviewerCap 和公开履历 | 协议升级、安全、审计和争议 |

普通参数可由单层决定；协议升级、大额金库支出和资产规则变更需要多层共同批准。创始人早期的特殊权限必须公开、可审计并设置失效或移交条件。

`TreasuryCap`、`UpgradeCap`、回款确认、紧急暂停和 RevenueSeries 创建权应由不同多签或能力对象控制，不能集中在创始人单一私钥。

## 阶段四内部实施里程碑

这些里程碑属于开放商业路线“阶段四”内部，不提前替代阶段一至三。

### S4.0：领域模型与链外影子账本

- 固化对象、状态机、事件、权限和失败语义；
- 在现有服务端建立只读或影子经济账本；
- 不发行代币，不迁移生产资金；
- 用现有 Matter、节点用量和开放商业调用生成模拟结算。

首个实施切片采用“共享节点任务经济回执”，详细边界、状态机、账本不变量、代理拆分和验收标准见 `docs/drafts/sui-economy-s4-shadow-settlement-plan.md`。该切片只映射现有计费事实，不重复扣款，并将算力补偿与任务结果奖励明确分开。

### S4.1：Sui 测试网适配器

- 建立独立 Move 包和服务端适配器；
- 先验证 `ProjectObject`、`MatterObject`、`ComputeNode`、Escrow 和 ResultReceipt；
- 使用测试资产验证托管、验收、退款、分账和重放保护；
- 对共享对象热点、Gas、失败恢复和包升级进行压测。

### S4.2：节点任务结算试点

- 选择低风险、结果可验证的开发或 AI 任务；
- 节点继续在链外执行，链上只保存预算、验收和结算；
- 使用稳定币或测试 CREDIT 支付，NET 只做测试质押；
- 建立争议、复算、处罚和人工兜底。

### S4.3：收入份额封闭试点

- 核验至少一个真实合同和连续回款记录；
- 创建独立 RevenueSeries、储备规则和月度证明；
- 使用少量、受控参与者完成连续 6 至 12 次分配；
- 在稳定运行前不开放无限制二级交易。

### S4.4：NET 网络资产

- 只有节点市场、AI 调用、插件或开放商业网络已有真实使用量后才进入；
- 固化总量上限、释放计划、团队锁定、金库多签和处罚规则；
- 主要通过可验证贡献释放，不以代币价格代替产品指标；
- 上线流动性之前完成合约审计、密钥恢复和紧急暂停演练。

### S4.5：公司融资与链上治理桥接

- 运营公司继续接受股权或其他公司级融资；
- 股权、NET 和 RevenuePosition 分别披露、分别核算；
- 评估协议基金会或 DAO 是否已经有独立存在价值；
- 只有公司权利和链上权利能够明确映射时，才研究代币化股权。

## AI 代理实施边界

后续 AI 代理使用本文时必须遵守以下顺序：

1. 先核对 `.elon/document-sections.json` 的能力图和实现引用，不用本文证明功能已经实现。
2. 先建立领域状态机、账本不变量和失败测试，再选择链 SDK 或 Move 类型。
3. 现有中心化数据库、项目权限和任务日志继续作为生产真源；迁移必须单独决策。
4. 链上集成放在独立适配器和功能开关后，不把 Sui 调用散落到项目空间、群体 AI 或开放商业模块。
5. 每个新领域模块只负责一个边界，例如收入账本、节点结算、链适配器或治理，不建立巨型 `sui_manager`。
6. 先使用测试网和测试资产；没有审计、回滚、密钥恢复和争议流程时不得接触真实资金。
7. 对外状态必须使用“已实现”“验证中”“草案”“长期设想”四类明确标签。

建议的代码责任边界为：

| 责任 | 候选模块 | 不应承担 |
|---|---|---|
| 领域对象与状态机 | `economy_domain` | RPC、钱包和 UI |
| 双重记账、收入与分配 | `revenue_ledger` | 代币交易和项目聊天 |
| 节点任务计量与结算 | `node_settlement` | 节点进程管理 |
| Sui RPC、交易与对象映射 | `sui_adapter` | 业务决策和合同估值 |
| 权限、多签与治理流程 | `economy_governance` | 客户合同原文 |
| PC/APK 展示 | 独立 feature 页面 | 私钥和服务端签名 |

模块名尚未冻结。真正实施前应先检查现有模块和文件规模，优先复用清晰边界，不为了匹配本文机械重命名。

## 尚未决定

- 主网络代币的最终名称、总量、释放比例和质押参数；
- CREDIT 是内部余额、闭环 Token 还是稳定币计价接口；
- 收入池由何种组织持有合同权利；
- 回款证明由支付机构、审计者、Oracle 还是多方共同确认；
- 首期融资期限、出售比例、储备和估值折现率；
- FounderPass 是否需要链上转让；
- 网络治理是否需要基金会、DAO 或公司委员会；
- 是否以及何时接入 DeepBook 等二级流动性；
- 公司股权是否需要链上映射。

## 关键风险与进入条件

- 任意 GPU 任务的验证成本可能接近重新执行，需设计复算、抽检、证明和争议机制。
- 高并发共享对象可能形成热点，必须按真实对象模型压测。
- 激励应主要来自真实任务收入，不能长期依赖新增代币补贴。
- 创始人和社区信任可以带来冷启动，但不能替代锁仓、多签、回款证明和独立审查。
- 一个资产同时承载功能、分红、股权和治理会放大价格、挤兑和控制权风险。
- 链上记录只能证明提交了什么，不能自动证明链外合同真实、客户必然付款或 AI 结果正确。
- Sui 不能解决第三方平台拒绝开放 API、原始数据失真或 AI 结果质量问题。
- 候选组件的成熟度、成本、退款、密钥恢复和争议流程必须单独验证。

进入测试网原型前，应同时满足：阶段二、三已证明跨 App 调用；存在稳定计费和分账需求；节点贡献可用任务结果和 SLA 衡量；中心化账本已出现真实的多方信任或迁移成本；普通用户无需理解钱包和 Gas；失败、退款和争议已有可执行方案。阶段二、三完成前只允许推进 S4.0 的领域模型、影子账本和测试设计。
